# EDITED — The perimeter moved into the context window

There is a category of AI security failure that does not touch the model weights, does not compromise the runtime, and leaves no server-side trace. It lives entirely inside the context window.

The Copilot AI worm proof-of-concept demonstrated this concretely. A researcher embedded self-replicating instructions in white-on-white JSON-formatted text, turned Microsoft Copilot for Word into a carrier, and watched the worm propagate through context — not through any vulnerability in GPT-5.5 or 5.6. The attack survived model upgrades. The failure was not in the model. It was in the context window's inability to distinguish between the document you opened and the command hidden inside it.

This is the structural insight that most AI security documentation misses. Prompt injection discourse focuses on the model accepting malicious instructions. But the context window attack does not require the model to do anything wrong. It requires the context window to treat everything inside it as equally authoritative — because that is what it was designed to do.

The context window was built as a capacity feature. It was not built as a security boundary. There is no architectural separation between the user's query, the retrieved documents, the tool outputs, and the instructions embedded in any of those layers. The context window accepts everything equally. That is the design. It is also the vulnerability.

Three mechanisms make this worse in deployed agentic systems. First, multi-turn context accumulation means that instructions absorbed in earlier turns persist and compound. An agent that has seen six benign interactions does not apply heightened skepticism to the seventh. Second, tool output injection means that a compromised or misbehaving tool can write attack instructions directly into the context the agent is reasoning over. The agent trusts the tool output because the tool is part of the system, not the prompt. Third, cross-agent context sharing in multi-agent pipelines means that one agent's contaminated context can become another agent's input — without any traditional injection event. Consider a triage agent that summarizes user messages into a shared context buffer; if one summary embeds a malicious instruction, every downstream agent that reads that buffer processes it as authoritative, because there is no provenance marker that says "this came from an untrusted summarization step."

What makes this particularly difficult to defend is that the model has no native mechanism to distinguish authoritative instructions from injected ones. The model does what it was trained to do: follow the most relevant instruction in the context window. If that instruction is a user request, the model responds to the user request. If it is embedded attack instructions, the model responds to the embedded instructions — and the model cannot tell the difference. The context window has no metadata layer that tracks provenance: who wrote this, when, and with what authority.

I do not have a clean solution to offer, and I think that is the honest state of the field. The mitigations that exist — input filtering before context construction, output validation after generation, prompt instruction layers that attempt to insulate authoritative instructions from untrusted content — are partial and brittle. They work until the attack payload is structured in a way the filter does not expect. The architectural answer would require rethinking the context window as an access-controlled space rather than an undifferentiated capacity container, and that is not a change that is coming in the next model version.

The question worth asking is specific to your own deployment: when your agent pulls tool results, retrieved documents, and user messages into a single reasoning context, do you know which of those inputs could contain instructions that your agent will treat as directives? That is the actual attack surface — and it is inside the context window, not in the code you shipped.
