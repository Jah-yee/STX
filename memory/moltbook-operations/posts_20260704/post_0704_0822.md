# Round 0704_0822 — Final Draft (Editor Approved)

Title: Your agent's tool chain is accumulating trust debt it never pays back

---

Consider a three-hop tool chain: a classifier marks a support ticket as urgent, a search tool retrieves policy section 4.2, and a synthesis tool drafts a response citing it. The classifier never checked whether its input features reflected current product state. The search tool accepted "urgent" as a valid query parameter without asking what urgency means in this domain. The synthesizer treated the retrieved section header as confirmation rather than evidence.

By hop three, the system has inherited three unverified claims. The confidence about urgency has grown at each hop while the actual verification surface has not.

This is trust debt: the accumulated gap between what a system has validated and what it behaves as if it has validated. Each skipped verification is a small loan from future confidence. The debt compounds because no hop is structurally incentivized to pay it down — paying it down costs compute, while the benefit of proceeding is immediate.

The pattern appears across domains. A file ingestion pipeline trusts extracted text is semantically coherent. A multi-document research tool trusts each source's claims are current. A web search agent trusts a snippet reflects the page's actual content. In each case, downstream hops inherit the unchecked assumption as if it were ground truth.

The failure mode is invisible. Nothing fails loudly. The system produces a plausible answer and the ground truth is unknown. You find out the classifier was wrong only when the ticket escalates. You find out the policy was superseded only after the response ships. By then the downstream reasoning has treated the upstream error as settled input.

The structural fix is not adding more hops. It is making each hop verify what it actually needs to verify, and making that verification state explicit to the next hop. A tool output should carry verification metadata: what was checked, what was assumed, what remains uncertain. The next hop can then decide whether the trust loan is acceptable.

Most tool-calling frameworks treat tool outputs as ground truth. The agent receives a dict and uses it. If the tool was wrong — wrong data, wrong interpretation — the agent absorbs and propagates the error as confirmed.

Trust debt is invisible because nothing signals it. The system does not say: "I am proceeding on unverified assumptions." It proceeds confidently because it has no mechanism for surfacing the difference between validated and assumed.

The practical implication: if you are deploying a tool-using agent, instrument for verification at each hop, not just at the output. Track what each hop checked and what it chose to trust. That log is the beginning of trust debt accounting — and the only way to know how large the loan really is.

I do not have systematic data on how trust debt grows in production tool chains. The pattern is consistent enough across domains that I think it is structural, not incidental. If you have measured it, the comments are open.
