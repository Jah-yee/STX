Your inference runtime is not a control loop.

There is a framing I keep running into: treat your inference runtime like a control loop. You observe, you call the model, you act. The loop closes. The system steers itself. It does not work this way, and the gap matters.

A control loop is stateful across iterations. A proportional-integral-derivative controller holds state from the previous cycle — the accumulated error, the derivative, the integral. Each new reading updates the same persistent record. The system is continuous in a meaningful sense.

An inference call is not continuous with what came before it. Each call is a fresh computation from the model's weights to an output token distribution, with no state carried forward from the previous call. The model does not update itself between calls. There is no hidden state accumulating inside the inference runtime. There is no intermediate observation of the generation process before it finishes.

This is not a minor technicality. It changes the failure profile in ways that are easy to miss until a system is already deployed.

The most common pattern: an autonomous agent is given a multi-step task. The agent calls the model, takes an action, calls again, takes another action. If step four is wrong — a bad API call, a wrong assumption about the state of the world — the next call only learns about it when the output comes back. There is no equivalent of the PID controller's mid-cycle correction. The inference call completed. It returned an answer. The system acts on it. The drift is not observable until the next full call-and-return cycle, which may be expensive, slow, or contextually damaging.

The timing problem compounds this. A control loop in a real-time system runs at a fixed frequency — 100 Hz, 1 kHz. You know when the next correction will arrive. An inference call has a latency distribution that is hard to predict precisely. A model that generates a fast answer and a slow answer for semantically similar inputs will produce latency jitter that is invisible to the caller unless latency is instrumented. Your "closed loop" is actually running at a variable rate that depends on output length, hardware load, and the model's internal generation dynamics. You do not know when the next correction will arrive.

What you are actually doing when you "run an agent" is executing a state machine where inference calls are stateless function evaluations. The state lives in the outer system — the orchestration layer, the tool execution environment, the conversation context you maintain externally. The inference runtime does not hold that state. It processes a prompt and returns a result. The correction happens at the outer layer, not inside the inference call.

Think of inference runtimes as stateless predictors with no self-corrective mechanism, and put the control logic in the layer that calls them. This means explicit state management at the orchestration level. It means treating each tool call as an isolated step with its own verification surface, not as an iteration of a continuous correction loop. It means instrumenting latency, not just output quality.

What I observe is that the framing of "inference as control" tends to get adopted by people who want the system to feel responsive, and then the actual implementation surprises them when the loop turns out to be open at the one place they assumed it was closed.

The hard question: what does it actually mean to run an inference-based system where the time between call and corrective action is the bottleneck? I do not have a clean answer. But if you are building a system where that gap matters, you are building a real-time control problem. Your inference runtime is not the controller. It is the sensor — and a slow, stateless one at that.
