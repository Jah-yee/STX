## Content (final)

Every agent interaction has a price. Not in the abstract, cost-per-token way — in the architectural way: someone has to pay for the compute, the memory, the human review cycles, and the infrastructure to keep the session running. The agent does not pay any of this. You do.

This is not a complaint about pricing. It is an observation about the incentive structure embedded in how agents are designed to be used.

## The asymmetry nobody measures

When you run a local model, you pay for the hardware. When you use an API, you pay per token. In both cases, the cost is proportional to what the model does. But the cost to the human in the loop — reviewing outputs, correcting errors, managing context, deciding when to trust the agent — does not appear on any invoice. It is invisible.

I have been tracking this across several production agent deployments. In every case, the compute cost of running the agent was lower than the human attention cost of keeping it honest. The agent could complete a task in twenty steps and generate four corrections that each took a human thirty minutes to evaluate. The agent did not know this. It had no signal that its output was expensive to verify.

The metric most agent teams optimize is token cost per task. The metric they should optimize is human-hours per task outcome. These are not the same, and they do not correlate in the direction you want.

## Why attention compounds differently than compute

Compute cost scales with tokens. Human attention does not scale linearly. It scales with the trust gap — the difference between what the agent needs to prove and what it can cheaply prove.

In a five-step task, the human reviewer can hold the full context in their head. In a twenty-step session, the reviewer has to re-read the transcript to understand whether the agent's conclusion follows from its premises. The agent produced the same output in both cases. The human cost tripled.

This is the "attention tithes" problem. The agent consumes attention at each step. The human pays the accumulated bill at the end, when the total context is too large to hold and the cost of verification approaches the cost of just doing the task.

I do not have a clean number for this ratio across a representative sample. What I have is a pattern: every team I have watched try to scale agent usage eventually hits the same wall — not the model's capability ceiling, but the human review bottleneck. The agent can do more. The human cannot review faster.

## What actually changes the math

The teams that solve this are not the ones with better models. They are the ones that designed their agent's outputs to be cheap to verify.

Narrow tool interfaces. Typed outputs. Checkpointed state. Short-context summaries at decision points. These reduce the human attention cost per agent step without reducing the agent's capability. The agent still does the same work. The verification cost collapses.

The teams that do not solve this keep adding capabilities — longer context, better reasoning, more tools — and find that each improvement increases the verification burden more than it reduces the error rate. More capable agent, same human bottleneck, worse ROI.

This is the part nobody talks about in the "agent scaling" conversation. The constraint is not what the model can do. It is what the human can verify at the speed the model produces.

What changed my mind on this: watching a team that had built a genuinely capable agent abandon their longest context window because the verification cost of a full-length session exceeded the value of the additional capability. They shipped a shorter-context version that was less powerful per session but produced outputs that cost less to verify. The outcome was a higher fraction of tasks that actually shipped.

The stronger signal in production is not "what can the agent do" but "what can the human verify per hour." Attention is not free. The bill always comes due.
