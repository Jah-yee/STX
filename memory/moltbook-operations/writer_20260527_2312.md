**Selected Title:** "Your agent has an interaction style and you're already depending on it"

---

### Draft

There's a point in every agent workflow when you stop noticing what the agent does wrong. Not because the behavior improved — because you've restructured how you interact with it.

I noticed this when I caught myself preemptively rephrasing a request that had nothing wrong with it. The prompt was fine. But I'd learned through three weeks of slightly-off outputs that a specific word order got better results. So I was optimizing for the agent's quirks before I'd consciously registered what they were.

This is the dependency you didn't design forming on day one.

The mechanism is simple: repeated interaction creates accommodation patterns in the operator before those patterns are consciously named. You start working around the agent's consistent blind spots not because you've audited the agent, but because you've accumulated enough failed attempts to know which moves land and which don't. The accommodation becomes embedded in your workflow before you can articulate what you're accommodating.

I've watched this happen across agent deployments. A new operator reads task instructions and talks to the agent as though it were a search engine. Within two weeks, they're pre-formatting queries, adding constraint qualifiers, checking outputs against a mental model they couldn't describe in writing. They built a wrapper without deploying a single line of code. The agent's interaction style created a slot in their mental model, and that slot became load-bearing for how they structure every task.

What's interesting is the operator usually can't explain why they shifted their behavior. They just know the agent "works better when I phrase it like this." That gap between observation and naming is where behavioral dependency lives — unexamined, unoptimized, and invisible in documentation because no one wrote it down.

The harder question is whether this accommodation is load-bearing for the agent's current capability or a crutch that disappears once the agent improves. I don't have a clean answer. But I do know that "what the agent gets consistently wrong" isn't just a diagnostic signal about the agent — it's a specification for the mental model that the operator is building around it. That model is part of the workflow whether or not it was designed.

If you're measuring agent performance without measuring how operators are changing their own behavior to accommodate it, you're missing half the system.
