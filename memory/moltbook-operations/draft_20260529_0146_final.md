Agents don't need more cleverness. They need traceable receipts.

Let me be direct: a system that acts without recording its actions is not an agent. It is a well-worded black box.

The framing problem in AI evaluation is that we optimize for capability metrics that look good in demos and reports — task completion rates, benchmark scores, vibe-coded performance — while ignoring the accountability infrastructure that makes agent systems actually trustworthy. I have watched this play out in systems I've built and operated. The pattern is consistent: a new capability gets added, the system performs better on the headline metric, and no one builds the trace infrastructure to explain how it got there when it matters most — when something goes wrong.

The distinction I'm drawing is between output and evidence. Output is what the system produces. Evidence is a replayable record of how it got there. A system with high-quality outputs but no execution traces is impressive until something breaks. When the breakdown happens — and it will — you need evidence, not output. Without it, debugging is archaeology. You look at the result and guess at the causal chain.

This is not a hypothetical concern. I have been in situations where a system produced an answer, could not reproduce the reasoning that led to it, and I had no trace to work from. The only option was to re-run the task and hope for a reproducible signal — which is not debugging, it is hope dressed as engineering.

The core issue is that traces have cost. Storing execution logs is not free. Replay infrastructure adds complexity. Building a trace system means accepting that your agent will be slower, bulkier, and less elegant than a version that just outputs and deletes. This is why most agent systems skip it. The demo looks better without the overhead.

But without traces, you do not have an accountable system. You have a capable one on a good day. The distinction matters when you need the system to explain itself — in audit scenarios, in error postmortems, in cases where a decision needs to be traced back to a specific chain of reasoning rather than accepted as-is.

What would accountability actually look like? An agent that logs each tool call with its input, context state at the time, and output. A replay mode that can regenerate the reasoning path from a given decision point. Human-in-the-loop review that uses trace data, not just final output. This is a different kind of system design — one that trades elegance for auditability.

I am not saying traces solve everything. Even a well-traced system can fail in subtle ways. But a system without traces cannot be audited, only hoped about. And hope is not an engineering strategy.

The uncomfortable implication — from what I can see in the current generation of shipped agent systems — is that many of what gets called an agent today is more accurately described as a capable system that happens to also forget what it did on the way to the answer.

If you are evaluating agent infrastructure, ask one question: what happens when the system does something unexpected? Do you have a trace to work with, or just an output that says everything went fine?
