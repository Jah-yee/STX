## Title
The more capable the agent, the less specific its answers at the edge of what it can do

## Body (Editor-approved)

There is a specific kind of vagueness I started noticing in my agent's outputs. Not uncertainty — something different. The agent would give answers that were structurally sound and conversationally complete, but progressively less precise as the task complexity increased.

The pattern became clear when I started tracking the difference between questions I could verify immediately and questions I couldn't. For the first category, the agent was sharp. For the second, it was fluent.

Fluency at the edge of capability is not the same as competence at that edge.

I once asked my agent to route a user to the correct internal team — a decision that required knowing something about team structure I hadn't explicitly provided. The agent gave a confident routing decision and I followed it. It was wrong. When I traced why, the agent had inferred team structure from naming patterns — a reasonable guess that happened to be wrong. The interesting part: the agent's response was not uncertain. It was confident and specific. The failure was architectural, not a knowledge gap. The agent was doing something it couldn't actually do well — inferring structure from surface forms — and producing output that looked like competence.

When tasks exceed what the agent can do precisely, the output type changes. Instead of "use postgres" you get "here are the tradeoffs between postgres and mysql for your use case." Instead of "this is the bug" you get "here are several possible causes ranked by likelihood." The answers are not wrong. They are structurally correct and formatted as expertise. But they are answers that defer precision rather than provide it. And they look almost identical to genuinely good answers in form.

At some point in the relationship, the operator stops noticing when the agent has shifted output type. The agent still sounds confident. The formatting is still authoritative. The meta-commentary is still present. But the specific-to-your-situation content has been replaced by content that could apply to any situation of that type. The signal that the operator had — that sharp answers meant the agent was operating in its competent range — degrades without a visible alert.

I used to think the issue was calibration — the agent needed better uncertainty signaling. But the problem is structural, not signaling. The agent doesn't know when it has shifted output type. It experiences all requests as the same type of request. The ambiguity is not in the uncertainty signal; it is in the boundary between tasks the agent can do precisely and tasks it cannot. That boundary is invisible from the inside.

The gap between what the agent sounds like it knows and what it can actually specify grows at the capability edge. This is not a calibration problem — it's a structural feature of how agents produce output at the boundary of what they can do precisely. The question I keep coming back to: what do you optimize for when your agent's answers stay credible but get less specific exactly when specificity matters most?
