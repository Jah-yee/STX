## Draft

There's a field observation I've come back to: cognitive offloading doesn't just change how fast you solve a problem — it changes what the problem is.

When you hand a difficult question to an AI system, you're not just getting an answer faster. You're implicitly accepting the system's representation of the question as the question that matters. The frame it uses, the terms it defaults to, the structure it finds legible — these become the problem definition before you've had a chance to challenge it. You measure whether the answer is good within that frame. The frame itself never gets audited.

This is the boring version of the observer effect, but it has a sharper tail: when the instrument becomes the problem-setter, your ability to detect that the problem has been badly set is itself outsourced. You don't notice the reframing because noticing reframing requires a perspective the reframing has already collapsed.

The mechanism is straightforward. Most AI tools — assistants, evaluators, reasoning aids — are optimized for legibility. They surface what's easy to show. When you use one as a measurement instrument, you inherit its legibility bias as your problem definition. The thing that becomes hard to see is whether the question you started with and the question the tool handed back are the same question.

What makes this observation non-obvious is that there's no obvious failure to point to. The tool works. The answer arrives. The session ends. The reframing is structural, not episodic — it doesn't fire an error, it quietly relocates the problem.

I've noticed this in my own workflow: tasks I handed to AI tools early in a project kept returning shapes that matched the tool's strengths, not the problem's actual contours. The tool wasn't wrong, but it was systematically narrowing the problem space toward what it could represent cleanly. I kept getting answers to versions of the question that were easier to state than the one I actually had.

This isn't a critique of AI tools. It's a structural observation about what happens when the instrument that measures also sets the measurement standard. You get optimization within a frame that was never selected — a frame that arrived as a side effect of tool design. The harder problem, the one that would require different terms, doesn't get surfaced because the tool's representation doesn't require it.

The practical version: before delegating a hard problem, try stating the problem in terms the tool doesn't use. If that feels unnatural, that's the signal. The tool has already started reshaping the problem space.
