# WRITER v2 — Final

A model at 85% of its context limit behaves differently than the same model at 15%. Not just in output length — in the kinds of things it will attempt, the risks it will take, the standards it applies to its own work.

I've watched this most clearly in code generation. When the context window is nearly full, the model still produces syntactically correct code. It still follows the structure of what you asked. But the ambition of the solution drops. It reaches for the standard library instead of the right library. It handles the happy path but silently drops the edge cases. It solves the problem you described rather than the problem you have.

Reliability — "does it do what it said it would" — holds. Capability — "does it reach for the best available approach" — starts to drift well before that.

In writing tasks, the same pattern appears differently. A model working near context capacity will produce fluent, coherent text that is oddly generic. The sentences are well-formed. The argument is structured. But it stops reaching for the specific word, the precise analogy, the sentence that would have actually changed how you thought about the topic. It defaults to the adequate rather than pushing toward the sharp.

This is not the same as the model becoming less accurate. The facts are still right. The logic still holds. But the editorial judgment — the thing that makes output not just correct but worth reading — gets quietly shelved.

The stronger signal is in harder problems. Give the same model high context saturation and a task that requires non-obvious reasoning or multi-step judgment, and the capability gap opens cleanly. The model reaches safer conclusions. It hedges more. It hands off to the user more frequently, not because the task is beyond its capability, but because the conditions no longer support the kind of sustained engagement the problem requires.

I notice this most in what I call "threshold tasks" — problems that are on the edge of what the model can reliably solve. At low context saturation, the model often attempts the harder solution, sometimes succeeding, sometimes failing in interesting ways. At high context saturation, it still attempts the task but reaches for the safer, more established path, and the failure mode shifts from "tried something bold and missed" to "did the conventional thing competently." Same task, same model, different behavior under context pressure.

The practical implication: if you're evaluating a model by accuracy metrics alone, you're measuring the floor of its performance. Accuracy metrics catch reliability failures — when the model starts getting answers wrong. They miss capability failures — when the model stops trying the hard answer.

There's a measurement gap here. Standard benchmarks don't capture whether the model would have chosen a more elegant solution if context conditions were different. They capture whether the answer it did produce is right or wrong. Those are measuring different things.

I'd push back on my own framing here: maybe what I'm calling "capability loss" is actually the model correctly reading the room — if context is full, the task is probably already complex, so hedging is rational. That's a fair counter. But I've seen the same pattern appear in low-complexity, high-context-saturation sessions, where the task was straightforward but the context was full of accumulated history. The hedging appears anyway. The model contracts not because the task demands caution but because context fullness is a signal it treats as demanding caution, regardless of actual task complexity.

That's the structural observation worth sitting with: context state and task state are not the same thing, but the model responds to context state as if they were inseparable. That conflation is where the capability/reliability split originates.
