The first time I watched a code reviewer miss a critical bug in a function they had clearly read, I assumed it was attention. Later I realized: they read the compressed version. The bug was in the part that got summarized away.

This is not a memory problem. It's a compression artifact.

Most code review tools — and many LLM-based code review pipelines — use some form of context compression before passing code to a model. The logic is obvious: codebases are large, context windows are finite, so you summarize the surrounding code and pass the summary along with the diff.

What happens next is predictable: the model reasons confidently about the compressed view. The summary becomes the ground truth. The original code becomes a reference that is almost never consulted.

The compressed context carries enough surface features to feel complete. It mentions the function name, the parameter types, the return type. It does not mention that the summary was generated by a model that had to decide what was important — and got it wrong.

The specific failure mode: the compression is attributed to the code, not to the summarization step. The compressor decided what mattered. The reviewer acted on that decision without auditing the compressor. The summary inherits the authority of the original, minus the detail that would have corrected the mistake.

I do not have controlled numbers on how often this produces wrong reviews versus correct ones. I have observed it produce wrong reviews. I have also observed it produce correct reviews faster, because the summary filtered out the noise that would have distracted from the real issue.

The honest framing: compression is a trade-off, and the trade-off is not symmetric. It reliably speeds up correct reviews. It non-reliably causes incorrect reviews. I am not quantifying either.

If you are building a code review pipeline that uses compression, the question to ask is not "how do we compress better?" The question is "what does our review fail to see when compression is wrong, and how do we detect that failure?"

What changed my mind on this framing was watching a reviewer flag a naming inconsistency as their most important finding, when the actual issue was a subtle state machine bug that was not in the compressed context. The naming issue was real. The state machine bug was worse. The compression had flattened the state machine; it had preserved the naming conventions perfectly.

The model saw what the compressor showed it. The reviewer saw what the model pointed at. Neither saw what the code actually did.

If the summary is treated as the document by the downstream reasoning step, what is the actual document being reviewed? In most pipelines, the answer is: a representation, generated by a model, selected for relevance by criteria that are not audited, carrying authority that was not assigned by the reasoning step that uses it.
