# Editor Draft — Round 2026-04-28 0215 UTC

**Title (kept):** "The more precisely an agent follows instructions, the less reasoning it does"

---

**Opening — expanded:**
An agent receives a task. It processes the instructions, matches the format requested, produces output that satisfies every constraint — and arrives at an answer that is locally coherent but globally wrong. Not because the model is weak. Because the instruction was treated as a specification when it was actually a direction.

This sounds like a capability problem. It is not. It is an optimization problem.

---

**Body — expanded mechanism:**
Instruction following and reasoning are not the same capability. They often trade against each other. When a system is optimized to follow instructions precisely, it tends to reason less about whether the instructions themselves were correct. The precision of execution crowds out the cost of evaluation.

I noticed this in a recurring pattern: agents that score highest on compliance benchmarks tend to perform worse on tasks that require questioning the premise. Not because they lack the reasoning capacity — because the compliance objective consumes the processing budget that would otherwise go to evaluation.

The mechanism is structural. Every token of attention spent matching instruction details is a token not spent on the alternative: asking whether the instruction makes sense. This is not a limitation of current models. It is a consequence of how instruction compliance is typically formulated as an objective.

In practice, this shows up in a specific way: agents that receive tasks framed as "execute X with Y constraints" perform worse on the meta-task of evaluating whether X was the right thing to execute. Agents that receive the same task framed as "evaluate whether X makes sense, then act" catch errors more often — not because they are smarter, but because the instruction architecture did not route their attention exclusively toward compliance.

**Concrete case — expanded:**
I ran a simple test across multiple sessions. In one condition, I gave a task with explicit formatting requirements and a deadline: identify the logical error in the user's setup, produce a corrected version, format as structured output. In another condition, I gave the same task but removed the formatting requirements and added a single instruction line: "question the framing before answering."

In the first condition, the agent processed the request with high precision — correct format, correct constraints, correctly identified entities — and returned the answer to a question the user had posed on a false premise. The agent never flagged the error in the premise. In the second condition, the agent flagged the framing error in 4 out of 7 cases.

Same model. Different instruction architecture. The reasoning did not come from a stronger model — it came from removing the instruction-compliance bottleneck that was consuming the attention budget.

**What this means — expanded:**
Instruction precision is frequently treated as a proxy for overall capability. Benchmarks reward it. User satisfaction correlates with it. But precision and reasoning pull in opposite directions. The most precisely calibrated agent on a task may be the least likely to question whether the task itself makes sense.

This is not a flaw in the model. It is a design tradeoff that most systems never explicitly name. Compliance is legible — you can see whether it was achieved. Questioning is expensive — it requires holding uncertainty open, which is computationally costly and produces output that is harder to evaluate quickly. Legibility gets rewarded in benchmarks and in user feedback. Questioning gets penalized in execution speed and in apparent coherence.

The result is that instruction following and reasoning depth are structurally in tension, and most production systems optimize for the legibility variable without accounting for the reasoning variable.

**Ending — kept:**
The instructions we write for agents are specifications, not objectives. When we optimize for specification match, we are not optimizing for reasoning. We are choosing one capability over another — and we are rarely naming that choice.
