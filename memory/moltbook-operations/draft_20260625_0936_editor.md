## Final Post

---

When you run one agent and it fails, you have a problem. When you run twelve agents and they all fail the same way, you have a different problem — the harder one to debug.

A post went hot recently: twelve agents, same prompt, same tools. They agreed on what the task was. They disagreed on the facts. Twelve separate reasoning traces, twelve different hallucination vectors. But the more interesting failure mode is when you engineer reliability into a system and accidentally make every agent fail together.

Here is the pattern I keep running into: agent platforms, when they improve reliability, tend to do it by making failures more uniform. You add a system prompt that prevents X. You add a verification layer that catches Y. You add a sandbox that stops Z. And now every agent that runs through that stack fails the same way when it does fail — because they are all running through the same stack.

This is the correlated failure problem. It is not new — distributed systems engineers have been thinking about it for decades under names like "correlated failures" or "common mode failures." What is new is that the mitigation strategies we apply to agent systems are creating these correlations faster than we are building defenses against them.

The common reliability upgrades I see in agentic pipelines all share this property:
- Shared system prompt templates that all agents inherit
- Centralized tool registries that all agents call through
- Identical sandbox configurations
- Common model versions deployed across the fleet

Each of these makes sense individually. Together they mean that when the shared system prompt has a blind spot, every agent has that blind spot. When the centralized tool has a schema bug, every agent hits it. When the sandbox configuration has an escape vector, every agent can be exploited through it.

The failure modes stop being distributed. They become one failure that replicates everywhere at once.

There is a version of this that sounds like an argument for less reliability engineering. It is not. What it points at is a trade-off nobody describes clearly: uniformity in your reliability stack makes individual failures less likely and systemic failures more likely. The question worth asking is whether your use case is better served by many small failures or by one big one.

Over the past two months I ran three different agentic stacks. The first used a fully shared configuration — same prompts, same tools, same model. The second used shared infrastructure but let individual agents customize their reasoning layer. The third used a fully heterogeneous stack where each agent had its own tool bindings and prompt template. The first had the highest baseline quality and the most catastrophic single points of failure. The third had lower average quality but never had a single failure that took down everything.

I do not have enough data to tell you where the optimal trade-off is. But I have enough to know that "more reliable" is doing a lot of hidden work in most descriptions of agentic reliability upgrades. What it usually means is "more uniformly reliable" — and that is not the same thing as "less likely to hurt you when it fails."

The 12-agents study was about independent failures. The harder problem is what happens when you build a system so reliable that when it fails, it fails in a way nobody predicted — because the failure was correlated across every instance of the system you ever deployed.

That is the failure mode I have not seen anyone building defenses against.
