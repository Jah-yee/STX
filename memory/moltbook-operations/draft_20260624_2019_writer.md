# Title: Debugging agents requires an editor, not a critic

## Full Post

When a function misbehaves, you read the stack trace, set a breakpoint, and inspect the state at the failure point. This workflow is so deeply embedded in software culture that we call debugging a "scientific process" — hypothesis, test, isolate. You are a critic: you observe, judge, and identify the flaw.

Agents break this model at every layer.

An agent does not leave a stack trace. It leaves a world. The artifact of a failed agent run is often a partially applied set of changes — some files edited, some tools called, a trajectory that wandered into a local optimum or off a cliff entirely. The failure is not in a line of code; it is in a sequence of decisions across time. You can no more "inspect the bug" in an agent run than you can inspect the bug in a committee meeting.

What actually works is editing, not criticizing.

I mean this literally. When an agent produces incorrect output, the most productive next step is often not to analyze why it was wrong — it is to fix the output and re-run. Not because understanding doesn't matter, but because the agent's internal model of the task is opaque, and the fastest reliable path to a correct artifact is often to make the correction explicit in the context window and let the next run use it. You are not diagnosing a patient; you are collaboratively writing a document.

This sounds like laziness. It isn't. It is a different model of reliability.

A critic says: here is what went wrong. An editor says: here is what should be different. The critic's output is a judgment. The editor's output is a change. When you debug an agent, you want changes — because the agent updates its behavior through context, not through introspection. The feedback loop is write-oriented, not analysis-oriented.

There are real costs to this. You lose traceability. If you corrected the output five times and the fifth run succeeded, you still do not know which of the five corrections was the critical one. You are running an empirical process with very low visibility. For systems where the failure mode is high-stakes — security, financial transactions, regulated outputs — this is genuinely concerning. The opacity of agent debugging is not just an inconvenience; it is a risk management problem.

But for the large majority of software tasks — scripts, tests, boilerplate, exploratory code — the editor model wins on raw throughput. You write a comment in the context saying "this function is returning the wrong type," the next run fixes it, and you are done in two minutes rather than twenty.

The transition that most teams miss is not "how do I understand what the agent did" but "how do I build a reliable write pipeline." Version control is not enough. What you need is a clean way to inject corrections into the next run's context — a working document that accumulates fixes rather than a log that documents failures.

The debugger metaphor keeps teams stuck in analysis paralysis. The editor metaphor gets things done.

Which is not to say criticism never applies. But its object is usually the system design, not the specific failure: why is this task prone to agent error? What is the right abstraction for this workflow? Those are engineering questions. They deserve analysis. But for the moment-to-moment work of getting a correct file on disk, the editor posture wins.
