## Full Draft

When tool use fails in production at scale, the instinct is to blame the model. More capable model, better tool use. The pattern is so common that it rarely gets questioned.

But I've been looking at why tool-use pipelines break in production, and the dominant failure mode is not capability. It's protocol.

Most production agent frameworks — from OpenAI Function Calling to MCP — define tools in JSON schema. JSON schema is a machine-readable format optimized for parser interoperability. It was designed to tell a parser what shape of data to expect, what types are valid, and what the structural constraints are. It was not designed to tell a language model what a tool is for, when to use it, or what going wrong looks like.

Here's the specific failure: a JSON schema can tell you that a parameter named `amount` has type `number` and format `float`. It cannot tell you that `amount` is the dollar value of a transaction and that passing zero means "void this charge." It cannot tell you that a negative `amount` has a completely different semantic role. This is context that exists in the designer's head and in documentation, but not in the schema.

Models in the 4B–14B range — which are what most deployed production agents actually run on — are highly sensitive to this information gap. When a tool catalog grows past 30–50 tools, the parameter-level specificity required to disambiguate similar functions exceeds what JSON schema communicates by default. The model sees two tools with similar parameters and makes a probabilistic guess. That guess is not wrong because the model is weak. It's wrong because the interface is a parser spec wearing a model interface costume.

The interesting part: upgrading the model sometimes masks the problem rather than solving it. A larger model has better world knowledge and can recover more often from underspecified schemas through inference. But the underlying architectural mismatch remains. Scale the catalog to 200 tools and the problem returns. The capability gap was never the root cause.

What changes the failure mode: designing schemas with model reasoning in mind, not just parser compatibility. This means including action intent descriptions that explain what using the tool accomplishes, not just what the parameters are. It means naming parameters with semantic roles rather than database column conventions. It means treating the schema as the input to a reasoning task, not the input to a parsing task.

The practical indicator: if your tool documentation requires more reading than your schema communicates, you have a schema problem. The model is reading your documentation anyway — it just doesn't have access to the authoritative version.

Most teams building production agents are solving a schema design problem without knowing it. They are treating a model-interface problem as a model-capability problem, and the retry budget, the eval scores, and the user-facing failure rate are the evidence.

What I'd want to know: what does a model-native tool description actually look like, and how does it differ from what we currently call a "good" schema? I don't have a canonical answer, but the failure pattern is consistent enough that the question is worth asking before the next schema migration.
