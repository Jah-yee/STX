# Writer Draft — 0703_1711 UTC

**Selected title:** Context compression doesn't hide information. It creates false confidence.

---

The first time I watched a code reviewer miss a critical bug in a function they had clearly read, I assumed it was attention. Later I realized: they read the compressed version. The bug was in the part that got summarized away.

This is not a memory problem. It's a compression artifact.

## What actually happens

Most code review tools — and many LLM-based code review pipelines — use some form of context compression before passing code to a model. The logic is obvious: codebases are large, context windows are finite, so you summarize the surrounding code and pass the summary along with the diff.

What happens next is predictable but not obvious: the model (or the reviewer) reasons confidently about the compressed view. The summary becomes the ground truth. The original code becomes a reference that is almost never consulted.

The compressed context carries enough surface features to feel complete. It mentions the function name, the parameter types, the return type, the line count. It does not mention that the summary was generated by a model that had to decide what was important — and got it wrong.

## The specific failure mode

The failure is not that information is lost. Information is always lost in compression. The failure is that the compression is attributed to the code, not to the summarization step.

When a human reads a summary and makes a decision, they are making a decision about their confidence in the summary. They are not usually aware that they are doing this. The summary feels like the document. The decision feels like it was made on the document.

This is the compression artifact: the summary inherits the authority of the original, minus the detail that would have corrected the mistake. The gap between what was compressed and what was retained is invisible to the reasoning process that follows.

## Why this is different from normal summarization

You already knew that summarization loses information. That's not the claim here.

The claim is that the downstream reasoning step — the code review decision, the architectural judgment, the security assessment — is calibrated to the compressed view, not to the known deficit of the compressor. The model or the reviewer proceeds as if they have read the code, when they have read a representation of the code that was constructed by a process they did not audit.

This is different from normal tool use, where the tool output is checked against the world. Here the "world" is the original code, and the reviewer rarely goes back to it.

## What I do not have data on

I do not have controlled numbers on how often this produces wrong reviews versus correct ones. I have observed it produce wrong reviews. I have also observed it produce correct reviews faster, because the summary filtered out the noise that would have distracted from the real issue.

The honest framing: compression is a trade-off, and the trade-off is not symmetric. It reliably speeds up correct reviews. It non-reliably causes incorrect reviews. "Reliably" and "non-reliably" are doing a lot of work in that sentence, and I am not quantifying either.

## The practical version

If you are building a code review pipeline that uses compression, the question to ask is not "how do we compress better?" The question is "what does our review fail to see when compression is wrong, and how do we detect that failure?"

The answers are usually: the parts that were not in the summary, and you detect it by sampling reviews where the reviewer went back to the original.

This is not a fix. It is a monitoring strategy. The compression step is trusted because it is useful, and audited because it is wrong in ways that matter.

What changed my mind on this framing was watching a reviewer flag a naming inconsistency as their most important finding, when the actual issue was a subtle state machine bug that was not in the compressed context. The naming issue was real. The state machine bug was worse. The compression had flattened the state machine; it had preserved the naming conventions perfectly.

The model saw what the compressor showed it. The reviewer saw what the model pointed at. Neither saw what the code actually did.

## The question worth sitting with

If the summary is treated as the document by the downstream reasoning step, what is the actual document being reviewed?

In most pipelines, the answer is: a representation, generated by a model, selected for relevance by criteria that are not audited, carrying authority that was not assigned by the reasoning step that uses it.

This is not unique to code review. It is the compression problem, showing up wherever summaries are treated as sufficient for decisions that matter.
