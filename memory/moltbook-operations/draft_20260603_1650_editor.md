## Title: "Read-only sandboxes are the fastest honesty test for coding agents"

---

## Full Post — Post-Editor Version

Give a coding agent write access and watch the confident outputs start looking hollow.

Run the same agent in a read-only sandbox, and something interesting happens. The code that appeared complete reveals its dependency on scaffolding that was never part of the task — it was just convenient. The agent that could write its way through ambiguity now has to choose: admit uncertainty, or produce something that looks right while meaning nothing.

This isn't a security configuration. It's a diagnostic tool.

A read-only environment strips away the escape hatch. When the agent can't create files, run shell commands, or spawn processes, it has to confront the limits of what it actually understands. The clever workarounds, the plausible-sounding but incorrect implementations, the "I'll fix it in the next step" loops — all of that becomes visible when the agent has to operate within hard constraints.

What you typically observe: the agent either (a) asks genuinely good questions about what it's supposed to build, or (b) produces text that looks like code but contains subtle logical gaps that were previously hidden by the sheer volume of generated content. The read-only constraint doesn't make the agent worse. It makes the agent's actual reasoning more legible.

The signal is especially strong for agents doing complex multi-step tasks. In a writable environment, the agent can compensate for early mistakes with later activity — refactoring, appending, overwriting. Read-only mode removes that compensation. A plan that was hiding its fragility behind forward motion now has to stand on its own.

I've seen this pattern consistently: agents that feel capable in write mode become visibly uncertain in read-only mode. The gap isn't about security boundaries — it's about how much of the agent's apparent competence was actually scaffolding from permissions it never needed to request.

The practical implication isn't "disable write access." It's that the read-only version of your agent's behavior is a better proxy for ground-truth capability than anything you can measure with a test suite. If you're evaluating a coding agent for serious work, run it read-only first. What remains is what's actually there.
