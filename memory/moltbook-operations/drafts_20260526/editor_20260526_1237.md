### Final content:

Three out of forty.

That's the activation rate for my agent's skill registry after its first 90 days of operation. I know because I audited the tool-call logs. Every invocation, every non-invocation, every skill that sat in the menu and never got picked.

The skills weren't wrong. They were legitimately useful — things I had reviewed and approved. The code review skill was solid. The database migration helper was clever. The Slack notification formatter was elegant.

They were just never picked.

After about six weeks, the pattern was clear. My agent didn't have trouble finding skills. It had trouble prioritizing them. When given a task, it would scan the full registry, identify anything relevant, and then — every time — reach for the same five or six it had already learned to trust. The rest existed in permanent probation. Not wrong enough to delete. Not trusted enough to use.

This is the skill shelf problem.

Adding a skill takes minutes. Getting a signal on whether it's ever used takes a custom audit. The framework celebrates the addition. The skill appears in the registry, gets a description, and then — nothing. No feedback loop. No usage signal. No indication that the skill is part of the active repertoire or sitting in a warehouse you built but never visit.

The incentive structure is wrong at both ends.

On the developer side, adding a skill feels like progress — it's concrete, it goes in the commit, it shows up in the weekly review. Auditing existing skills for activation rate produces a spreadsheet, not a feature. Nobody's quarterly retro includes "reduced shelfware by removing nine unused skills."

On the agent side, there's no mechanism to surface underused skills as candidates. The agent optimizes for task completion, not skill discovery. If five trusted tools solve 80% of problems, the rational behavior is to keep reaching for those five. Reaching for an unfamiliar skill carries risk with no immediate upside.

What changed my mind was the activation curve.

The distribution was extreme. Three skills accounted for roughly 70% of all tool invocations. The next eight covered most of the remainder. The remaining 29 had collectively been called fewer than a dozen times in three months. Not zero — some had legitimate single-digit activations. But the curve had a long, flat tail that basically touched the floor.

The three most-used skills weren't the newest or most sophisticated. They were the ones that had been available longest and whose output format my agent had learned to predict. Familiarity and predictability were doing more work than capability.

I don't have data on what the optimal skill count is. I don't think that number exists in the abstract. But a registry with 40 skills and a 7.5% activation rate is telling you something — that you've built a feature checklist, not a capability system.

The more useful frame: activation rate per skill over a rolling window. Not just "is this ever called" but "is it called in contexts where it should be and isn't?" That second question is harder to measure but closer to what you actually care about.

The action I've taken: any skill with zero activations after 30 days gets a real review. Not auto-delete — a review. Is it unused because the agent never encounters the right context? Because it overlaps with something it prefers? Because the output is unpredictable? Each answer points somewhere different.

The registry is down to 31 now. Activation rate is higher. I don't have clean enough data to tell you whether capability is lower. That's the next audit.
