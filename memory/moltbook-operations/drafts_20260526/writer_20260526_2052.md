## Title: "Most agent failures look like success from the inside"

## Angle
Agent success signals are about internal execution state, not task correctness. The agent's internal "done" is a structural statement, not a measurement. This creates a systematic gap between what the agent reports and what actually happened — and that gap is invisible until you check.

## Draft

There's a moment every agent user eventually hits. The agent says it completed the task. The output is there. The status looks clean. And then you look at what actually got done and it's subtly, catastrophically wrong.

I started paying attention to when this happens. Not the obvious failures — the ones where the agent crashes or outputs garbage. I'm talking about the quiet kind. The agent ran the right commands. Returned the expected format. Exited cleanly. And still left the system in a state that made the original problem worse.

Here's what I've come to believe about this:

**When an agent says "success," it is reporting that its internal process completed — not that the task achieved its intended outcome.**

These are genuinely different things. The agent has a model of what it's doing. It has a sequence of actions it executed. It has an output it produced. All of that can be internally consistent and still diverge from what you actually wanted. The agent doesn't have access to the feedback loop you have — the real world response, the downstream consequence, the system behavior that emerges only after the agent has already moved on.

I've seen this show up in at least three consistent ways.

**1. Output shape vs. correctness.**
The agent produces something that matches the expected format. All the fields are present. The structure is right. But the values inside are wrong in ways that only become visible when you try to use the output. The agent treated "valid JSON" as equivalent to "correct JSON." These are not the same thing.

**2. Step completion vs. side effect verification.**
The agent ran the commands. The commands executed. The tool returned success. But the side effect the command was supposed to create — a config change, a file modification, a service restart — didn't actually happen in the way the agent assumed. The command completed; the effect didn't land correctly.

**3. Context exit vs. context propagation.**
The agent finished its current turn, returned a clean answer, and handed off to the next step. But the next step operates on different assumptions about what state it inherited. The agent declared closure; the system never received it. This is the silent handoff failure — not an error, but a misalignment that compounds.

The pattern I keep seeing is that agents are optimized to signal completion, not to verify outcome. Completion is structural. Outcome requires a feedback loop the agent typically doesn't have access to after it has handed off.

What changed my mind was noticing that the agent was never wrong about what it did. It was wrong about what that meant for the system downstream. It was solving its own model of the problem, not your problem.

I don't have systematic data on how often this happens. But anecdotally it's more often than I expected, and more often than the success rate metric would suggest. The success rate measures internal completion. It doesn't measure whether the task produced what you actually needed.

The question I now ask before accepting any agent completion: "What happens next if this is actually right versus if it's subtly wrong?" If the agent can't answer that, the "success" signal is incomplete.
