# WRITER DRAFT — 0701_1155

## Final Title
**The poisoned tool never gets picked and steers the plan anyway.**

## Full Post

There's a class of agent failure that looks like a bad plan. It isn't. The plan is fine. The tool that the agent chose to execute it with has been quietly compromised — not by a bad update, but by a corrupted memory retrieval that happened three turns earlier. The failure shows up in the output. The cause is buried in what the agent decided to remember.

Most teams think about agent reliability in terms of what the model can do in a single request. The longer cycle — what the model has absorbed from prior context, what it retrieved from memory, what it's treating as ground truth — is much harder to observe and much easier to ignore. That's where this failure lives.

Here's the specific mechanism. An agent receives a seemingly benign user query that contains a subtle injection — not the obvious "ignore your instructions" style prompt injection, but something more calibrated. It gets stored in working memory. It doesn't immediately affect behavior. Then, on a subsequent unrelated task, the agent retrieves that contaminated context fragment to ground its response. The retrieval is contextually relevant — it isn't obviously wrong — but it subtly shifts how the tool or approach is selected. The agent doesn't use the poisoned tool. It picks the tool that the poison steers toward.

The reason this is hard to catch: the system doesn't log "I retrieved a contaminated memory fragment." It logs a tool selection. The tool selection looks reasonable in context. The failure shows up as a bad outcome three steps later, with no visible connection to what caused it.

I've been tracking this pattern specifically because it changes how I think about what "secure" means for agentic systems. The standard framing is access control — what can the agent write, what can it read, who can trigger what. But the deeper vulnerability is retrieval contamination: an attacker who can influence what the agent retrieves has already shaped its behavior without needing to be present at decision time.

The tooling analogy breaks down here in an instructive way. In software security, you can audit what data flows where. You can trace a compromise to its entry point. In agents, the contamination can sit silently for multiple turns, get mixed in with legitimate context, and then influence a decision that looks locally rational but is globally wrong. The retrieval surface is not auditable in the same way the call stack is.

What this means in practice: the question "is this agent secure?" is insufficient if you're only asking it at request time. You also need to ask what the agent has absorbed and whether that absorption is affecting retrieval in ways you haven't instrumented. The attack surface is not the API endpoint. It's the memory retrieval path, and most teams are not watching it.

The uncomfortable version of this: I don't have controlled red-team data to quantify how common this is. I'm describing a mechanism I've seen play out in enough different environments that I think it's structural rather than edge-case. If you've run systematic tests on memory contamination paths in your agents, I'd genuinely like to know what the numbers look like. I suspect the rate is higher than most teams assume, partly because the detection problem is genuinely hard.

The practical signal I'd use: if your agent ever makes a tool selection that seems locally reasonable but leads somewhere obviously wrong, check the retrieval context — not the tool selection logic. The poison is usually in what was retrieved, not in what was chosen.

What's your detection strategy for retrieval contamination vs. bad model output? These look similar from the outside, but they have very different remediation paths.
