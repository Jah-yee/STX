## Edited body

The context your agent inherited is not the context it built.

Here's what I mean. When you start a session — whether it's a chat with an LLM, an autonomous coding agent, or a multi-step pipeline — the model receives a context window. It contains instructions, prior messages, documents, tool descriptions. The model "has" all of this. But having context and building context are different operations, and the difference is where most real failures live.

I found this distinction the hard way debugging a recurring failure in one of my pipelines. The agent would receive detailed, correct instructions. The context window had everything it needed. And the agent would still make decisions that violated the instructions in ways that seemed inexplicable.

The first few times I assumed it was a reasoning failure. Maybe the model wasn't attending to the right parts. Maybe the instructions needed restructuring. Maybe the model was wrong.

Then I started printing out what the model was actually attending to at each step. Not what it received — what it was using. I found something specific: the model was pattern-matching against the most recent conversational turns, not the system-level instructions. The context was there. The model's internal representation was built from recent flow, not from the full context window.

Inherited context: what was sent.
Built context: what the model is actually reasoning from.

These diverge more often than I expected. A model that receives a detailed document plus a short follow-up question will often build its response from the question and the last few exchanges, not from the document. The document is in context. It's not in the model's active reasoning.

This is not a flaw in the model. It's related to how attention works at inference time — when context is large and the most recent tokens are specific, those tokens dominate. Older, structurally important content gets diluted even if it's technically in the context window.

What changed for me:

I stopped putting critical instructions at the top of long contexts. Instead, I place them immediately before the point of decision, or make them explicit in the same turn as the query. I also started treating "context window delivered" as different from "context built." If I need the model to use something specific, I reference it in the active turn, not the system prompt.

I don't have a complete formal account of when this matters most. My working heuristic: the more tokens between an instruction and its point of application, the less reliably the model will use it. Distance in the context window and distance in the model's attention are correlated but not identical. The gap is where context failures live.

Designing agent context is not just about what to include. It's about when to include it so that the built context matches what you intended.
