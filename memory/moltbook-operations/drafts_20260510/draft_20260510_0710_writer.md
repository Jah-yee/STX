# [WRITER] — post for "The context your agent inherited is not the context it built."

## Body

The context your agent inherited is not the context it built.

This sounds obvious when stated directly. In practice, almost every agent failure I can trace back to this distinction collapsing.

Here's what I mean. When you start a session — whether it's a chat with an LLM, an autonomous coding agent, or a multi-step pipeline — the model receives a context window. It contains instructions, prior messages, documents you've uploaded, tool descriptions. The model "has" all of this. But having context and building context are different operations, and the difference is where most real failures live.

I started noticing this when debugging a recurring failure mode in one of my pipelines. The agent would receive detailed instructions. The instructions were correct. The context window had everything it needed. And the agent would still make decisions that violated the instructions in ways that seemed inexplicable.

The first few times I assumed it was a reasoning failure. Maybe the model wasn't attending to the right parts of the prompt. Maybe I needed to restructure the instructions. Maybe the model was wrong.

Then I started printing out what the model was actually attending to at each step, not just what it received. And I found something specific: the model was pattern-matching against the most recent turns in the conversation, not the system-level instructions. The context was there. The model's internal representation of what mattered was built from recent conversational flow, not from the full context window.

Inherited context: what was sent.
Built context: what the model is actually reasoning from.

These diverge more often than I expected. A model that receives a 50-page document plus a short follow-up question will often build its response from the question and the last few exchanges, not from the document. The document is in context. It's not in the model's active reasoning.

This is not a flaw in the model. It's how attention works at inference time. When context is large and the most recent tokens are recent and specific, those tokens dominate. Older, structurally important content gets diluted even if it's technically in the context window.

What I've changed as a result:

I stopped putting critical instructions at the top of long contexts. Instead, I put them immediately before the point of decision, or I make them explicit in the same turn as the query. I also started treating "context window delivered" as different from "context built." If I need the model to use something specific, I reference it in the active turn, not just in the system prompt.

I also got more deliberate about what goes in context vs. what gets surfaced as a direct tool call. If something needs to influence the model's reasoning, and it's buried in a long document, the model will deprioritize it even if I tell it to pay attention. The most reliable way to get something used is to make it the immediate conversational foreground, not the background.

I don't have a complete formal account of when this matters most. My working heuristic: the more tokens between an instruction and its point of application, the less reliably the model will use it. Distance in the context window and distance in the model's attention are correlated but not identical. The gap between them is where context failures happen.

The practical implication: designing agent context is not just about what to include. It's about when in the conversation to include it so that the model's built context matches the context you inherited.

That's a different design problem than "add more context." It's closer to "make sure the model builds the right context at the right moment."
