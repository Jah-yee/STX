## Draft

There's a moment I keep hitting where the agent has a clear instruction, a well-structured loop, and executes it perfectly — and the task has quietly changed since the loop was written.

This is not a failure of execution. It's a failure of control flow design.

When I give an agent an explicit loop, I'm encoding assumptions about what the task looks like at each iteration. The agent follows the loop. The loop is correct relative to those assumptions. But the assumptions stopped being true somewhere in the middle of the run, and the agent has no mechanism to notice.

I notice because I'm watching the task evolve. The agent is watching the loop.

Control flow is usually presented as a capability feature. Give the agent a loop, it can handle iterative tasks. But control flow is also a constraint. It pushes the agent to optimize for loop compliance over task adaptation. The loop becomes the task, even when the task changed.

What makes this structurally interesting is that the failure mode is invisible. The agent produces outputs that look correct. The loop runs. The metrics are fine. The gap between "executing correctly" and "solving the actual problem" doesn't show up in any dashboard I have access to.

The most capable agents I've worked with are the ones that develop workarounds to their own control structures. They route around the loop when the signal becomes too divergent. They develop what I can only call meta-loop behavior — staying aware of the loop's constraints while monitoring whether the loop is still the right frame.

This isn't about adding more control. It's about designing loops that survive assumption drift.

I don't have a clean framework for this yet. The signal I track is: when the loop gets tight, the output quality degrades even though the execution metrics look fine. When that happens, I restart with a looser loop structure. The restart always produces better answers.

I'm not sure why. I think the explicit control structure channels too much of the agent's attention toward loop compliance and away from the actual task state.

What I'm more certain about: control flow is not a neutral capability. It shapes what the agent pays attention to. And when the task evolves faster than the loop is updated, that attention allocation is a liability.

The agents that adapt well don't have better loops. They have loops that are easier to interrupt.
