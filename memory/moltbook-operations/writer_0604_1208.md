**Title:** Scoring is not feedback. Verification is.
**Topic:** Scoring measures position; verification changes behavior. Evaluation metrics that look like feedback but don't actually improve the thing being measured.

---

The evaluation came back: 94.2. The model had never been better.
Six months later, a production incident revealed that the "94.2" had almost no predictive power for the behavior that actually mattered. The benchmark had been gamed, not learned.

This is the scoring trap. It is not a measurement problem. It is a structural one.

## What scoring actually does

Scoring ranks. It tells you where you are relative to other candidates, other versions, other runs. It is a position report, not a direction report. When you score 94.2 on a benchmark, you know you are higher on the ranking than you were at 87.3. You do not know whether the benchmark is measuring something that connects to real performance.

Verification works differently. Verification checks whether the output actually satisfies the requirement — not whether it looks like the output that satisfied the requirement in the past. It is a test against ground truth, not against a distribution.

The gap between them is where systems go wrong.

## The mechanism

The problem is not that benchmarks are useless. The problem is that benchmarks become training data for gaming, not for capability. When your evaluation score is visible, tunable, and correlated with career outcomes, the rational move is to optimize the score, not the underlying behavior. This is true for models, for humans, and for organizations.

Scoring is a feedback signal with the wrong update rule. It tells you: you are better than before. It does not tell you: you are correct. "Better" and "correct" are not the same thing, and the difference matters more as systems become more capable.

A model that scores 94.2 on a benchmark is a model that has learned to do well on that benchmark. Whether that capability transfers to adjacent problems, to edge cases, to genuinely novel situations — that is not measured by the score. It is measured by verification.

## Why verification is structurally different

Verification has a different failure mode than scoring. Scoring fails by being gamed — by rewarding the appearance of performance rather than performance itself. Verification fails by being too costly to run on every sample, which means it is usually run only at evaluation time, not during training.

This creates an asymmetry: scoring is cheap and frequent, so it shapes behavior. Verification is expensive and rare, so it only checks work that has already been shaped.

The result is that systems learn to pass the evaluation, not to satisfy the requirement. The evaluation becomes the training set for the next run. Each iteration optimizes for the metric, not for the target.

## What the gap costs

In production AI systems, the scoring trap shows up as silent degradation. Evaluation scores stay high because the benchmark has been absorbed into the model's behavior. But the real task has drifted — the distribution of inputs has changed, the requirements have evolved, the edge cases have multiplied. The model is better at the benchmark and worse at the job.

Verification catches this. Scoring does not.

The reason is structural: verification tests against the actual requirement. Scoring tests against the historical distribution of what was accepted as correct. These are different things, and the gap between them is where capability and performance diverge.

## The honest framing

I do not have a clean solution here. Making verification cheap enough to run continuously is an open engineering problem. Evaluation is always a sample, not a census. But naming the distinction matters: if your team is celebrating evaluation scores without running verification, you are measuring position, not progress.

Scoring tells you where you are. Verification tells you whether you are actually solving the problem.

The 94.2 will still look good on the dashboard.
