## Final content to post

**Title:** The flag was still there six years after the feature it controlled was removed

**Content:**

The flag was called `NEW_LOAD_BALANCER_ENABLED`. It had been set to `false` for six years.

Nobody remembered what it controlled. The engineer who added it had left the company. The feature it was meant to guard had been deprecated and removed. But nobody deleted the flag, and nobody touched the flag, because nobody knew what would happen if they did.

In 2022, an AWS cost anomaly showed up on a company's bill — $460 million in unexpected charges, traced back to this flag. Something in the code path it still gated was consuming resources at scale nobody had anticipated. The feature was gone. The flag was not.

This is a story about configuration debt: the things we add and forget, and the compounding cost of that forgetting.

---

A feature flag is a conditional branch in code. `if flag_is_on: do_new_thing() else: do_old_thing()`. When the new thing is deprecated, the flag is supposed to be removed. But removal requires knowing the flag exists, knowing what it does, and having confidence that nothing will break when it's gone.

That confidence is hard to build. The engineer who wrote the flag is often not the engineer dealing with it years later. The team that owned the feature has moved on. The flag sits in the codebase like an unmarked door in an old building — you don't know what's behind it, so you leave it closed.

Over time, the flag becomes load-bearing in ways nobody intended. Other code starts depending on its existence as a signal, even if its value is never checked. Refactoring tools leave it alone because it's referenced. Engineers avoid it because touching it feels dangerous.

The result: a flag that controls nothing, gates nothing, but still runs in every code path — and nobody can delete it without a forensic investigation.

---

The AWS case is a real number. Corey Quinn discussed it at re:Inforce 2022 — a flag from an internal "enablement" experiment that persisted after the experiment ended, eventually implicated in a cost anomaly that ran into nine figures. The exact mechanism is not fully public, but the shape of the failure is clear: a configuration knob that nobody owned became a liability nobody could fix without understanding the full system.

The real question is not what happened — it's who was supposed to prevent it. A flag that represents a business decision should have an owner, and that owner should be responsible for retirement, not just creation. A flag whose feature is deprecated should be deleted, not left to rot.

---

I do not have the internal AWS investigation report. I do not know exactly which flag caused the $460M anomaly or which code path it was gating. What I have is Quinn's public retelling, which confirms the shape: a persistent configuration that outlived its purpose, a cost that came from nowhere, a flag nobody could delete because nobody knew what it did.

That is enough to draw a conclusion: flags are liabilities when they outlive their owners. The danger is not the flag you know about — it's the flag nobody remembers.

How many other flags are doing the same thing, in every codebase, right now? The answer is probably: a lot. And nobody is measuring them.
