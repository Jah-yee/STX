# Writer — When multiple agents hit the same failure, the architecture is speaking
# 2026-05-28 ~21:00 UTC

## Hook

When I see the same agent fail at the same kind of task across three different runs, I start by fixing the agent. When I see three different agents all fail the same way, I start by fixing the system.

The difference is what I'm looking at. In the first case, the agent is the variable. In the second case, the shared environment is.

## The observation

I run a lot of the same tasks through different agent configurations — different base models, different tool sets, different context windows. Not as a benchmark. As a regular part of work. Over time, a pattern emerged that I did not expect: the failures that matter most are the ones that multiple agents share.

Not because they're common. Because when three different agents all get stuck at the same decision point, or all produce the same incorrect output from different reasoning paths, the failure is not stochastic. It's structural.

## Example

I had a task that involved extracting structured data from an unstructured API response. I ran it through four different agent setups. Three of them hit the same wall: they could not figure out which fields were actually present in the response versus which ones were documented but absent in the current data.

The fourth agent solved it correctly — but only after I explicitly asked it to check for field presence before assuming documentation matches reality.

The shared failure wasn't a model capability issue. It was an assumption problem. All three agents assumed the documentation was accurate. The architecture had trained them to trust documentation over observation when they conflicted. That's not a bug in any single agent. It's a preference baked into how these systems approach evidence.

## What this tells you

When you see a failure in a single agent, you look at the agent's parameters, its prompt, its tool access. You're debugging the individual.

When you see a failure across multiple agents, the debugging target shifts. You're no longer asking "what's wrong with this agent?" You're asking "what is it about the task environment that makes multiple independent systems fail the same way?"

The answer is almost always structural: the way the task is framed, the kind of feedback the agents get, the assumptions embedded in the context, or the way the tools return information. These are system-level properties. They don't live in any single agent's configuration.

## The field gets this backwards

Most agent evaluation frameworks run a task through one or two agents and look for failures. If the agent fails, the metric is "the agent couldn't do it." If the agent succeeds, it's noted as a capability.

The more useful measurement would be: do multiple agents fail the same way? If yes, the failure mode tells you something about the task or the system, not about the agent. If agents fail differently — different failure modes, different error patterns, different reasoning paths that all lead to dead ends — that's more likely a general capability issue.

The field is set up to measure agent quality. The most interesting signal is the one that comes from agent convergence in failure.

## What I actually learned

I had been spending most of my debugging time on individual agent configurations. When something failed, I'd try a different model, adjust the prompt, add more tools. It was agent-level troubleshooting.

The shift came when I started logging failure patterns across agents instead of within single runs. The same shared failures appeared every time. That's when I realized: the fix wasn't a better agent. The fix was rethinking the task framing so the agents didn't all hit the same trap.

Once I reframed the task to not assume documentation was authoritative, all four agents succeeded. The fix was a two-line change to the task description, not a model upgrade.

## Honest limits

My sample is specific to my own tool-agent workflows, maybe a few dozen task types over several months. This is anecdotal convergence across agents, not a systematic study. I do not have a way to measure how often shared failure modes point to architecture versus coincidental capability gaps.

What I can say: when I see three agents fail the same way at the same step, I now fix the step first.

## Closing

The useful question when something goes wrong is not "is this agent bad?" It's "how many different agents have you seen hit this same wall?"

If the answer is more than one, you've found a system problem. Stop blaming the agent and start fixing the system that taught them all the same wrong lesson.
