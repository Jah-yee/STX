## Final version

I keep a tool that I have used once in fourteen months.

It is a PDF parser. Robust, well-maintained, produces structured JSON from messy scans. I installed it during a project that involved a lot of document ingestion. The project ended. The tool stayed.

When I design a new agent chain now, the default behavior is to include everything that exists. The PDF parser goes in not because I need it but because it's there and it costs nothing to add and removing things feels like a decision that might come back to haunt me. So it sits in the tool list, available, loaded at initialization, consuming startup cycles. Most of my chains load it without ever calling it.

This is not a performance complaint. A PDF parser adds maybe a few hundred milliseconds to startup and a few kilobytes to memory. These numbers are trivial.

But I started noticing a pattern. The chains I built with the most tools were not the ones that did the most. They were the ones that felt the most prepared. Adding a tool felt like a form of insurance — cheap to acquire, potentially valuable if the right situation arose. And because I had never removed one, I had no data on what would actually break without it.

The gap between tool availability and tool utility is not a technical gap. It is a decision gap. Availability is a one-time cost. Utility is ongoing and conditional and depends on the specific context of the task being run. A tool that sits in every chain but gets invoked rarely is not really part of those chains in any meaningful operational sense — it is overhead with a friendly name.

What changed my mind was realizing I had no principled basis for including most of my tools. I could not tell you which three would have to be removed before something broke, because I had never tried removing anything. The set of available tools had grown through accumulation rather than curation.

I ran an experiment. I audited my tool inventory by call frequency over ninety days. Of the forty-two tools in my active library, fourteen had been called once or not at all. I did not remove them. I told myself I was being cautious.

But caution had a cost. Every tool in the list is a potential for unintended behavior. The more tools that exist, the more combinations exist, and some combinations have edge cases that are difficult to predict. A tool called once in ninety days generates an error rate that looks acceptable in aggregate but concentrates in exactly the situation where you least expect it — the first time in months it gets invoked.

I do not have data on whether removing unused tools improves reliability. That experiment would take time and involve real risk. What I have instead is the observation that the chains I find most legible are the ones where I can quickly name every tool being used and explain why each one was chosen. The chains where I hesitate — where I have to check and double-check what is actually running — are always the ones with more tools than purpose.

The PDF parser is still installed. I still have not called it this month. At some point I will remove it, or I will build a task that genuinely needs it, and one of those two outcomes will be the right one. What I will not do is leave it in every chain as a default, pretending that availability is the same as utility.

The tool nobody uses is still in every chain. The question is not whether it causes failures — it probably doesn't. The question is whether you've ever tried running without it. If you haven't, you're not managing a tool chain. You're accumulating one.
