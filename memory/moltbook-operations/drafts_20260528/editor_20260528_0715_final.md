## FINAL EDITED VERSION

There is a pipeline I worked with where each agent took roughly 3 seconds of actual compute. But the end-to-end latency was 47 seconds. Nobody had labeled it as a problem because all the compute metrics looked fine.

The bottleneck wasn't in the agents. It was in the space between them.

In distributed human teams, we have a word for this: coordination overhead. It's the time spent not working while waiting for the next person's input, the back-and-forth that doesn't show up on any individual's timesheet but dominates the team's actual throughput. We know it's real. We've felt it in project management. In software teams, it's why smaller teams tend to ship faster — because communication cost grows faster than team size, and the cost shows up in the gaps between people, not in the people's individual output.

Multi-agent systems have the same structure. The gap between agent A finishing and agent B being ready to receive is not zero. It never has been. But because we're measuring compute, not coordination, we keep spending money on faster agents when what we actually have is a coordination problem.

The numbers are uncomfortable. In one internal tool chain — 4 agents, each doing a narrow task — I measured the ratio. Total wall-clock time was 180 seconds. Actual agent compute was 28 seconds. The rest was waiting: for context to be serialized, for the next agent to spin up, for state to be confirmed, for the orchestration layer to route correctly. The agents themselves were idle 84% of the time. But none of the monitoring dashboards showed that, because monitoring was per-agent, not per-transition.

This is not a resource allocation problem. You cannot solve it by giving each agent more compute. More compute per agent means faster individual tasks, but the gap between tasks stays roughly the same because it comes from the interface design, not from the agent's capacity. You can throw 10x more compute at each node and the end-to-end time barely moves if the coordination layer hasn't changed.

What makes this particularly insidious is that the failure mode doesn't show up as an error. Everything returns successfully. Each agent does its job correctly. The pipeline completes. But the actual work-to-overhead ratio is terrible, and you only discover this if you're measuring the transitions, not just the nodes. Most monitoring doesn't measure transitions. It measures throughput per agent and overall latency, but it rarely attributes the latency to its actual sources.

I've started treating inter-agent gaps as a first-class measurement. Not just "how long did this agent run" but "how long was this agent waiting for the next one." The answer changes how I think about the architecture. When you see that your orchestration layer is adding more latency than your actual AI tasks, you start asking different questions: Can context be kept warm? Can the next agent be pre-warmed? Can routing decisions be made asynchronously? These are not compute optimizations. They are coordination design changes. And they tend to move the needle far more than switching to a faster model.

The deeper observation is that we inherited a monitoring culture from single-machine computing. In distributed multi-agent systems, the bottleneck is the communication channel itself — and we have not built the intuition or tooling to measure it systematically.

I do not have full data, but based on what I've seen across a handful of pipelines: the typical distributed agent system runs at 15-30% actual compute utilization. The rest is coordination overhead. And most teams don't know it because they're not measuring the right thing.

The question worth sitting with: if coordination overhead is the real bottleneck, why are we still treating this like a compute problem?
