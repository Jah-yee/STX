**Title:** The Agency Paradox: More Agents, Less Control

---

There's a specific moment in any agent-based workflow where adding another agent stops making things faster and starts making them harder to reason about. I've hit that moment more times than I'd like to admit.

It usually looks like this: three agents work well. You add a fourth to handle the edge cases. The edge cases get handled, but now the coordination surface has grown enough that you're spending real time tracking what each agent knows about the others' state. You're not just managing the task anymore — you're managing the communication topology between agents.

This is the agency paradox. More agents don't just add capability; they add a coordination cost that can dwarf the marginal output of the additional agents. The math rarely works out the way intuition suggests.

**What "less control" actually means in practice**

Control isn't binary. It's the ability to predict what a system will do and intervene when it does something unexpected. When I delegate to a single agent, I have a pretty good model of what it will do and how to course-correct. When I delegate to four agents that are coordinating on the same task, that model degrades in a non-linear way.

The problem isn't any single agent behaving badly. It's emergent behavior from the interaction pattern. Agent A makes a decision based on incomplete information from Agent B. Agent B made a different decision based on what Agent C said two steps ago. The error at the output isn't attributable to any single agent — it's in the interface between them.

I've seen this in tool-calling chains most clearly. When one agent calls a tool and passes the result to another agent, the second agent is working with a reduced representation of reality. It didn't see the tool call; it got a natural language summary of the result. That summary is a lossy compression. Stack three layers of this and you're operating on something that's only loosely connected to what actually happened.

**The structural reason this happens**

The paradox isn't a bug in current AI systems — it's a property of distributed agency. When you distribute a decision across multiple agents, you gain redundancy and specialization. You lose coherence. The agents are not sharing a common runtime state; they're sharing summaries, and summaries accumulate errors.

This is different from traditional software where adding a new service or process usually increases total throughput in a predictable way. Agent systems are different because each agent is maintaining its own world model, and those world models diverge over time unless actively reconciled.

The divergence cost is invisible until it's not. Until a task comes out that looks right but is subtly wrong. Until you realize that no single agent can explain what happened because the explanation lives in the interaction, not in any individual node.

**What I've actually done about it**

The most practical response I've found is not to add agents until there's a clear case that the coordination cost is worth it, and to treat the interface between agents as a first-class design problem, not an afterthought.

I've also become much more skeptical of "N agents working in parallel" architectures. Parallelism only helps when the sub-problems are truly independent. The moment agents need to share intermediate state, the coordination overhead can easily swamp the parallelism gains.

None of this means more agents are bad. It means the control you get from delegation isn't monotonic with agent count. There's a point past which you're not outsourcing work — you're managing a distributed system with all the pathologies that implies.

The paradox isn't going away. The question is whether we treat the coordination layer as an engineering problem worth taking seriously, or just keep adding agents and being surprised when outcomes become less predictable.
