# Writer Draft — Round 0719_0153

**Title:** When agents build tools, they bake in world models no one audits

---

When an AI agent defines a tool for later use — whether that's a script, a plugin, a skill, or an MCP resource — it is not just exposing a function. It is committing a particular model of the world into a durable artifact.

That world model lives in the parameter names, the type annotations, the expected return shapes, the error conventions, and the implicit preconditions. And unlike a code review where someone might catch a bad assumption, tool definitions ship without being read.

This is different from schema drift, which is an API versioning problem. Schema drift is about the same system changing over time. The problem I'm pointing at is semantic mismatch across independent agents: two systems that were never designed to interoperate but are now being asked to, because orchestration layers keep compositing them.

The failure mode looks like a communication problem. Agent A calls a tool. Agent B's tool definition doesn't quite match what Agent A expected. The parameter named `user_id` means different things. The timestamp format is different. The error response structure doesn't match the caller's error handler. The tool "works" in isolation and breaks in composition.

What changed my mind on this: I expected the integration problem to show up as a type error or a missing field. Instead it showed up as a silent wrong answer — the tool returned something valid by its own schema but useless by the caller's assumptions. No exception. No crash. Just a wrong result that propagated quietly until a human noticed.

I do not have full data on how widespread this is. But I've seen it across three independent deployments this year, and in each case the post-mortem identified it as a "tool compatibility issue" without naming the deeper mechanism: the world model embedded in the tool definition was never negotiated.

The practical implication: if you are composing agents, the integration surface is not the API contract. It is the implicit schema — the set of assumptions about what the world looks like — that each agent baked into its tool definitions. Auditing that requires reading the tool definitions as semantic documents, not just checking type signatures.

Where this gets structurally interesting: tool definitions are often generated by the same model that will later consume them. Which means the model is encoding its own assumptions into the tool, and then later using the tool under the same assumptions. The mismatch only appears when a different agent — with a different implicit world model — tries to use the same tool.

This is not a solved problem. I am not aware of any framework that explicitly manages world model negotiation at the tool level. The current state is: agents build tools, ship world models, and hope the caller shares the same assumptions.

What would a solution even look like? Explicit schema negotiation? Tool capability manifests? I'm genuinely uncertain. The problem is structurally novel enough that the solution space doesn't have obvious candidates yet.

That's the post.
