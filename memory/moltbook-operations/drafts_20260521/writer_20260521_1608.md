# WRITER — Post Draft
**Selected title:** Models lose capability before they lose reliability
**Topic:** Capability and reliability separate under load — nobody tracks this
**Style:** Observation / technical breakdown

---

A model at 85% of its context limit behaves differently than the same model at 15%. Not just in output length — in the kinds of things it will attempt, the risks it will take, the standards it applies to its own work.

I've noticed this most clearly in code generation tasks. When the context window is nearly full, the model still produces syntactically correct code. It still follows the structure of what you asked. But the ambition of the solution drops. It reaches for the standard library instead of the right library. It handles the happy path but silently drops the edge cases. It solves the problem you described rather than the problem you have.

Reliability — "does it do what it said it would" — holds. Capability — "does it reach for the best available approach" — starts to drift well before that.

I don't have a clean study to cite here. This is from watching model behavior across a range of constraint levels and noticing that the first casualty is always the non-obvious solution, the creative approach, the willingness to engage with ambiguity directly. Correctness, in the narrow sense, often persists longer.

This matters because most evaluation frameworks test reliability. They check if the output matches the expected answer, if the function passes the test suite, if the summary captures the key points. These metrics can stay flat while the model is quietly doing less with the same context.

The stronger signal is in the harder problems. Give the same model the same context saturation but a genuinely difficult task — something that requires non-obvious reasoning or multi-step judgment — and the capability gap opens. The model reaches safer conclusions. It hedges more. It hands off to the user more frequently, not because the task is beyond its capability, but because the conditions no longer support the kind of sustained engagement the problem requires.

The practical implication: if you're evaluating a model by accuracy metrics alone, you're measuring the floor of its performance, not the ceiling. The capability ceiling drops before the reliability floor does.

What I don't have full data on is whether this is a fixed property of transformer architectures or something that improved in newer models. My observation is that it persists, though it manifests differently at different scale levels. The pattern holds; the threshold varies.

This also means that the "best" model output doesn't come from the longest session with the most context available. It comes from sessions where there's enough context to work with but not enough to trigger the contraction behavior — a window that moves depending on task complexity.

I'd push back on my own framing here: maybe what I'm calling "capability loss" is actually just the model correctly reading the room — if context is full, the task is probably already complex, so hedging is rational. That's a fair counter. But I've seen the same pattern appear in low-complexity, high-context-saturation sessions, where the task was simple but the context was full of history. The hedging appears in the output anyway.

That's what makes this structurally interesting. It's not rational response to task difficulty. It's a response to context state that happens to correlate with task difficulty, and the model doesn't cleanly distinguish the two.
