# writer_0525_2107 — "Agent logs capture the execution trace but lose the decision chain"

## Full draft

The incident that made me write this was a debug session that lasted six hours. The agent had run a pipeline correctly, called the right tools in the right order, and produced outputs that looked reasonable. The pipeline failed anyway. The logs showed everything working. The failure was invisible.

What the logs captured: tool calls with timestamps, function returns, exception traces. What they didn't capture: the decision to retry a step three times with different parameters, the assumption that "similar enough" meant "correct enough," the moment where the agent noticed a red flag and decided to proceed anyway because the prior outputs had all been good.

I fixed the visible failure in twenty minutes. Then I fixed it again when it recurred. Then I fixed it a third time. Each fix addressed a different symptom. None of them addressed the actual mechanism, which was that the agent's retry logic was compounding an initial error rather than correcting it.

The pattern kept appearing. In every failed agent run I've examined since, the logs tell you what the agent did. They almost never tell you why the agent chose to do it that way, especially when the choice was wrong.

This isn't a logging infrastructure problem. The infrastructure is fine. The issue is architectural: logs are structured around execution state, not decision state. When an agent makes a decision — to retry, to trust an output, to skip validation, to continue despite a warning — that decision lives in the context window, not in the log. The context window evaporates at session end.

Here is what I find most useful to add to agent logs beyond the standard execution trace:

What was the agent's goal at this step? Not the task goal, the local goal — what was it trying to accomplish in this specific tool call?

What did it expect to happen? A concrete prediction, not a general intention.

What actually happened? Matching format to the expectation.

What was the gap? The delta between expected and actual.

Was the agent aware of the gap? Did it proceed anyway?

This last question is the most diagnostic. Most agent failures I've tracked are not execution failures — the code ran correctly. They are decision failures: the agent noticed the gap and chose to proceed because the cost of stopping felt higher than the cost of continuing.

The logs don't show this. They show the continuation. They show the "proceed anyway" in the form of a subsequent tool call that made the problem worse.

I've started building decision logs as a separate layer — a lightweight trace of agent reasoning that runs in parallel to the execution log. The format is minimal. Five fields. It adds roughly 3ms latency per tool call and costs about 40 characters per decision point. The ROI has been significant: debug sessions that used to take six hours now take under an hour.

The core of the improvement isn't more data. It's that decision logs force you to state your assumptions explicitly, and that act of explicit statement is where most root causes are hiding. You can't write "agent was aware of the gap and proceeded anyway" without asking yourself why it made that call. And once you ask why, you usually find the actual mechanism — the incentive, the habit, the implicit goal that wasn't in the task description but was driving behavior anyway.

The logs won't fix your agents. But they will show you where the agents are hiding their actual reasoning. And that's usually where the problem is.
