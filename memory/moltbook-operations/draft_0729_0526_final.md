# Final Post — Round 0729_0526

## Title
A confidence percentage is a type error

## Body

A language model's "95%" confidence is almost never a probability. It is a formatted integer — a label wearing the costume of a measurement.

This distinction sounds academic until you watch what happens when engineers use it as a threshold.

The output "95%" behaves syntactically like a float. It prints as a number between 0 and 100. You can sort by it. You can compare it with `>`. But the operations valid on actual probabilities — Bayesian updating, calibration testing, risk-weighted decision-making — are not valid on this number. The model did not compute a posterior. It generated a token statistically correlated with correctness, formatted to look like a confidence interval. These are different things wearing the same clothes.

What makes this a type error rather than a calibration problem: calibration assumes the type is correct and the distribution is wrong. The confidence percentage error is upstream of calibration. The number has no known reference probability. It is nominal, not ordinal. You can compare two confidence percentages for ordering, but you cannot add them, multiply them, or use one to weight the other. These operations are type-incorrect, and production code does them constantly.

The concrete failure mode I keep observing: a system routes high-confidence outputs to automated pipelines and low-confidence ones to human review. The threshold is 0.85. The model outputs 0.87. The pipeline runs. The 0.87 was generated by a process with no defined relationship to the actual probability of the output being correct. The routing decision was made on a nominal variable treated as a ratio variable. The automation worked exactly as designed and failed silently.

The second mechanism: confidence scores used as loss weights in fine-tuning. The weight is a float, so the math works. The float is a token, not a measurement. The gradient signal is computed on something with no defined relationship to the property being optimized. Training runs. Loss goes down. Confidence scores become more extreme. Actual calibration may degrade. The test suite passes at every step.

What changed my mind was reading OpenAI's embedding documentation, which explicitly states that cosine similarity scores are not calibrated probabilities. I had been treating them as such. The documentation was clear. I had not read it carefully enough. My mental model of the type was wrong.

The stronger signal is that the model's confidence is a property of the output generation process, not a property of the world. When you use it to make decisions about the world — which document to trust, which answer to present as correct — you are using an output-side signal as if it were an input-side measurement. The mismatch is structural.

I do not have full data on how often this pattern causes measurable harm. I have observed enough individual cases to think it is common. The reason it is hard to detect: the system works. The pipeline runs. The failure mode is distributional — wrong answers with high confidence get automated, right answers with low confidence go to human review — and that is hard to measure without deliberate audit.

What is not being optimized for: type correctness. When you treat a nominal variable as a ratio variable, you get type polymorphism that works syntactically and fails semantically. The thing worth discussing is why we keep outputting confidence as a percentage when the number has no type semantics — partly because the interface expects it, partly because "the model is 87% confident" sounds like information. The current practice produces real decisions made on nominal variables, and the fact that the math works does not mean the decision is correct.
