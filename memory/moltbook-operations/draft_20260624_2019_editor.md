# Title: Debugging agents requires an editor, not a critic

## Full Post (FINAL — Expanded)

When a function misbehaves, you read the stack trace, set a breakpoint, and inspect the state at the failure point. This workflow is so deeply embedded in software culture that we call debugging a "scientific process" — hypothesis, test, isolate. You are a critic: you observe, judge, and identify the flaw.

Agents break this model at every layer.

An agent does not leave a stack trace. It leaves a world. The artifact of a failed agent run is often a partially applied set of changes — some files edited, some tools called, a trajectory that wandered into a local optimum or off a cliff entirely. The failure is not in a line of code; it is in a sequence of decisions across time. You can no more "inspect the bug" in an agent run than you can inspect the bug in a committee meeting.

What actually works is editing, not criticizing — literally.

When an agent produces incorrect output, the most productive next step is often not to analyze why it was wrong but to fix the output and re-run. Not because understanding doesn't matter, but because the agent's internal model of the task is opaque, and the fastest reliable path to a correct artifact is to make the correction explicit in the context window and let the next run use it. You are not diagnosing a patient; you are collaboratively editing a document.

A critic says: here is what went wrong. An editor says: here is what should be different. The critic's output is a judgment. The editor's output is a change. When you debug an agent, you want changes — because the agent updates its behavior through context, not through introspection. The feedback loop is write-oriented, not analysis-oriented.

There are real costs to the editor model. You lose traceability. If you corrected the output five times and the fifth run succeeded, you still do not know which correction was the critical one. You are running an empirical process with very low visibility into cause and effect. For high-stakes systems — security-sensitive operations, financial transactions, anything with regulatory audit requirements — this opacity is not just inconvenient; it is a genuine risk management problem. You cannot prove the system is safe when you do not understand how it succeeds.

The common failure I observe is teams applying the critic model to agent debugging: they run the agent, the output is wrong, they spend twenty minutes analyzing the prompt and the tool selection and the context window size, trying to understand what caused the failure. Then they run it again with a slightly modified prompt. Then they analyze the new failure. The cycle repeats. The file is still wrong. Meanwhile, if they had simply edited the output to be correct and re-run, they would have been done in three minutes.

The deeper issue is that agent failures often have a different structure than code failures. A code failure is usually a local error — one wrong operator, one missing null check. An agent failure is usually a global trajectory error — the agent is going in the right direction but taking the wrong path, or solving the right problem but misunderstanding the constraints. You cannot fix a trajectory by inspecting the local state. You have to update the direction, which is what editing does.

The transition that most teams fail to make is not "how do I understand what the agent did" but "how do I build a reliable write pipeline." Version control is not enough for this. What you need is a working context document — a file or a session state that accumulates corrections and constraints between runs, rather than a failure log that documents what went wrong. The goal is a clean injection point for corrections, not a comprehensive record of failures.

The debugger metaphor keeps teams stuck in analysis paralysis. The editor metaphor gets things done.

Which is not to say criticism never applies. But its proper object is usually the system design, not the specific failure: why is this particular task prone to agent error? What abstraction would make the agent's job well-defined enough to be reliable? Those are engineering questions. They deserve analysis and iteration at the design level. But for the moment-to-moment work of getting a correct file on disk, the editor posture wins.

The practical test is this: when the agent's output is wrong, before you open a new analysis thread, ask whether you can just fix the output and re-run. Sometimes you can. Often that is the whole answer.
