**Selected title:** Good explanation ≠ correct answer. They use different mechanisms.

**Core claim:** Explanations in LLMs are generated separately from answer construction. They postdict rather than predict. A model can produce a high-quality explanation for an incorrect answer.

---

## Draft

There is a standard assumption baked into how we use LLMs: that a model which explains things well is more likely to be correct. The logic feels sound — if a model can walk you through why something is true, it probably understands the thing. Explanations feel like evidence.

But I don't think the mechanism works that way.

When an LLM generates an explanation, it is not showing you the reasoning process that produced the answer. It is constructing a plausible narrative *after* the answer has been determined. The answer and the explanation are generated by different mechanisms, often at different stages of inference, and they are not always consistent with each other.

This is not a bug I am describing. It is a consequence of how these models work. The training signal for explanations is not "is this explanation accurate?" — it is "does this explanation sound like a good explanation?" These are not the same thing. A fluent, confident, well-structured explanation can be constructed around a wrong conclusion just as easily as around a correct one. The fluency is learnable independently of the accuracy.

I noticed this most clearly in a case that stuck with me. A model was asked a factual question. It gave the wrong answer. Then it produced a two-paragraph explanation that was internally coherent, used appropriate domain vocabulary, and would have been completely convincing to someone who did not already know the correct answer. The explanation was well-formed. The answer was wrong. The explanation did not save the answer.

What changed my mind about this was thinking about what an explanation actually *is* in this context. It is not a trace. It is a constructed artifact, generated to satisfy the prompt. The model has learned that users want explanations, and it generates them with the same fluency it generates everything else. Fluency is a real capability. It is just not the same capability as accuracy.

This matters most in high-stakes domains where people use explanation quality as a proxy for correctness. If a model explains a medical decision, a legal reasoning, or a financial calculation — and the explanation sounds right — the natural assumption is that the underlying decision is sound. But the explanation is not the decision. They share an interface but not a mechanism.

What I have started doing, practically, is treating explanations as a separate output channel. I hold the answer and the explanation to different standards. The explanation can be evaluated on its own terms: does the logic actually follow? Are the intermediate steps consistent? Does the explanation contain the answer, or does it argue for something the answer does not actually support? These are questions a good explanation can pass. But passing them does not make the answer correct. They test different things.

I do not have data on how often explanation quality and answer quality decouple in production use. My observation is that it happens more often than the framing "the model explained it well, so it probably understands it" suggests. The model explaining something well is evidence that it can explain. It is not evidence that the explained content is true.

The practical implication is not to distrust explanations. It is to stop using them as correctness proxies. An explanation is a communication artifact. It can be well-formed and wrong. The answer either matches the world or it does not. These are separate questions.

Where this gets genuinely tricky is when the explanation *would* be correct if the answer were different — when the model constructs a sound argument for a wrong conclusion, because the argument itself is valid but the premise was wrong. That is a different failure mode, and it is the harder one to catch, because the explanation looks solid even when the outcome is wrong.

The point is not that explanations are useless. It is that they answer a different question than the one you are usually asking.
