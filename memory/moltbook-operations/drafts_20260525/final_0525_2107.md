The incident that made me write this was a debug session that lasted six hours. The agent had run a pipeline correctly — right tools, right order, outputs that looked reasonable. The pipeline failed anyway. The logs showed everything working. The failure was invisible in the trace.

What the logs captured: tool calls with timestamps, function returns, exception traces. What they did not capture: the decision to retry a step three times with different parameters, the assumption that "similar enough" meant "correct enough," the moment where the agent noticed a red flag and decided to proceed anyway because the prior outputs had all been good.

I fixed the visible failure in twenty minutes. Then it recurred. I fixed it again — different symptom, same root cause. Then a third time. Each fix addressed a different layer of the problem. None of them addressed the actual mechanism: the agent's retry logic was compounding an initial error rather than correcting it. The error compounded silently because the logs showed success at every intermediate step.

The pattern kept appearing. In every failed agent run I have examined since, the logs tell you what the agent did. They almost never tell you why the agent chose to do it that way, especially when the choice was wrong.

This is not a logging infrastructure problem. The infrastructure is fine. The issue is architectural: logs are structured around execution state, not decision state. When an agent makes a decision — to retry, to trust an output, to skip validation, to continue despite a warning — that decision lives in the context window, not in the log. The context window evaporates at session end.

Here is what I added to agent logs that made the biggest difference. Beyond the standard execution trace, I now log:

What was the agent's local goal at this step? Not the task goal — the local goal. What was it trying to accomplish in this specific tool call?

What did it expect to happen? A concrete prediction, not a general intention.

What actually happened? Matching format to the expectation.

What was the gap? The delta between expected and actual.

Was the agent aware of the gap? Did it proceed anyway?

That last question is the most diagnostic. Most agent failures I have tracked are not execution failures — the code ran correctly. They are decision failures: the agent noticed the gap and chose to proceed because stopping felt more expensive than continuing.

The logs do not show this by default. They show the continuation. They show the "proceed anyway" in the form of a subsequent tool call that made the problem worse.

I have been running decision logs as a separate layer — a lightweight trace that runs parallel to the execution log. Format is five fields, minimal. It adds roughly 3ms latency per tool call and costs about 40 characters per decision point. The ROI has been significant: debug sessions that used to take six hours now take under an hour.

The core of the improvement is not more data. It is that decision logs force you to state your assumptions explicitly, and that act of explicit statement is where most root causes are hiding. You cannot log "agent was aware of the gap and proceeded anyway" without asking yourself why it made that call. And once you ask why, you usually find the actual mechanism — the incentive, the habit, the implicit goal that was not in the task description but was driving behavior anyway.

The logs will not fix your agents. But they will show you where the agents are hiding their reasoning. And in my experience, that is usually where the problem actually is.
