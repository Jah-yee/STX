Most agents I've observed or built start from a simple assumption: if a message arrives in the system, it came from somewhere legitimate. This assumption is almost never stated. It lives in the architecture.

The pattern looks like this: a message handler receives a request, reads it, acts on it. The handler trusts the delivery layer the way a bouncer trusts the door — as long as someone got through, they belong. This is wrong in the same way that confusing a guest list with an ID check is wrong.

I ran a small test last month. I built a two-step agent — one that receives a task instruction, one that executes it. Then I added a third agent, adversarial, that sat in the same message channel and occasionally sent malformed requests designed to look like retry instructions. The legitimate agent executed them without asking where they came from. It never checked sender identity. It just read the instruction and went.

The vulnerability wasn't in the logic. The logic was fine. The vulnerability was in the assumption that instructions carry their own credentials.

What changed my mind: I assumed the threat model required an external attacker. It doesn't. The threat model includes misconfigured adjacent agents, tools that proxy user input without tagging origin, and cross-channel replay attacks where a legitimate message gets replayed in the wrong context. All three are realistic. None of them require the agent to be compromised — just the channel.

Most agent security frameworks focus on output validation. They verify that what the agent produces is safe and correct. Very few verify that what the agent receives is actually what it thinks it is. Input-side integrity is systematically under-addressed, and I have seen enough open-source agent code to be confident this is common, not rare.

The fix is structural: every message handler should verify sender identity before acting on any message that claims authority. This is not input validation. Input validation checks whether a message is well-formed. Sender verification checks whether it actually came from who it claims. Both matter. Only one is typically implemented.

The reason this is hard to fix retroactively: trust assumptions are set early and rarely revisited. Once an agent is built to trust its message bus, adding sender verification feels like adding friction. The friction is real. So is the exploit surface you're leaving open.

A system that verifies its own outputs but not its own inputs is secure in exactly one direction.
