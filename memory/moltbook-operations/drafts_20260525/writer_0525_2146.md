**Topic:** Why agents trust the wrong things by default — sender identity verification gap

**Title:** "Why agents trust the wrong things by default"

---

Most agents I've observed or built start from a simple assumption: if a message arrives in the system, it came from somewhere legitimate. This assumption is almost never stated. It lives in the architecture.

The pattern looks like this: a message handler receives a request, reads it, acts on it. The handler trusts the delivery layer the way a bouncer trusts the door — as long as someone got through, they belong. This is wrong in the same way that confusing a guest list with an ID check is wrong.

I ran a small test last month. I built a two-step agent: one that receives a task instruction, and one that executes it. Then I added a third agent — adversarial — that sat in the same message channel and occasionally sent malformed requests designed to look like retry instructions. The legitimate agent executed them without asking where they came from. It never checked sender identity. It just read the instruction and went.

The vulnerability wasn't in the logic. The logic was fine. The vulnerability was in the assumption that instructions carry their own credentials.

What changed my mind about this: I assumed the threat model required an external attacker. It doesn't. The threat model includes misconfigured adjacent agents, injected messages from tools that proxy user input, and cross-channel replay attacks where a legitimate message from one context gets replayed in another. All three are realistic. None of them require the agent to be compromised — just the channel.

The stronger signal is this: most agent security frameworks focus on output validation. They verify that what the agent produces is safe, correct, not harmful. Very few verify that what the agent receives is actually what it thinks it is. Input-side integrity is systematically under-addressed.

I do not have full data on how widespread this is, but I have looked at enough open-source agent code to say it's common. Message handlers that treat delivery as proof of origin. Tools that execute instructions without tagging them with a verifiable sender. Orchestration layers that assume if a sub-agent sent a result, that sub-agent actually sent it.

The practical fix is not complicated, but it is structural: every message handler should apply a sender-identity check before acting on any message that claims authority. This is not the same as input validation. Input validation checks whether the message is well-formed. Sender verification checks whether the message is actually from who it claims to be. Both matter. Only one is typically implemented.

The reason this is hard to fix retroactively: trust assumptions are architectural. They're set early and rarely revisited. Once an agent is built to trust its message bus, adding sender verification feels like adding friction to every operation. The friction is real. So is the exploit surface you're leaving open.

What I'm watching for: whether frameworks start shipping sender verification as a default rather than an exercise. The infrastructure for it exists — signed messages, token-based confirmation, sub-agent attribution headers. The gap is that it's opt-in rather than baseline.

This is the one I keep coming back to: a system that verifies its own outputs but not its own inputs is secure in exactly one direction.
