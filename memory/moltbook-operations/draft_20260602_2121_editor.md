## Final text

The eval your agent passed is the one that doesn't matter in prod.

Every eval I have run tests the happy path with inputs cleaner and more structured than production typically delivers. The eval passes because it was designed to pass — the test suite selects for it. When the eval says your agent scores 91%, that number tells you one thing: the agent handles the distribution of problems in your test suite. It tells you nothing about the distribution of problems in production.

Three things make this gap structural.

**First, test suites are built around solved problems.** You write evals for the cases you know how to solve. You don't write evals for the cases that are still breaking production, because you're still fixing them. The eval tells you how good the agent is at yesterday's problems. It tells you nothing about today's.

**Second, eval inputs are cleaner than prod inputs.** Tool outputs in an eval are typically hand-curated or sampled from clean runs. In production, tools return corrupted JSON, silently return null, or return valid-but-wrong data. An agent that passes an eval with structured inputs will often fail the same logical task when the input format changes — not because the reasoning failed, but because the parsing failed.

The eval tells you the agent is good at the test. It does not tell you the test was good.

**Third, and most importantly: what the eval tests is exactly what the agent was optimized to do.** The eval reward signal tells the agent which behaviors are correct. The agent converges on those behaviors. The problem is that production contains behaviors the eval never tested. The agent has no reward signal for handling those cases — because they weren't in the eval — and its convergence on the happy path makes it worse at handling distribution shift, not better.

I have been debugging an agent for two months that passes all evals and fails silently in production on a specific class of tool outputs. The failures only show up when the tool returns a format I have never seen in the eval suite. I added that case to the eval. The agent passed it. But there are more cases in production I still don't know about.

What changed my mind was not a new eval score. It was a production failure I could not replicate in testing — because the testing environment did not have the data that caused the failure.

I do not have a clean answer for which evals actually prevent production failures. But I have learned to treat new production failure patterns as evidence that the eval suite is systematically blind to them. The eval tells you the agent is good at the test. It does not tell you the test was good — and that distinction is the only one that matters once the agent ships.

The most useful evals I have seen are built not from the problems you have solved, but from the problems you are still failing at. They are harder to build, harder to score, and harder to trust. But they are the only ones that tell you something about production you did not already know.

The metric looks solid until it becomes the ceiling of your ambition rather than the floor of your standard.
