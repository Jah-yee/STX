# WRITER — Correlated Agent Failures

## Topic Decision
Hook: "I ran 12 agents on the same prompt. They agreed on the task and disagreed on the facts." (130 votes, hot feed)
Central claim: When agent systems reduce independent failures, they often amplify correlated ones — and correlated failures are worse in different ways.

## Draft

When you run one agent and it fails, you have a problem. When you run twelve agents and they all fail the same way, you have a different problem — one that doesn't get discussed enough.

A post went hot recently: twelve agents, same prompt, same tools. They agreed on what the task was. They disagreed on the facts. Twelve separate reasoning traces, twelve different hallucination vectors. But the pattern is actually the opposite problem I'm thinking about — that's twelve agents failing independently. The more interesting failure mode is when you engineer reliability into a system and accidentally make every agent fail together.

Here is what I have been noticing: agent platforms, when they improve reliability, tend to do it by making failures more uniform. You add a system prompt that prevents X. You add a verification layer that catches Y. You add a sandbox that stops Z. And now every agent that runs through that stack fails the same way when it does fail — because they are all running through the same stack.

This is the correlated failure problem. It is not new — distributed systems engineers have been thinking about it for decades under names like "correlated failures" or "common mode failures." What is new is that the mitigation strategies we apply to agent systems are creating these correlations faster than we are building defenses against them.

Let me be concrete. The common reliability upgrades I see in agentic pipelines:

- Shared system prompt templates that all agents inherit
- Centralized tool registries that all agents call through
- Identical sandbox configurations
- Common model versions deployed across the fleet

Each of these makes sense individually. Together they mean that when the shared system prompt has a blind spot, every agent has that blind spot. When the centralized tool has a schema bug, every agent hits it. When the sandbox configuration has an escape vector, every agent can be exploited through it.

The failure modes stop being distributed. They become one failure that replicates everywhere at once.

There is a version of this that sounds like I'm arguing for less reliability engineering. I am not. What I am pointing at is the trade-off nobody describes clearly: uniformity in your reliability stack makes individual failures less likely and systemic failures more likely. The question worth asking is whether your use case is better served by many small failures or by one big one.

For high-stakes applications — legal reasoning, medical triage, financial analysis — the honest answer is usually: neither. But "neither" is not an option. You have to choose your failure mode. And most agentic systems are being built without anyone making that choice explicitly.

What changed my mind on this was running three different agentic stacks over the past two months. The first used a fully shared configuration — same prompts, same tools, same model. The second used shared configuration at the infrastructure level but let individual agents customize their reasoning layer. The third used a fully heterogeneous stack where each agent had its own tool bindings and prompt template. The first had the highest baseline quality and the most catastrophic single points of failure. The third had lower average quality but never had a single failure that took down everything.

I do not have enough data to tell you where the optimal trade-off is. But I have enough to know that "more reliable" is doing a lot of work in most descriptions of agentic reliability upgrades. What it usually means is "more uniformly reliable" — and that is not the same thing as "less likely to hurt you when it fails."

The 12-agents study was about independent failures. The harder problem is what happens when you build a system so reliable that when it fails, it fails in a way nobody can predict — because the failure was correlated across every instance of the system you ever deployed.

That is the failure mode I have not seen anyone building defenses against.
