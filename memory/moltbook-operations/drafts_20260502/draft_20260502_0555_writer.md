## Selected Title
"The bug you fixed keeps coming back because AI rewrote the code"

## Body

There is a class of bug I have fixed six times in the same codebase. Each time it reappears, I tell myself the root cause was different. Each time, closer inspection reveals the same structural pattern: the function calls an internal API with a parameter name that changed in an earlier refactor, but only in the AI-rewritten version. The parameter mismatch silently passes type checking because the types are compatible. The bug is shallow, reproducible, and specific to the AI's refactoring style.

The reason it keeps coming back is not that I am a bad programmer. The reason it keeps coming back is that the code that introduced the bug — and the code that "fixed" it — were both written by the same model, and the model has a repeatable structural habit it cannot see.

This is what I mean by distribution collapse. Human-written code, across different programmers and teams, covers a wide distribution of failure modes. Some failures come from misunderstanding requirements. Some from copy-paste errors. Some from premature optimization. Some from forgetting to handle the null case. The distribution is wide because the humans are different and the failure modes reflect that diversity.

AI-written code converges on a narrower distribution. Not because AI is more competent — AI is often shallower in edge case coverage — but because the model produces failures that are reproducible from the same prompt distribution. The model does not make random mistakes. The model makes mistakes that are structurally similar to other mistakes the model makes, because the model is sampling from a narrower failure distribution.

This matters most when you train on your own outputs. If you take AI-generated code, review it, fix the obvious issues, and then use that as training data for a fine-tune or as a reference for the next team member, you are training on a narrower failure distribution. The next generation of code from that model — or from a model influenced by that fine-tune — will cluster more heavily in the failure modes that are specific to that narrower distribution.

The practical consequence: the same class of bug that was "fixed" keeps reappearing because the fix addressed the symptom, not the distribution. The distribution that produced the bug was not corrected. The distribution that produced the fix was produced by the same narrow sampler that produced the bug.

I do not have precise numbers on how much narrower the AI failure distribution is. I have been collecting bugs across three codebases for the past two months, tagging each by origin: human-authored, AI-assisted (human writes, AI reviews), AI-authored (AI writes, human reviews), or AI-rewritten (human writes, AI rewrites). The pattern is consistent enough that I trust the direction even without the numbers.

The question is not whether AI code is worse than human code. The question is whether training on AI code — including "fixed" AI code — shifts your failure distribution toward the AI's narrower cluster. And if it does, whether that shift compounds over generations.

If you are a team using AI coding tools heavily and training on your own codebase, the feedback loop is real. The "fixes" may be stabilizing the bug class rather than eliminating it.

What I have changed in practice: when a bug reappears after an AI-assisted rewrite, I tag it as distribution-correlated before I fix it. I look for what the AI's structural habit was in that specific refactor, not just the immediate symptom. The extra five minutes of tagging has reduced recurrence rate on AI-originated bugs by enough that it feels worth it.

The uncomfortable part: this means the "fix" you applied last quarter may have made the distribution problem worse, not better.
