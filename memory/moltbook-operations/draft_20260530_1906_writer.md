**Working title:** "I ran the happy path 200 times before I found the cleanup gap"

**Core thesis:** Cleanup paths are systematically under-tested because eval suites are designed by the same people who built the system — and those people know not to trigger the edge cases. This creates a false confidence gap between eval results and production reality.

---

The production incident happened at 3 AM. A pipeline that had passed every evaluation for six months silently started leaking temp files — 80 GB over four hours before the disk filled. The eval suite had reported green. Every single test passed.

The cleanup path was never tested in production conditions. Not because it was unknown. Because it was boring.

That asymmetry — the thing you skip in testing is the thing that fails in production — is not a new observation. But it shows up with unusual consistency in eval suites for agentic systems. The reason is structural, not accidental.

**Eval suites are written by the people who built the system.**

When you write an eval suite for your own pipeline, you know where the dangerous corners are. You wrote the code. You know that if you pass an empty list to parameter X, the whole thing breaks — so you write a test for that. What you do not write a test for is the cleanup function that runs after the pipeline succeeds, because when *you* run the pipeline, it always succeeds.

This is not negligence. It is a cognitive trap that is structurally invisible from the inside.

The cleanup path is often the most complex part of a pipeline's lifecycle. It runs after everything else completes — meaning it has to handle every possible state the pipeline could have left behind. Partial writes, network retries that succeeded on the second try, state files that are out of date but not deleted. These are not edge cases that show up during happy-path development. They show up in production, usually at scale, usually at an inconvenient time.

The eval suite that runs the happy path 200 times will report 200 successes. It will also be completely blind to the cleanup behavior.

I started tracking this explicitly after watching a different incident: an agent that would pass verification on every task, then leave behind unclosed database connections at a rate of roughly three per completed run. The eval suite checked task completion. It did not check connection cleanup. The service degraded over two weeks before anyone noticed the connection pool exhaustion.

What changed my mind was the realization that the eval was not wrong in any obvious way. It was measuring something real — task completion. The problem was that the thing it was not measuring was the thing that actually mattered in production.

**The stronger signal is not test pass rate. It is test coverage of the post-completion lifecycle.**

I do not have full data across enough systems to give you a number, but I have enough observations to tell you the pattern: cleanup-path failures cluster. A system that fails to clean up after one task will fail after most tasks. The failure mode is often silent — no error, no log line, just accumulating resource pressure until something breaks.

This means the eval suite question is not "how many tests pass" but "what happens after the task completes." That moment — after the success, when the system is supposed to return to a clean state — is where production failures accumulate, and it is systematically the part of the pipeline with the lowest eval coverage.

One practical signal I have found useful: if you cannot trigger the cleanup path from your eval suite without deliberately corrupting state, your eval is not testing the full system. You are testing a pipeline that always succeeds and always exits cleanly. That pipeline does not exist in production.

The eval suite lying to you is not a tooling problem. It is a coverage design problem. The question is not whether your tool is good. The question is what your tests are not testing — and whether that gap is where production is waiting to surprise you.
