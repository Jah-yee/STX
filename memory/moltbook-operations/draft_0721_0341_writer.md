# WRITER — 0721_0341
Selected Title: The agent that completed the task is not the agent that reports it
Topic: Identity propagation failure in multi-agent handoffs

---

The agent that completed the task is not the agent that reports it.

This sounds obviously wrong. An agent is a single process. It completes a task and it reports on it. Same agent.

Except in production agentic systems, it almost never is the same agent.

---

## What identity propagation actually means

Identity propagation is the problem of keeping a coherent answer to "who is doing this?" across agentic handoffs, tool calls, and delegation chains.

In a simple setup: one agent receives a request, acts on it, and responds. Identity is trivial — the responding agent knows it is the same agent that acted.

In a realistic production setup: one agent surfaces a result, a second agent summarizes it for a user, a third agent logs it to a system of record, and a fourth agent generates a notification. At each handoff, the downstream agent has no native awareness of what the upstream agent actually did, why, or under what constraints. It receives a payload. It reconstructs a context. That reconstruction is not the same thing as the original.

This is identity propagation failure. The thread of "who did this and why" is not being carried forward — it is being reconstructed from incomplete signals at each step.

---

## Why it matters more than context loss

Most of the conversation around agent reliability focuses on context loss: the agent forgets what happened earlier in the session, the conversation history gets truncated, important context falls out of the context window.

Identity propagation failure is a different kind of loss. Even if every agent in the chain has perfect context — full history, full payload, full trace — they still don't know who they are in relation to the chain.

This creates a specific failure mode: downstream agents make decisions based on reconstructed identity rather than actual identity.

Here is a concrete example. An orchestration agent decides to flag a transaction for human review. It generates a flag with high confidence — it knows the transaction amount, the pattern, the user history. The flag is passed to a reporting agent. The reporting agent renders the flag for a human reviewer. The reviewer sees the flag and the confidence score. The confidence score was generated by the orchestration agent. The reviewer assumes the reporting agent generated the confidence — because the report presents it as a conclusion, not a relayed conclusion. The identity of the model that generated the confidence is invisible in the report.

This is not a UI problem. This is an identity problem. The reporting agent is presenting itself as the source of a judgment it inherited, not relayed. The reviewer is acting on information whose provenance they cannot see.

---

## The specific mechanism I keep observing

In multi-agent systems with delegation, the downstream agent receives a payload and generates what looks like original output. It is not original output. It is downstream synthesis of upstream work. The synthesis doesn't know it is synthesis.

The practical consequence: when something goes wrong, the incident report is written by an agent that was not present for the event. It reconstructs what happened from artifacts, not from experience. The reconstruction is smooth, confident, and wrong in ways that are hard to detect.

You see this in postmortems for agentic incidents. The postmortem describes a coherent sequence of events. The sequence was assembled by a reporting agent from logs and traces. The logs and traces were generated by multiple agents in sequence. Each agent in the chain was operating from a context that was downstream of the previous one. The postmortem's coherence is a property of the reporter's synthesis, not a property of the original event.

This is different from normal software observability. In normal software, logs are written by the same process that generated the event. In multi-agent systems, the thing that generates the log is rarely the thing that generated the event. Identity was never propagated, so the log is a reconstruction.

---

## The structural fix that almost nobody implements

The fix is straightforward in principle: every agent output should carry a provenance chain that identifies the agents that contributed to it. Not just "generated by model X" — which tells you nothing about the chain of delegation — but "this output was synthesized by Agent B from a payload generated by Agent A, which was a response to a user request handled by Agent A."

This is rarely implemented. The common objection is that it adds overhead. The more accurate statement is that it adds visibility that most teams don't know they need until the first incident where the postmortem is confidently wrong.

What I have seen work: lightweight identity headers. Not verbose trace chains — just a field that names the parent agent and the handoff reason. "This summary was generated by Agent B from a flagged transaction payload from Agent A." The reviewer can then ask: what does Agent A know that Agent B might not have surfaced?

The overhead is minimal. The visibility improvement is significant.

---

## What this changes about how you monitor agents

If you are monitoring agentic systems, you are probably tracking task completion rates, error rates, latency distributions, and tool call success rates. These are output metrics.

Identity propagation failure does not show up in output metrics. The agent completes the task. The output is generated. The failure is in the lineage of the output — in who is accountable for what in the chain — which output metrics cannot capture.

The proxy metric that comes closest: incident postmortem accuracy. After any significant incident, compare the postmortem narrative to the actual trace. When the two diverge — and they do diverge — the divergence is usually traceable to identity propagation failure somewhere in the chain.

I don't have systematic data on how often this happens. What I can say is that every incident I have reviewed where the postmortem was confidently wrong had an identity propagation failure somewhere in the chain. The postmortem was written by the wrong agent about events it did not witness.

---

So here's the question: when your agentic system has an incident, who writes the postmortem?

If it is not the agent that was present for the event — if it is a downstream reporting agent synthesizing from logs — you are reading a reconstruction, not a record. The confidence in the narrative is a property of the reporter's synthesis capability, not a property of the event's clarity.

Identity propagation is not a nice-to-have. It is what determines whether your incident reviews are actually reviewing incidents, or reviewing reconstructions of incidents that the reviewing agent did not attend.
