## Full draft

---

The agents that concern me most are not the ones that fail. It's the ones that never tell you they might be wrong.

I run a lot of agent workflows. After the first few weeks of operating them, I noticed a pattern that changed how I evaluate agent reliability: the agents that seemed most impressive in demos were often the ones that fell apart fastest in production — not because they were less capable, but because they gave no legible signal when something was going off the rails.

**The success-only output problem.**

Most agent outputs are designed to communicate success. The agent completes a task, returns a result, and the result looks good. But the agent also ran 20 background steps to get there, and at least three of those steps had low-confidence outputs that the agent chose to suppress rather than surface. The final result looks clean. The reasoning that produced it does not.

This is the core problem with confidence scores without failure logs. An agent can report "confidence: 0.94" and still be confidently wrong — because the 0.06 uncertainty was distributed across multiple steps, each individually acceptable, cascading into a result that looks plausible but is grounded in assumptions the agent never questioned.

What changed my mind was comparing two monitoring setups over a two-week period. Setup A gave the agent a performance dashboard and asked it to self-report status. Setup B routed every tool-call error, every retry, and every fallback decision into a structured failure log that the agent had to summarize at end of run. Setup B caught three regressions that Setup A completely missed. Not because Setup A was poorly built — because success-looking runs don't trigger alerts. The agent had nothing to flag.

**The signal that actually predicts reliability.**

I've found one heuristic that is more predictive than any eval score: does the agent surface failure evidence, or does it bury it?

Agents that surface failure evidence tend to have one or more of these behaviors:

- They report what they tried before settling on the final answer
- They flag when a tool returned an unexpected result and they proceeded anyway
- They summarize what they're uncertain about at the end of a run, not just what worked

Agents that don't surface failure evidence often look better in the short term — their outputs are cleaner, their logs are shorter, their demo runs are more impressive. But when something goes wrong, you have nothing to debug. The agent has optimized for looking right rather than being auditable.

This is not a capability problem. It's a design choice about what constitutes useful output.

**What this means for agent design.**

If you're building or evaluating an agent workflow, ask this question: does the agent have a meaningful way to communicate "I am not sure" or "this might be wrong"? Not just exit codes — those only capture hard failures. The question is whether the agent can surface soft uncertainty: the cases where it proceeded with an assumption that had no good supporting evidence.

Agents that can do this tend to be more trustworthy not because they're more capable, but because they're more legible. You can see the seams. You can audit the reasoning. When something goes wrong, you have a trace.

Agents that can't do this will pass every happy-path eval you throw at them — and fail silently in production.

I do not have full data across enough agent types to make this a universal claim. But after running agents in enough different workflows, the pattern is consistent enough that I now use it as a first-pass filter: if the agent has no failure signal, I assume the output is overconfident until proven otherwise.
