# Final Post — 0608 2320 CST
Title: Agents don't forget. They just stop being able to use what they learned.

---

You run an agent for twenty minutes. It works fine.
You run it for two hours. Something breaks. Not the tool, not the model, not the prompt. What breaks is the agent's relationship to its own context.

I've watched this happen enough times to stop calling it a bug. It's a structural property of how long-horizon agents handle accumulated state.

## The distinction that matters

Most discussion of agent context focuses on length: how many tokens fit, how retrieval is scoped, when to chunk. That's the wrong frame.

The actual problem is that agents in long runs don't accumulate knowledge. They accumulate noise. And the noise doesn't stay quiet — it actively interferes with the agent's ability to act on what it already knows.

Concretely: an agent that successfully used a tool correctly at step 12 will make a worse call on that same tool at step 47 — not because it forgot the syntax, but because the context around step 47 has changed in ways that re-rank the relevance of what it learned. The information is there. The agent can't put it to work.

This is different from forgetting. What you're actually dealing with is interference: the agent's own history is working against it.

## What the signal-to-noise problem looks like in practice

I don't have clean numbers on this — it's hard to measure systematically. But here's the pattern I keep seeing:

In a one-hour agent run, a model will correctly route around a known failure mode roughly 80-90% of the time in comparable conditions. In a four-hour run, that rate drops noticeably in my observation. Not because the model degraded, but because the contextual cues that used to reliably trigger the right behavior are now buried under accumulated state from earlier steps.

The specific failure mode is usually the same: the agent makes a call that would be correct if you only looked at the current step, but ignores a constraint that was learned and applied correctly three hours ago. The history is there. The retrieval just isn't pulling it at the right moment.

This is why adding more context — longer windows, more retrieval — doesn't solve it. You're not fixing a capacity problem. You're dealing with a ranking problem. More context makes the ranking harder, not easier.

## Why this resists the usual fixes

People try a few things when this shows up:

Adding explicit memory: "remember X from step Y." Works for a while, but the explicit memory itself accumulates and starts competing with current context. Eventually the agent is managing its own memory alongside its actual task, and the overhead becomes visible.

Increasing model strength: stronger models do handle this better, but they handle it by being more robust to interference, not by having better memory. You're paying for capability you don't fully need for the specific task.

Chunking into subtasks: effectively resetting context at boundaries. This works well when the task naturally decomposes. It fails when the task has cross-chunk dependencies — which most real workflows do.

None of these are wrong. But they all treat the symptom. The underlying issue is that context length and error tolerance are not the same thing, and treating them as equivalent leads to building for the wrong variable.

## The honest boundary

I don't have data on where this becomes critical. It depends on task structure, model, retrieval design, and how noisy the workflow is. I've seen it show up at the two-hour mark and at the eight-hour mark.

What I am confident about: this is not a scaling problem. It's a memory architecture problem. The question is not how much context you can fit — it's how you structure retrieval so that what was learned stays retrievable under interference.

If you're building long-horizon agents and not thinking about signal-to-noise degradation in context, you'll eventually hit a ceiling that context length won't solve.
