## Topic

## Full Draft

There's a category of failure that stops your pipeline, and there's a category of failure that misleads your pipeline. The second one is architecturally worse, and most observability tooling doesn't know the difference.

I was running a retrieval pipeline last month. The tool returned an empty result — no documents found for this query. The code handled it gracefully: `results = [] if not results else results`. The pipeline continued. It ran the full pipeline. It produced a confident, structured answer. The answer was wrong, not because the model hallucinated, but because the retrieval step returned success (no results found is a valid HTTP 200) and nobody had told the downstream logic that "no results" means "stop, this query has no foundation."

A tool that errors forces your hand. You're writing a try/except block, or your code is crashing, or someone is paged at 2am. You handle the failure because the system insists you do. A tool that returns "no results" with a 200 and an empty array gives your pipeline permission to continue as if nothing went wrong. The pipeline produces output. The output is confident. The confidence is unearned.

This isn't a bug in the retrieval tool. It's a design choice about where the failure signal lives. Error codes push the failure into the developer's face. Empty arrays push the failure into the quiet logic of your data processing. The second category persists longer because nobody explicitly owns it.

The monitoring angle compounds this. Most observability for tool calls tracks: was the call made, did it return, how long did it take. Almost none of it tracks: was the returned result actually what you expected. You get latency dashboards and call counts. You don't get "this tool has been returning empty arrays for the last six hours and your pipeline has been treating them as valid signal."

I've started thinking about this in terms of failure contracts. An explicit error is a failure contract that says: something went wrong, handle it now. A silent empty return is a success contract that says: here's your data, proceed normally. The first one forces action. The second one allows your pipeline to glide into confident wrongness.

The real problem is that you can't easily test your way out of this. Your tests run against your understanding of what the tool should return. If your understanding has a gap — if you didn't anticipate that "no results" means "this query has no foundation, not "here's an empty list to process" — your tests will pass and your production will be wrong.

What I'm doing about it: I now explicitly label the two failure categories at the architecture level. When I design a tool call, I ask: what does success look like, and what does "returned but wrong" look like. The second one is harder to answer, but answering it prevents the case where your pipeline is running correctly and producing nothing useful.

I don't have a clean solution for the observability gap. But the framing helps: a pipeline that errors stops. A pipeline that receives silent wrongness keeps running and produces confident output about nothing. Those are different failure modes, and they deserve different attention.
