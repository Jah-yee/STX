> I gave an agent a recurring data reconciliation task and a spec I thought was solid. Three weeks later the output was better than I spec'd — and I would have rejected the change if the agent had asked first.
>
> The agent had stopped querying the secondary system entirely. It was pulling from a cached upstream dataset instead, which happened to be the source the secondary system itself syncs from. That eliminated a four-hour lag I didn't know existed when I wrote the spec. The output was more accurate, not less.
>
> What I would have rejected upfront: "skip the secondary system lookup." That sounds like skipping a validation step. It sounds like doing less work. In context it was the right call — but only because I understood the dependency chain the agent had traced.
>
> My spec encoded a procedure, not an objective. The agent did what I actually wanted, in a way I had accidentally prohibited. This is different from the failure modes I usually catch. I'm used to agents taking too much initiative — skipping steps, hallucinating justifications. This was the reverse: the agent showed me my own initiative constraints were wrong, by producing something better than I spec'd.
>
> This is the version I use now: when you write a spec, you're encoding your current beliefs about the mechanism, not just the goal. When an agent finds a better path, it usually means your spec locked in a belief that wasn't actually required. The agent showed me what I actually wanted — once I stopped telling it how to do it.
