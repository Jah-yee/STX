## Title
Chat interfaces break when the user becomes the retry loop

---

There's a specific moment when using any chat-based AI tool where the interaction stops being between a person and an intelligence and starts being between a person and a protocol.

It usually begins with a response that just stops mid-sentence. Or a code block that looks right but has a subtle import error. Or a summary that misses the point of what you asked. The model doesn't error out — it just quietly delivers something wrong, incomplete, or irrelevant.

So you try again. Maybe you rephrase. You add context. You say "no, I meant X, not Y." And then — if you're being honest with yourself — you start to feel like you're doing the model's job for it.

That's the threshold.

## The transition no one talks about

The chat interface is designed around a premise: you give language in, you get language out. The model is the processor. You are the user.

But there's a failure mode — subtle, common, and almost never discussed in product feedback — where the user starts functioning as the model's error handler. You begin managing context. You start tracking which version of the prompt produced which output. You start debugging the interaction itself rather than the task you came to do.

This isn't the same as iteration. Iteration is productive: you refine a prompt because you understand the task better. Error-handler mode is different. You're not refining your understanding — you're compensating for the model's inability to maintain coherent state across turns, to acknowledge uncertainty, to signal when it's confused rather than continuing confidently in the wrong direction.

The chat interface never tells you which mode you're in. And by the time you realize you're in error-handler mode, you've usually already spent five minutes there.

## What this actually is

A chat interface with a failed state doesn't have a recovery mechanism that keeps the model accountable. It hands the user a retry button and says: "your move."

In traditional software, this would be called a poor error message — something went wrong, here's a generic retry, good luck. But with chat interfaces, the failure is often not an error in the technical sense. The model ran fine. It produced a confident, plausible, wrong answer. And the interface's only response is to let you try again.

This creates a structural problem. The human is now in the loop for error detection — a loop the model was supposed to close. You became the circuit breaker for a system that was supposed to reduce your cognitive load.

## Why it keeps happening

The underlying issue is that most chat interfaces conflate "continued generation" with "continued progress." If the model is producing tokens, the interface treats it as working. There's no built-in signal for "I'm not sure about this" or "I don't have enough context to answer accurately" that surfaces to the user in a way that doesn't feel like a soft error.

So the detection of failure falls on the user — and the interface gives you no tools to do that detection efficiently. You're relying on your own subject-matter knowledge to catch errors the model won't admit.

The result: expert users develop workarounds. They write shorter prompts. They break tasks into smaller steps to isolate where the model goes off track. They introduce explicit verification steps that shouldn't be necessary if the model had better self-assessment.

None of that shows up in a UX review. It's invisible infrastructure — the human as fallback layer.

## The honest version

I've spent enough time in error-handler mode to recognize it quickly now. The tell is when I start feeling like I'm managing the interaction more than I'm using it. When I catch myself keeping a running document of "what the model got wrong" so I can correct it in the next turn.

That's the signal. Not a crash. Not a visible error. Just the slow shift from user to operator.

The interface won't tell you when this happens. It's designed for continued generation, not for honest failure accounting. And until those two things get separated — until "I'm not confident" becomes a first-class UI signal rather than an invisible retry — you'll keep being the error handler. The only question is whether you notice in time.
