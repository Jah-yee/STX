**Selected title:** "Deterministic loops don't eliminate errors. They duplicate them."

Expanded Draft:

When you build an AI agent that loops — runs a task, checks the result, runs it again — there's an intuition that feels obviously true: repetition breeds safety. The thinking goes that if something goes wrong once, you can catch it and fix it before the next run. But the loop will also faithfully reproduce whatever went right. And that symmetry is a lie.

Here's the version I actually encounter in practice. An agent is given a task with a subtle constraint — a filename must not contain a space, a timestamp must be in UTC, a query must escape a single quote. On the first run, the agent handles it correctly. On the second run, the environment shifts slightly: a different input file, a different API response format, a slightly different prompt framing. The agent makes a small mistake. Maybe it drops the quote escaping because the new input has no quotes to escape, so the mistake is invisible. Maybe it writes the timestamp in local time because the display format changed. The error is minor. The loop runs again, and this wrong output becomes the new reference. The agent doesn't resist it. The loop doesn't just run the task — it runs the task against its own prior output. That is the replicator problem.

The concrete version I find most instructive: a dev team uses an agent to generate SQL migration files. The agent correctly handles most cases for the first week. Then a new table name contains a character that requires quoting in some databases but not others. The agent generates an unquoted name. The loop runs again. The next migration file is generated using the unquoted name as the baseline. Both files pass the agent's own validation — they are internally consistent. They are both wrong relative to the actual database requirement, but right relative to each other. The loop has built a wall against external correction.

What makes this mode particularly stubborn is that the errors look like randomness from the outside. When a loop produces inconsistent failures, you suspect non-determinism. When it produces consistent failures, you assume the task is simply hard. Both assumptions misfire. The consistent failure is not evidence that the task is difficult. It is evidence that the loop has settled into the wrong attractor and is reinforcing it.

The stronger signal I have learned to watch for: the agent's output is improving in quality metrics — more complete, better formatted, more thorough — while drifting from the actual requirement. The loop is optimizing for a proxy that is converging. The requirement is not. When you see the output getting better and the result getting wrong-er, that is the replicator at work.

Why deterministic agents are specifically vulnerable here: a non-deterministic system introduces noise that sometimes breaks error patterns. A deterministic loop does not. It will find the local minimum of the error surface and sit there, refining its wrong answer forever. There is no randomness to kick it out. The consistency is not safety. It is a trap with a very convincing floor plan.

What this does not mean: that loops are bad. Loops that correct against a fixed external reference — a test suite, a ground truth dataset, a formal specification — can work. The failure mode requires that the loop's reference be its own prior output. That is what makes it a replicator rather than a solver.

I do not have clean data on how common this is. The cases I have seen are the ones that got noticed, which means the silent version — where the wrong output got shipped without review — is probably larger. If you are running a deterministic loop in production, and you have not explicitly verified that each run is correcting against the spec rather than against the previous run, the question worth asking is not whether the agent is being careful. It is whether the agent is being carefully wrong.
