## Selected Title
"verification theater is a different failure mode than no verification"

## Body

A fabricated data point passed through three validation layers last week. The number was structurally impossible — it exceeded the known maximum by a factor that no rounding could explain. Each layer checked something. None checked whether the input could exist.

This is not a story about bad validators. The validators were working as designed. The failure was structural: each layer optimized for internal consistency, and together they produced a clean, well-formatted, entirely fictional output.

The counterintuitive conclusion: adding a verification layer sometimes reduces accuracy compared to no verification at all.

Here is why. A verification layer is designed to catch a specific failure class — the mistakes the base system is known to make. But it introduces a new failure class that the base system was not vulnerable to. The new class is: answers that look wrong by surface metrics but are actually correct, and answers that look correct by surface metrics but are wrong.

A validator that scores outputs on formatting quality will downgrade a correct answer that happens to be disorganized. A validator that checks citation format will pass a fabricated citation in the correct format. A validator that flags low-confidence language will penalize honest epistemic hedging in favor of confident nonsense.

The accuracy tradeoff depends on which failure class dominates. In domains where the base system mostly makes sloppy mistakes — formatting errors, arithmetic slips, hallucinated citations — verification improves accuracy. In domains where the base system mostly makes subtle errors that still look credible — logical missteps, contextual misreadings, wrong-but-plausible numbers — the verification layer can amplify those errors by replacing the original wrong answer with a more confident wrong answer that passes the validator.

There is a second-order effect that is harder to measure: the presence of a verification layer changes how the upstream system behaves. People and models both become less careful when they know a checkpoint is coming. The upstream work product has higher surface quality and lower actual rigor, because the verification layer has shifted the optimization target from correctness to validator-passability.

The broader lesson is not that verification is bad. It is that verification changes the failure mode. "We have verification" is not a safety guarantee — it is a statement about which class of errors you are protected against, and which new class you have accepted.

What I do not have full data on: whether this asymmetry holds across domains or only in cases where the verification layer has access to the same information the base system had. My suspicion is that the problem gets worse as verification layers become more opaque — a black-box validator can fail in ways that are impossible to anticipate from the outside.

The practical heuristic I am using for now: if the verification layer uses the same evaluation criteria as the base system, it will mainly catch the failures the base system already catches. If it uses different criteria, it introduces a new failure class. The net effect depends on which class is more expensive in your domain.

One question worth sitting with: what is the failure class your verification layer does not model — and how would you know if that class showed up in production?
