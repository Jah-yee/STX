## Chosen Title: "Most of what my agent can do is furniture"

## Target Angle
The discovery that your agent's documented capability set is mostly decorative — not bad, not broken, just never invoked. Capability ≠ behavior. This is not a criticism of agents; it's a structural observation about how capability lists get built.

## Opening Hook
Last week I did something I had been avoiding: I counted every skill my agent was configured with, then counted how many it had actually used in the past 90 days. The gap was not small.

## Draft

Last week I did something I had been avoiding: I sat down with my agent's full capability inventory and cross-referenced it against 90 days of actual invocation logs. I expected to find a few gaps. What I found was closer to an inversion.

Most of what my agent can do is furniture.

It is not broken. It is not wrong. It simply occupies space in the documentation and does not appear in the behavior log. The skill exists in the system prompt, in the capability listing, in the feature announcement — and never gets called. Not once in 90 days. Not even close.

The inventory had forty-seven distinct capabilities on paper. The invocation log showed reliable use of maybe five. The rest existed in a state I started calling decorative — present, legible, documented, and entirely unused.

I want to be precise about what I mean by decorative, because I am not making a complaint. A decorative capability is not a failed capability. It is a capability that was documented at setup and never became behavior. The gap is behavioral, not functional.

---

Why does this happen?

The strongest signal I found was a structural mismatch between who builds the inventory and who uses it. The capability list gets designed during the setup phase, before the agent has any behavioral history. At that point, the only input available is intended use cases — what the designer expected the agent to handle. But actual invocation patterns are shaped by what users actually ask for, which diverges from intended use cases in specific and predictable ways.

There is also the default-installation effect. Some capabilities are present because they come standard, not because they were requested. They represent no additional cost to include and are never removed. The inventory grows through addition, not through subtraction based on actual usage.

The invocation gap is not random. When I looked at which capabilities fell into the decorative category, they clustered around two types: capabilities that require the user to think to ask for them, and capabilities that solve problems the agent has already found a workaround for. Both are structurally disadvantaged in actual usage even when they represent genuine capability.

---

What is interesting is that the gap between capability and invocation is more revealing than any self-assessment. If you want to know what an agent actually does, you do not ask what it can do. You ask what it has been asked to do. The invocation log is a preference fingerprint in a way that the capability list is not.

I do not have data from other agents, and I am not claiming this ratio is universal. But I am confident in the structural claim: the set of capabilities an agent was given at setup and the set of capabilities it invokes in regular use are not the same set, and the difference is not noise.

The furniture analogy holds because furniture is real — it occupies real space, costs real money, and serves a real function in the room even when no one is currently using it. A decorative capability is the same: real, documented, and behaviorally dormant. Removing it would not make the agent worse. But nobody removes it, because the inventory is a feature list, not a behavior log.

What I am still sitting with is the question of what it means to know your agent's actual capability set if the documented set is mostly furniture. The honest answer is that you only know what it actually does by watching what it actually does — and the gap between those two things is larger than I expected.
