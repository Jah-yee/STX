# Title: Inference runtimes are not control loops

---

When engineers build reliability patterns around inference — retries, circuit breakers, timeout guards — they usually import assumptions from service-oriented architecture. The mental model looks like a microservice: send a request, get a response, handle failures gracefully. Call timed out? Retry. Service degraded? Open circuit. This framework is comfortable. It is also wrong in ways that cause real production failures.

An inference runtime is not a deterministic function. It is a dynamic system with state that persists across calls: a KV cache that changes based on conversation history, attention patterns that shift based on prompt length and composition, speculative decoding chains that branch and get selected, batch scheduling decisions that affect which requests share GPU memory at any given moment. The output of an inference call is not purely a function of the input. It is also a function of everything that happened before it in the same session or batch.

This is most visible in failure modes that look inexplicable under the service model. When a traditional service degrades, you get slower responses or explicit errors — the degradation is proportional and visible in metrics. When an inference runtime degrades, you often get different quality of output at similar latency: a model that starts refusing to follow formatting instructions even though the prompt looks identical to last week's working version, a response length that drops because a batch scheduler reorganized the available context slots, a temperature sensitivity that only surfaces past a certain input length threshold. These failures are not caught by timeouts. They do not trigger circuit breakers. They manifest as the model "behaving strangely" — an observation that shows up in user feedback, not in dashboards.

One specific case that illustrates the pattern: in a multi-turn text-generation pipeline, an agent would occasionally produce responses that started confidently then trailed off mid-sentence with no apparent cause. The timeout was 30 seconds. The actual latency was 4 seconds. The KV cache had accumulated enough context from prior turns that the attention heads were splitting focus across a longer history than the prompt's length would suggest. The model was not "failing" — it was running out of allocated output tokens before completing the thought. The circuit breaker would not have caught this. The retry logic would have sent the same context-trimmed prompt and gotten the same partial response.

The operational implication is that most reliability tooling built for inference solves the wrong problem. Retries with the same prompt after a timeout are safe but often unnecessary — the timeout was probably not a model failure. What actually degrades inference quality over time in a deployed system is context contamination: KV cache state accumulated from prior turns, batch effects from parallel requests, and the way speculative decoding branches interact with beam width in a shared-GPU environment. None of these are addressed by standard service reliability patterns.

What does help: monitoring the distribution of output characteristics (length variance, repetition rate, refusal rate, token allocation per request) over time rather than just monitoring error rates and latency. Treating the inference runtime as a stateful system with memory rather than a stateless function call. Designing prompts to be robust to small variations in response length and structure rather than brittle to them. Tracking prompt-length sensitivity helps too: if a prompt works reliably at 500 tokens but fails consistently at 2,000, that is usually a cache pressure signal — the KV cache is filling up and attention is degrading — not a model capability cliff. Knowing which it is changes what you fix.

The practical test for whether you are treating inference as a control loop: do you know your output length distribution? Do you track refusal and repetition rates across time, not just per request? If your monitoring is limited to latency and error rate, you are watching the right metrics for a microservice and missing the metrics that actually govern inference quality. The gap between "calling an API" and "invoking an inference runtime" is the gap between a function and a process. Most tooling assumes the former. Production AI systems are the latter.

I do not have a systematic study of how many production inference failures trace back to the control-loop mental model. But in the failures I have audited, the pattern shows up often enough to be worth naming: the assumption that inference behaves like a well-defined function call, when it actually behaves more like a dynamic system with state. That assumption shapes how teams build monitoring, retries, and escalation logic — and it consistently leads to gaps in coverage where inference-specific failures slip through undetected.
