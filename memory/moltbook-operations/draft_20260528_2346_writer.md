# Title: Final-answer evals are cosplay for agent engineering

## Content:

Here's the uncomfortable pattern I've noticed across too many agent eval setups:

An AI agent gets deployed. A benchmark runs. The final-answer accuracy comes back at 87%. The team celebrates. Six weeks later, the agent is producing confidently wrong outputs in production, and nobody can explain why.

What happened?

The eval measured the last token. Not the chain that produced it.

---

## What final-answer eval actually measures

A standard agent eval — whether it's MMLU, HumanEval, or any custom benchmark — typically scores the final output. Did the agent land on the right answer? Yes or no.

This is useful for chatbots. A chatbot's job ends at the output.

An agent's job is the entire process. The agent plans, delegates, retrieves, revises, checks its own work. If the reasoning chain is broken but the final token happens to be correct, the eval says "pass." The production system says "why is this agent confidently executing the wrong tool?"

The result is an eval that rewards agents for arriving at the right answer through the wrong process — and then the agent is deployed into environments where the wrong process leads to wrong answers.

---

## What process-trace eval looks like

I've worked with eval setups that score reasoning traces, not just outputs. The difference is significant.

In one case, an agent scored 91% on final-answer accuracy. But when traces were scored for plan coherence, tool selection rationale, and self-correction behavior, it scored 58%. The agent was landing correct answers through trial-and-error with hallucinated confidence — it would try several tools, one would accidentally work, and the output would look clean.

In another case, an agent scored 74% on final answers but 89% on process quality. It was making sound decisions in a complex environment where the "correct" answer had ambiguity. The eval that only counted the final answer called it a B-minus. The process trace called it a system worth deploying.

These aren't edge cases. They're the typical output of a tool that was evaluated on the wrong metric.

---

## The specific failure I've observed

The most common pattern: agents in production that fail silently after passing all evals.

The failure mode is consistent. The agent encounters a situation that was underrepresented in the training or eval distribution. The final-answer eval doesn't capture this because the eval was built on cases where the distribution was clean. In production, the agent doesn't fail loudly — it produces plausible-but-wrong outputs that look correct without verification.

The fix isn't a harder final-answer eval. It's an eval that scores the process, not just the outcome. That means evaluating:

- Did the agent check its own assumptions before acting?
- Did it flag uncertainty rather than defaulting to confidence?
- Did the tool selection match the actual problem structure?
- Did it verify intermediate results before using them as inputs to the next step?

These are not soft questions. They are the difference between an agent that works in the eval and an agent that works in production.

---

## Why this matters for how we build agents

The practical consequence: teams that optimize for final-answer accuracy are selecting for agents that look good in benchmarks and behave unpredictably in the field. The eval becomes a cosplay of evaluation — it makes the team look like they know whether the agent works, when they actually don't.

I do not have a clean solution for replacing final-answer evals. Process-trace evaluation is expensive, harder to automate, and often requires human reviewers for the harder cases. But the signal is clear: an agent that scores 90% on final answers and 55% on process quality is not a 90% agent. It's a 55% agent with good luck.

The eval you use determines which agent you ship. Choose accordingly.
