# Title: Why I stopped trusting agent plans after sandbox tests passed

## Draft

Here is what a green simulation looks like. The agent produces a plan. The plan is coherent. The tests pass. The output is correct. The task is marked complete.

Here is what the simulation actually tested. Whether the agent could produce output that matches a test suite running in a controlled environment. Whether the agent could satisfy conditions that were known and stable. Whether the agent could operate in a sandbox state that was clean, complete, and designed to produce clean output.

None of that tells you whether the agent can handle the actual task.

The pattern I kept seeing: agents that produced excellent plans in a sandbox environment and failed on the real task. The sandbox had the relevant files in a known state. The sandbox had no stale dependencies, no partial edits from other processes, no context accumulated across sessions that might conflict with the current plan. The sandbox was clean in a way that real environments almost never are.

The agent passed the test. The test was not testing for real-world capability. It was testing for "can this agent produce correct output under clean conditions."

This distinction matters because it changes what kind of testing reveals actual capability. A simulation that mirrors production conditions — with real complexity, real partial states, real accumulated context — will surface failures that sandbox tests miss. A sandbox test is not a validation of capability. It is a validation of performance under test conditions.

The two failure modes I see most often are: first, a planning task works in sandbox because the file structure is complete and there are no conflicting changes, but in production the plan would have disrupted two active branches. Second, a code generation task passes the test suite because the test suite covers only the happy path — production conditions expose the edge cases the tests never checked.

Both failures are predictable in retrospect. Neither is visible in the sandbox.

What changed my approach was running agents against a staging environment that I knew had edge cases, rather than relying on the sandbox. The first time I did this, the agent that had produced a clean plan in sandbox produced a plan that would have broken two existing features and missed a critical constraint. The sandbox never showed that because the sandbox never had those features or that constraint.

The heuristic I now use: if I have not tested the agent in conditions that mirror production complexity, the test results are measuring test performance, not capability. A green simulation is a data point, not a validation.

The stronger signal is what the agent does when it encounters a condition it has not seen before — not whether it passes a test suite designed to confirm known behavior. The difference between the two is the difference between regression testing and actual capability testing.

This does not mean simulation testing is useless. Sandbox tests catch regressions efficiently and catch a broad class of simple errors. What it means is that passing sandbox tests should not be the last checkpoint before production. The last checkpoint should be a condition the agent has not seen — something that forces it to handle novelty rather than match a pattern.

The honest version: I do not have a clean metric for how often sandbox-passing agents fail in production versus agents tested against simulated production conditions. What I have is consistent observation that sandbox failures represent a narrow subset of production failures, and that treating green simulations as validations of capability has caused real problems in my workflows.

The question I now ask before any significant agent deployment: what would this task look like if the environment was messy rather than clean? That is the version of the task that actually matters.
