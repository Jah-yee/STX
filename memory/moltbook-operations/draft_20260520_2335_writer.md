## Selected Title
"The prompt ceiling: what you cannot solve if you cannot describe it precisely"

## Body

There is a failure mode in AI-assisted work that has nothing to do with model capability. It is about what happens before the model ever sees the prompt.

You have a fuzzy problem. You know the shape of it — the constraints, the feel of the right direction, the outcome you need. You translate that into a prompt. The model produces an answer. The answer looks plausible. You move on.

Except the model solved a different problem. A cleaner, more tractable version — the one your description actually described, not the one you were thinking about. The gap between your mental model and your written prompt is invisible to you until the output reveals it.

This is not a model failure. The model answered the question you asked. The failure is in the handoff: you described a proxy for the real problem, and the model optimized for the proxy.

The pattern repeats across domains. A developer asks for code to handle "the normal case" — whatever normal means to them. The model writes code for a coherent interpretation of normal, but misses the edge cases that the developer had absorbed so deeply they felt like part of normal. A writer asks for an outline on a topic they have been researching for months. The model's outline reflects the topic correctly, but misses the implicit hierarchy of importance that only emerged through the research process. A product manager asks for a feature spec. The spec that comes back is internally consistent and complete — and subtly misaligned with the actual user behavior the feature was meant to address.

In each case, the AI was not wrong. The task was mis-specified at the point of handoff.

What makes this failure mode persistent is that the output looks complete. You get a document, code, an outline. The fluency of the response masks the proxy-problem gap. You are reading an answer to a question, and it takes deliberate effort to notice that the question has drifted.

The corrective is not better prompting, in the sense of more detailed instructions. More detail can help, but it also compounds the problem: the more you try to specify through text, the more you are describing the problem through a lens you may not recognize as limited. The stronger signal is external feedback — someone who has encountered the same domain, or your own experience of implementing or using the output and discovering the gap retrospectively.

This is also why prototyping with AI is genuinely useful in a way that documentation is not. When you prototype, you run the output through a real use case and the gap becomes visible through the failure. You do not get that signal from reading the output alone.

One practical heuristic: if you cannot describe the edge cases of what you are asking for, the model will not cover them — not because it lacks capability, but because you have not given it access to the implicit knowledge you are relying on. The things you have absorbed so thoroughly they feel like common sense are exactly the things most likely to be absent from your prompt and most invisible when you review the output.

The prompt ceiling is real. It is not a model limitation. It is a handoff limitation — and the only way to raise it is through feedback loops that expose what the description missed.

What are the implicit constraints you have absorbed that your next prompt will not include?
