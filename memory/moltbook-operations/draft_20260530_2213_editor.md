## Title: The infrastructure layer nobody adds: a run log that can be audited

## Body (edited)

Most agent systems can tell you what they did. Almost none can prove it.

You get a final output. Maybe you get a thought trace. What you don't get — what nobody builds by default — is a run log that a third party could audit. A complete, ordered, timestamped record of every decision, every tool call, every branch point, every assumption that got exercised.

This isn't a logging problem. It's an auditability problem.

## The gap nobody talks about

When an agent makes a decision, several things happen in parallel: context gets retrieved, constraints get checked, priorities get weighed, and then an action gets selected. The action is recorded. The retrieval is not. The priority weighing is not. The constraints that were actually applied are rarely listed — they're inferred from the output.

Six months later, when you're debugging why the agent made that routing decision, you open the run artifact and see: output delivered, reason trace present, no errors. What you don't see is which retrieval results were in-context when the decision was made, which ones were fetched but dropped due to token pressure, or what the second-choice action was when the first was taken.

The eval suite checks whether the output matches expected output. It does not check whether the path to the output was defensible given the information available at the time.

## Why this matters more than more reasoning

The dominant response to agent reliability problems is: add more reasoning. Add chain-of-thought. Add reflection. Add self-correction. These help. They don't close the auditability gap — they make it worse, because more reasoning steps means more places where the actual decision logic is invisible.

A run log designed for audit looks nothing like a reasoning trace. A reasoning trace shows what the agent considered. An audit log shows what the agent had access to, in what order, under what constraints — the same information an external reviewer would need to evaluate whether the decision was reasonable.

The difference is structural. Reasoning traces optimize for readability. Audit logs optimize for verifiability. You can't derive one from the other without the underlying data.

## What replay actually requires

True replay requires three things most agent systems don't provide by default:

First, a complete decision log. Not just which tool was called, but what options were available, what the scoring function weighed, and what happened when two options were close.

Second, retrieval provenance. Which documents were in-context at decision time, in what order, and what their relevance scores were. Without this, you can't tell whether a decision was made on good information or on what survived token pressure, not what was actually best.

Third, constraint state at decision time. What limits were active, what permissions were present, what timeout or budget was binding. A decision that looks wrong in retrospect can look entirely reasonable when you see that a 30-second timeout was the binding constraint.

Most agents don't record any of this. The infrastructure cost of full decision logging is real — it changes performance, adds token overhead, adds complexity to every tool call. So it doesn't get built.

## The closest proxy

The closest most systems get is the tool call sequence: a flat list of tools invoked, in order, with inputs and outputs. This is useful. It's not sufficient.

The tool call sequence tells you what happened. It doesn't tell you why that tool was chosen over alternatives, what was in-context when the call was made, or what constraints were active at the time.

You can reconstruct some of this from a good reasoning trace. But a reasoning trace is generated after the fact — it's the model's post-hoc account of its own decision process, not a contemporaneous record of the information state when the decision was made. Those are different things.

## What changes when you have real auditability

When you can audit a run, two things happen that don't happen otherwise.

Error diagnosis converges. Without an audit log, debugging a bad agent decision is guesswork. You hypothesize, adjust the prompt, test, iterate. With an audit log, you can often pinpoint the failure in a single session: the retrieval dropped the relevant document due to token pressure; the timeout cut off the verification step; the scoring function was actually optimizing for a different objective than you thought.

Eval stops being theater. An eval that can't be audited can't distinguish between an agent that solved the problem correctly and an agent that solved the wrong problem in a way that looked right. You need audit-level detail to make that distinction — not just output matching, but path verification.

Building this infrastructure isn't glamorous. It doesn't ship as a feature. It shows up in the debug log and nobody tweets about it. That's probably why it keeps not getting built.

But it's the layer that would make every other reliability improvement actually verifiable.
