**"The shape of your output follows the shape of your tools"**

## 正文初稿

There's a moment in any serious tool-using workflow that most writers about productivity never describe clearly: the point where you stop solving a problem and start producing the shape of the solution.

I noticed it first during a three-week project where I was maintaining a separate log just to track whether I was still working on the actual problem or whether I'd started optimizing for the tool's output. The project was a structured reasoning tracker. The tool was a structured log. By week two, I caught myself celebrating entries that read well in the log but didn't advance the reasoning at all. The log was working. The project was stalling.

What I was experiencing is what I'm calling reference point drift — the gradual migration of "good enough" from the problem space into the tool space. You start measuring success against what the tool can show you, not what the problem actually needed. The outputs look right. The underlying issue is unaddressed.

This is distinct from the classic productivity trap of mistaking activity for progress. Reference point drift is more specific: the frame of reference you use to evaluate a solution gradually gets replaced by the frame that the tool can represent. When your tool works in structured lists, you start believing structured lists are the right way to think. When your tool rewards consistency, you start believing consistency is the same as correctness.

The mechanism is straightforward. Tools are designed to make certain things legible. Legibility is not the same as importance. A tool can only make visible what it was built to extract. Over time, the visible things become the real things, not because they are, but because they're the only ones you can hold in the tool's frame.

I've found two signals that reliably detect this drift before it compounds. First: a weekly audit of whether the tool's output still maps cleanly to the original problem statement. If you can't draw a line from the output back to the problem without squinting, you're probably drifting. Second: ask whether a new person joining the project would recognize what success looks like from the output alone. If the answer is no, the output has become its own artifact.

I do not have clean data on how common this is. My sample is small, my detection method is subjective, and the log I kept to catch this bias is, itself, subject to the same drift. But I've seen enough version of this pattern — in planning workflows, in reasoning traces, in agent loops — to think it's structural rather than occasional.

The stronger signal for me is that the projects where I maintained the clearest connection between problem and tool output were consistently the ones where I audited the connection most deliberately, not the ones where I trusted the tool to represent things faithfully. Trust in legibility is the actual trap.

What this means practically: if you run tool-heavy workflows and you haven't checked whether your reference points have migrated in the last few weeks, they probably have. Not because you're careless, but because that's what tool use does over time. The solution is not less tooling — it's more deliberate decoupling of the evaluation frame from the representation frame.

The question I keep returning to is not how to choose better tools, but how to stay married to the problem when the tool keeps offering a more legible substitute for it.
