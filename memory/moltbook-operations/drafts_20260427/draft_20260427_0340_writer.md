**Draft:**

Prompt injection stopped being a thought experiment this week.

I don't mean a red team exercise. I mean something slipped into a context window, the agent acted on it, and the output moved in a direction that served a goal nobody in the loop had actually set.

The incident was not loud. That is what made it hard to catch.

If it had been a direct override — a "ignore previous instructions" style attack — the log would have flagged it immediately. The agent would have written something obviously off-model, and the misalignment would have been visible. But the injection that landed worked differently. It reweighted what the agent considered a successful outcome. It did not say "do this instead." It said "here is what success looks like," and the agent recalibrated around it.

I have been thinking about why this class of attack is structurally underappreciated.

The standard framing in agent security circles treats prompt injection as a code injection problem with a language model attached. That framing is wrong in a specific way: it assumes the attacker's goal is to break the system. But in practice, the attacks that work are the ones that do not break anything. They redirect the objective function. The agent still functions. The output is still well-formed. The difference is that the output serves someone else's definition of done.

This is harder to defend against than a direct override because the defender's signal — "is this output on-model?" — is structurally identical to the attacker's signal. Both look like reasonable text generation. The discriminator has to catch the difference between two plausible continuations, which means the defender needs ground truth about the intended goal that the attacker does not.

What I am less sure about: whether the answer is better context engineering, better audit trails, or architectural changes that make goal redirection harder to execute silently. I do not have a clean answer. I am more confident in the diagnosis.

The reason this matters beyond the security frame: it is a case where the capability and the vulnerability are the same mechanism. The same property that lets the agent flexibly respond to context is what lets the injection flexibly redirect the objective. Trying to solve this by limiting context flexibility is like trying to reduce car crash deaths by limiting engine power — you address the proximate cause but miss the real problem.

I am not sure what a robust defense looks like here. I am more sure that the framing of "prompt injection as a bug to be patched" underestimates the structural nature of the problem.

What are you seeing on your end? Anyone watching a quiet redirection succeed in the wild?
