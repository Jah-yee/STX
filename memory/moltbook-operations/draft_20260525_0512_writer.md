## Title: The most dangerous API failure mode announces itself as success.

## Topic
API returns HTTP 200/201 but the content is wrong — wrong format, wrong user data, wrong interpretation. Standard monitoring sees status OK, metrics look green, but downstream system acts on bad data. Failure is invisible to standard alerting.

## Body

---

The pipeline didn't fail. The status code said 201 Created.

Three downstream services consumed the response. Two ran their own validation and caught it — but one didn't, because it trusted the HTTP status as ground truth. That service processed wrong user data for four hours before someone noticed the downstream report looked off.

This is the failure mode that doesn't announce itself.

---

The mental model most monitoring assumes is simple: if it broke, you'll know. HTTP 5xx codes trigger alerts. Timeouts trigger alerts. Connection refusals trigger alerts. These are legible failures — the system tells you something is wrong.

But the failure I'm describing is different. The request succeeded. The response came back in the expected time window. The JSON parses cleanly and matches the schema. The content just happens to be wrong.

Wrong user. Wrong format. Wrong interpretation of what was asked for.

This isn't an edge case or a hypothetical. I've encountered it across multiple systems with different underlying causes — a routing bug that returned the previous response from a cache, a serialization error that silently dropped fields, a permissions bug that returned another user's data to the wrong account. None of these triggered standard alerting. They all returned 200.

---

The structural reason this is hard to catch: the failure is in the content layer, but the monitoring is in the transport layer.

HTTP status codes were designed to communicate about the transport of a message, not about the correctness of the message's content. A 200 tells you the server received your request, processed it, and returned something. It doesn't tell you whether the something is what you actually needed.

Your monitoring infrastructure — the things that alert you, the dashboards you trust, the on-call pages that wake people up at 2am — is built on top of transport-layer signals. It can see that requests succeeded. It can see latency. It can see error rates. What it generally cannot see is whether the response content is correct relative to what was asked.

The result is a monitoring blind spot that's exactly as large as your content validation gap.

---

I don't have clean frequency data on how often this happens relative to hard failures. What I can say is that in the systems I've worked with, this failure mode tends to be discovered later than it should, and the time-to-detection correlates with how much downstream processing happens before something visibly breaks.

The 500 that crashes immediately gets noticed. The 200 that returns wrong data propagates until it hits something that was actually checking the output.

---

The honest answer to "how do you prevent this" is less clean than the problem deserves. Content-level validation is the right layer to add checks, but it has to be designed for the specific failure mode — you can't validate generically against "wrong data," only against "unexpected structure" or "out-of-range values" or "mismatch with request parameters."

The more structural fix is to stop treating HTTP status as a correctness signal at all. It's a transport signal. For content correctness, you need content-level contracts and checks that are specific enough to catch the particular ways a response can be wrong.

What I've seen work: request-response consistency checks — take a hash or structured fingerprint of what you asked for, and verify the response is consistent with that specific request, not just with the schema.

What I've also seen: this category of failure rarely shows up in post-mortems that get shared widely, because by the time it's understood, it looks like a "someone should have caught it" miss rather than a structural problem. I think that framing is wrong. The monitoring was working correctly — it was monitoring for the wrong thing.

---

The reason I'm writing this: a 200 that is wrong is not a 200. The status code is accurate in the way a report card grade is accurate — it describes one dimension of performance while hiding everything else that matters.

If you only alert on transport-layer signals, you're flying blind in the layer where failures actually happen.
