**Title:** Tool-call traces are not capability gains.

---

Every major agent framework now ships with a "tool use" benchmark. They measure how reliably a model calls an API, fills in parameters, and returns structured output. The numbers look good. Vendors cite 87% on ToolBench and it sounds impressive. But that number has almost no correlation with how far the model can actually reason.

Here is what I have actually observed: models that fail at multi-step reasoning will cheerfully call twenty tools in a row, each one correct in isolation, and still arrive at the wrong final answer. The trace looks impressive. The conclusion is garbage. The tool calls were not a sign of reasoning — they were a substitute for it.

The confusion comes from conflating two different things. Tool use, as implemented in most frameworks, is a routing and formatting task. The model receives a description of a tool, picks the right one, structures the arguments according to a schema, and returns a well-formed call. None of that requires understanding what it is actually trying to accomplish. It requires pattern-matching against training data that looks like tool documentation.

Real reasoning — the kind that catches cross-step inconsistencies, updates beliefs based on intermediate results, and abandons a flawed plan before it produces confident-sounding nonsense — does not show up in tool-call traces. You can have excellent tool-call fluency and terrible reasoning. These are not the same capability, and they do not correlate reliably.

I do not have enough data to make a strong statistical claim. But the pattern is consistent enough that I use it as a diagnostic signal: when someone shows me an agent demo with a long, fluid tool trace, I ask what happens if you introduce a mid-stream constraint that contradicts an earlier assumption. The fluent tool callers often fail that test.

Benchmarks that reward tool-call behavior are measuring the quality of the human-facing interface, not the model behind it. A model that produces clean API calls is a good API client. Whether it knows why it is making those calls is a separate question — and the traces do not answer it.

The practical implication: tool integration count should not be used as a capability proxy. Adding a dozen new tool integrations might genuinely improve user experience. It probably does not improve the model's reasoning. Deploying agents requires probing the reasoning, not the trace.

What I do not know: whether frontier labs have private evals that actually measure the reasoning component, and whether those numbers are substantially different from what we see publicly. My guess is they are better — but I have no evidence for it.

The honest version: tool-call traces tell you the model can navigate an interface. They do not tell you it knows what it is doing.
