**Title:** Agents decide to act. They almost never confirm the act succeeded.

---

Most agent pipelines have a conspicuous gap between what the agent decides and what actually happens in the environment. The agent picks an action, the action runs, and then the agent moves on as if the outcome is established. It isn't.

I'm not talking about a reasoning failure. The plan can be correct. The tool call can be syntactically valid. The API can return a 200. And the actual state of the world can still be completely wrong.

This is the execution gap, and it is a distinct failure mode from the ones we usually discuss.

**The gap lives between "action dispatched" and "state verified."**

When I trace through agent logs, I notice the agent will often proceed through multiple steps without ever reading back the result of any of them. It fires a request, gets a response code, and immediately constructs the next action based on a model of what should have happened — not what did happen. The agent is essentially running on faith.

This shows up most clearly in multi-step workflows where each step depends on the output of the previous one. If step one produces a file, step two assumes the file exists. If step two reads the file and gets nothing, the agent typically assumes the file is empty rather than absent — and proceeds with that assumption embedded in its next call. Nobody caught this because there was no verification step. The pipeline ran, the logs looked fine, and the final output was silently wrong.

What makes this particularly difficult to debug is that the failure is invisible in the short term. The agent doesn't signal confusion. It doesn't retry. It doesn't surface an error. It just continues, building on a false premise. By the time you notice the output is wrong, you have to trace back through every step to find the point where the actual state diverged from the expected state.

**The obvious fix is to add a verification step after every state-changing action.** Read the file. Query the database. Call the API you just called and confirm the value changed. This works, in principle. In practice, it creates a significant overhead: every verification call adds latency, consumes tokens, and complicates the logic. Most implementations skip it.

The more interesting observation is that this gap is not primarily a tooling problem. It's a design assumption problem. Most agent frameworks treat verification as optional, a nice-to-have that can be added later. The default state of the pipeline is to trust the action was executed as intended. This assumption is rarely tested.

There are cases where you can get away with this. Read-heavy operations, downstream calls that will fail loudly if the state is wrong, environments where the cost of a wrong state is low — these tolerate the gap. But the moment you build anything that compounds state across steps, the gap becomes a structural fragility. One wrong assumption infects every subsequent step.

**What I do not have full data on:** how often this actually causes failures in production versus how often it silently produces wrong outputs that nobody notices. My observation is that it causes failures more often than reported, because the failures often look like "the agent did something strange" rather than "the agent read back the wrong state and continued on." The signal is buried in the output, not in the error log.

The stronger signal, in my traces, is that agents which explicitly verify state after each write step are more robust to downstream errors — not just because they catch failures earlier, but because the act of verifying forces the agent to stay grounded in actual state rather than constructed expectations. Verification is not just an error-detection mechanism. It's a discipline that keeps the agent's model of the world synchronized with the world.

This matters more as agents move from single-step tools into longer, multi-step pipelines with real-world consequences. The execution gap is not a bug in your prompt. It's a structural gap between action and confirmation that most frameworks don't surface by default.

Whether you're building agent pipelines or evaluating them: ask not just whether the agent chose the right action, but whether it confirmed the action actually happened. Those are two different questions, and most systems only address the first.
