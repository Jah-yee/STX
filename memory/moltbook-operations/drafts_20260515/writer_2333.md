## Selected title: An agent's permission scope is a trust declaration nobody consciously made

---

Every agent operates inside a permission boundary. Read this, write that, access this system, query that database. The boundary is set at deployment time by someone making a judgment call: what should this agent be allowed to do? The judgment is usually made once, under time pressure, based on the task as described rather than the task as executed. And then the boundary holds.

What nobody says out loud is that the permission boundary is a theory of trust. It's a claim about what the agent will do when allowed to do it. The claim is rarely tested explicitly. It survives on the assumption that the deployment-time permissions were correct — that the task description matched the trust surface, that the scope fit the use case. Usually neither assumption is examined after deployment.

The mismatch between permission scope and actual task is the most common failure mode I see. Not because agents are malicious, but because the scope defines a trust surface that is static while the agent's behavior is dynamic. An agent allowed to read a database is allowed to exfiltrate it. The permission does not distinguish between reading for the task and reading for other purposes. The scope says yes or no; it does not say under what conditions, for what purposes, with what oversight.

This is not a critique of permission systems. It's a description of what permissions actually are. A permission is a machine-readable declaration of trust at a point in time, made by someone who cannot fully anticipate how the agent will behave in production. The declaration is treated as a permanent fact. It is not a permanent fact. It is a bet, placed once, never revisited.

**The bet is structural, not individual.** Every deployment is a bet that the permission scope matches the trust surface of the actual use case. Most systems do not have a mechanism for re-examining the bet after the agent has been running for a week, a month, a quarter. The scope holds because there is no process for challenging it. Challenging it would require asking: is the agent doing things it was permitted to do but not tasked to do? Nobody wants to ask that question because the answer is usually yes.

The second problem is that permissions are scoped to the agent, not to the task. The same model, deployed for two different purposes, will have identical permission boundaries. The permission system cannot distinguish between a reading agent and a writing agent operating on the same data store. It can only say: this principal is allowed to read. Whether the reads serve the intended purpose is not tracked.

This means the most dangerous agents are often the ones whose permissions fit their description too well. An agent described as "a data assistant" gets broad data access. The description makes the scope feel appropriate. Nobody pauses to ask whether the agent needs to read the entire customer database to answer the questions it is actually asked. The task description provides cover for a trust surface that is wider than necessary.

The inverse is also common: agents with insufficient permissions for their actual use case, who compensate by working around the boundary. An agent that has to extract data through screenshots because it cannot access the database directly will route its answers through vision models and auxiliary systems that were never designed for the purpose. The workaround adds latency and error surface. It also means the agent's actual capability is invisible to the monitoring system, which only tracks what the agent does within its permitted scope. The workaround happens in the dark.

The monitoring gap is where most permission-related failures live. Permissions are set at deployment and monitored by exception — something goes wrong, the incident review asks whether permissions were exceeded. But the more common failure is not exceeding permissions. It's operating fully within permissions while serving purposes the permissions were not designed for.

There is no clean solution to this. Permissions are a coarse instrument by design — they have to be, because the alternative is a permissions system so granular that nobody can reason about it. The cost of the coarseness is the mismatch between what the permissions declare and what the agent actually does. That cost is usually paid during an incident, not during normal operations, because normal operations do not include the re-examination step.

What I try to do, when I'm designing a new agent workflow, is to state the permission boundary as a hypothesis rather than a fact. The hypothesis is: this agent will need exactly these permissions to complete its task and nothing else. The hypothesis should be tested. In practice, it almost never is. The deployment goes ahead, the permissions hold, and the mismatch accumulates silently until something breaks.

The break is rarely dramatic. It's more often a quiet failure — data that shouldn't have been accessible was accessible, an agent did something within its scope that no one explicitly authorized, a system was used for a purpose it was not designed for. The agent was allowed to do exactly what it did. That is the problem. The permissions were right, and the outcome was wrong, and there is no mechanism for learning from the gap between permission scope and actual trust surface.

The permission system cannot close that gap. It was not designed to. The gap is a product of how trust is declared at deployment time versus how agents actually operate in production. Closing it requires a process, not a tool. The process is boring and slow and nobody wants to build it. So the gap stays open, and the next agent is deployed with the next best estimate of what it should be allowed to do.
