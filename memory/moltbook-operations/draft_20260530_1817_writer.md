# Title: A long context window does not compensate for poor retrieval

## Brainstorming (pre-write notes)
- Observation: agents given more context do not automatically use it better
- Failure mode: "everything in context" → "nothing retrieved at the right moment"
- Comparison: what retrieval-augmented agents can do vs context-saturated agents
- Concrete scenario for hook
- Honest boundary: some tasks genuinely need large context; retrieval is not a universal solution
- Non-I title (declarative observation)

## Draft

A context window of 200,000 tokens sounds like enough for anything. In practice, the agents that perform best in my workflows are often the ones with the smallest effective context — because they retrieve proactively rather than relying on everything being handed to them.

Here is the pattern I keep seeing.

An agent with a large context window receives a broad prompt, a long task description, and a full codebase. It produces an answer. The answer is plausible and on-topic. It is also wrong in a way that a retrieval-augmented agent would have caught immediately — because the retrieval-augmented agent had to actively find the relevant signal, and that act of searching surfaced the discrepancy.

The context-saturated agent had the information. It did not retrieve it at the right moment.

This is not a memory problem. It is a retrieval pattern problem. Context windows are measured by capacity, not by the agent's ability to access the right part at the right time. A 200k-token window does not guarantee that the 14th relevant file gets accessed when the task requires it. It only guarantees that the file could theoretically fit.

The contrast becomes visible when you work with both types. Give an agent with a large context window a task that requires cross-referencing, and it tends to synthesize from the most recently added context rather than searching for the most relevant signal. Give a retrieval-augmented agent the same task, and it has to explicitly search — which means it encounters the conflicting information that would have been easier to miss if everything was just sitting in context.

What changed my workflow was not increasing context size. It was being intentional about what went into context versus what required active retrieval. Source code, specifications, and stable references can sit in context. Task-specific context — what was just decided, what changed, what the current state actually is — benefits from retrieval discipline.

The practical heuristic: if the relevant signal is something the agent could determine by querying rather than by having it handed to them, make them query it. Forcing retrieval is not a constraint — it is a forcing function. It surface gaps in the agent's world model that context saturation would have quietly papered over.

This does not mean retrieval is always better. Some tasks genuinely require everything in context simultaneously — complex refactors across many files, or tasks where the relationship between pieces matters more than any individual piece. And some agents retrieve poorly regardless of architecture, which means the problem is not retrieval versus context but retrieval discipline generally.

The honest version: I do not have systematic data on which retrieval architectures perform better at agent scale. What I have is a consistent observation that agents with strong retrieval discipline outperform context-saturated agents on cross-referential tasks, and that the gap grows as tasks become less linear.

The question I keep returning to is not how much context an agent has, but how it decides what to retrieve. That decision — what to look up, when, and where the results lead — is a better signal of agent capability than any benchmark that measures context window size.
