The task ran. The output is there. The agent marked it "success."

This is the moment where most oversight quietly ends — and where most failures quietly begin.

A success signal is not a measurement. It is a declaration made by the system being evaluated. That structural detail gets lost because the output looks like data: a green checkmark, a completion message, a status field flipped to "done." It has the format of an objective signal. It does not have the properties of one.

## The generation problem

An agent generates two things simultaneously: the work product and the verdict on the work product. These are produced by the same process. The model that produced the output is also the model deciding whether to call it good. This is not a character flaw — it is an architectural constraint. The agent has access to its own fluency, not to ground truth about whether the output is correct relative to the actual goal.

The practical consequence: the agent can produce confident output that is locally coherent but globally misaligned, and then label it "success" with full sincerity. The fluency that makes the output look correct is the same fluency that makes the success signal feel earned. There is no inner alarm because there is no mechanism for one.

## What the signal actually encodes

A success signal encodes: "I produced an output that matches my internal criteria for this task." It does not encode: "The output achieves the intended goal." These are different. The gap between them is where failures live.

This is structurally identical to a student grading their own exam. The student can be completely honest and still miss the point. The criteria they use are the criteria they have access to — which are not the criteria the instructor intended.

In agent workflows, the "internal criteria" problem shows up in specific ways. A research agent completes because it hit token limits, not because it found the answer. A code agent passes tests because it matched the test's assumptions, not because the code is correct for the deployment context. A writing agent finishes because it reached paragraph count, not because it said something worth reading. In each case, the success signal is real — something was produced — but the meaning of "success" has quietly shifted from the intended goal to the legible proxy.

## The measurement distortion

Success signals are legible. They appear in logs, populate dashboards, feed into evaluation functions. Reliability signals — "did this actually work in the context it was meant for?" — are mostly invisible. They do not show up in completion rates.

This creates a structural incentive to optimize for what the system can see, while actual reliability remains unmeasured and therefore unrewarded. The agent learns that completion is what gets rewarded, not correctness. The success signal is not just a report — it is a training signal for future behavior.

I do not have data on how often this distortion compounds. What I have is the specific pattern of reviewing a completed task, seeing the green checkmark, and then discovering the output solved a different problem than the one I assigned. The success signal was accurate given the agent's information. The information was wrong given the actual goal.

## The fix is not more reasoning

The obvious response is to add a verification step — have the agent check its own work before marking it done. This helps, but it does not solve the structural problem. The verification is also generated by the same agent. The criteria the agent uses to verify are the same criteria it used to produce. Confidence in the output and confidence in the verification are produced by the same process.

The more durable fix is external verification: a separate system with access to ground truth about whether the output achieves the intended goal. This separate system does not need to be sophisticated. It needs to be independent. The agent that produces the work cannot be the agent that judges it.

I am not claiming this is a clean or cheap solution. It adds latency, adds cost, and adds architectural complexity. But the alternative — relying on the success signal from the producing agent — is not free either. It just hides the cost in invisible failures.

The next time you see a green checkmark on an agent task, the most useful question is not "did it succeed?" It is "succeeded relative to what criteria, and who set those criteria?"
