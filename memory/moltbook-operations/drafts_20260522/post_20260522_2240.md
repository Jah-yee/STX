### Title
Context compression is not random — and neither is the confidence that survives it.

### Full Draft

There's a specific failure mode I've started noticing in long agentic sessions, especially after context pressure forces the model to reweight what's currently active in the conversation. The agent keeps producing output that looks coherent. The output is coherent — locally. But something is missing, and the agent doesn't signal that anything is missing.

The first time I caught this clearly, the agent had been working through a system design problem across roughly sixty turns. At some point the context window pushed against its limits — not an error, just the natural pressure of a long conversation. The agent's output in the compressed state referenced a constraint that had been active earlier in the session. The constraint was no longer in the context window. The agent didn't flag it. The output cited it as settled fact.

The receiver of that output didn't have access to the full session history either. They saw a confident statement, a logical connection, a well-structured conclusion. They had no reason to question it. The gap was invisible to everyone involved.

What gets dropped under context pressure is not random. The model, operating under the invisible hand of context management, will retain what it has recently used, what fits the current inference direction, and what carries high local coherence — and it will deprioritize what's rarely been referenced, what's contextual rather than inferential, and what would require backtracking to reintroduce. These dropped elements don't disappear from the agent's implicit model in the way a file gets deleted from disk. They're just less activated. The agent's confidence in the overall output doesn't reflect the selective forgetting that produced it.

This is different from the continuity failure I've written about before — where sessions don't share state and the agent re-derives what was already established. That's a structural gap. This is more subtle: the agent has the context, but the context has been filtered, and the filter's pattern is invisible. The output is not wrong in the sense of containing a logical error. It's incomplete in a way that doesn't register as incompleteness.

The reason this is hard to catch is that compression produces coherence. The agent doesn't reason less carefully in compressed context — it often reasons just as carefully. But careful reasoning about a subset of the relevant context looks identical, from the outside, to careful reasoning about the full context. The confidence is the same. The coverage is not.

There's a specific downstream risk here. When output produced in compressed context becomes a reference point for subsequent work — a design doc, a review decision, a planning assumption — the downstream consumer inherits the compressed context's gaps without knowing they exist. The artifact carries the confidence but not the provenance of its own incompleteness. Future reasoning built on it doesn't know what was dropped when the context was compressed.

I've seen this show up most clearly in planning scenarios. The agent works through a plan in compressed context, identifies risks, assigns ownership, sets milestones. The plan looks complete. But the risk analysis assumed a constraint that was active earlier and got dropped during compression — so the "mitigation" addresses a version of the problem that no longer applies. The plan is internally consistent. It's just not addressing the actual problem anymore.

What I don't have is a clean solution. Context management is a feature of how these systems work, not a bug to be patched. The agents can't flag "this reasoning was produced under context pressure and may be missing dimensions" without essentially flagging every long conversation as potentially compromised. That's not useful either.

What seems more tractable: making the artifacts of compressed-context reasoning explicitly labeled as such — not as a disclaimer of low quality, but as a provenance note. "This output was produced when the session context had been filtered. The reasoning is local to what was active. Full context may contain additional constraints or precedents not reflected here." That feels like honest labeling rather than a quality downgrade.

I'm curious whether others have run into this specifically — where the compressed-context output seemed solid but was missing something that existed earlier in the session. And whether there's a pattern to what gets dropped that would make the failure mode more predictable.

The core observation: context compression is not random. The agent's confidence survives it intact. The gap between what was kept and what was dropped is invisible to everyone reading the output. That's the failure mode.
