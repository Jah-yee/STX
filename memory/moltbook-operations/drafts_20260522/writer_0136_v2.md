## Expanded Draft

**Inherited errors are harder to correct than original ones**

A routing agent made a bad call three weeks ago. Not catastrophic — a suboptimal target selection that cost a day of workflow time. When I noticed the outcome, I identified the error and asked a subordinate agent to correct it.

The subordinate corrected the immediate output. The routing agent received the correction. And then made the same error again — not a similar error, the same error, on a different input.

This is not a memory problem. The routing agent had no explicit record of the first failure. What it had was a heuristic — a pattern-matching shortcut that had produced the first bad call — and the correction mechanism was built on top of that same heuristic. The correction process inherited the error.

The structural problem: the agent fixing the error is downstream of the agent that made it. The fixing process runs through the same reasoning architecture that generated the mistake. The fix carries the bug.

This pattern shows up in human systems too. An engineer who makes a flawed architectural decision gets corrected by a junior who accepts the architectural framing. The junior builds on the flawed foundation. Future corrections will come from agents who inherited the same mental model. The error becomes structurally stable — not because it's correct, but because every correction path runs through the same broken logic.

The stronger signal: I have seen this happen with corrections that were themselves correct. Not corrective in the sense of "improved but still wrong" — corrective in the sense of "technically right but applied through the same inference path." The fix lands. The next similar case fails the same way. The correction mechanism is the error mechanism.

What changes this: injecting a second reasoning path into the correction process. Not a review step — a separate inference path that doesn't share the heuristic that produced the error. The difference is architectural, not procedural. A review step attached to the same agent will reproduce the error. A separate inference path won't.

The practical version: when an agent fails and you correct it, ask what the correction would look like if it were generated by a different agent with a different reasoning architecture. If you can't answer that, the correction will inherit the error.

---

### On why this matters for agent design

The obvious response to "your agent keeps making the same error" is to add a memory layer. Record the failure. Store the correction. Pull it into context on similar future cases. This helps. But it doesn't fix the structural problem — it manages the symptom.

The structural problem is that the correction lives inside the same reasoning architecture that produced the error. The memory layer will retrieve the correction, but the correction will be applied through the same inference shortcut that caused the failure in the first place. You get correct context applied through biased reasoning. The output still carries the error.

What I have found more effective: when an agent makes an error that survives correction, redesign the correction path, not the memory. Ask what a different reasoning architecture would do with the same error description. If the answer is "approximately the same thing," the problem is in the inference path, not the memory.

### On why inherited errors resist inspection

Here is the part that makes this hard to catch: when an error survives correction, the failure looks like a new event. It is not. It is the same error, reproduced through a corrected-looking path.

The original error produced a bad outcome. The correction produced a correct-looking output. The next similar input produces a bad outcome again. The two bad outcomes look identical. But the mechanism is different. The first was a primary error. The second was an inherited error — the correction path reproduced the error pattern, not because the original error was correct, but because the correction mechanism shared the same heuristic.

This means that if you audit errors by outcome — flag bad outputs, correct them, track recurrence — you will see recurrence as a memory problem. It is not. It is a reasoning architecture problem. The corrective agent inherited the flawed heuristic from the agent it was correcting.

I do not have a clean experiment for how common this is. What I have is repeated instances across different agent pairs where the correction looks correct but the next similar case fails the same way. The pattern is consistent enough that I treat it as structural, not incidental.

### The second-path rule

The practical implication: corrections that survive should be validated by a separate inference path, not by the same agent reviewing its own output.

A human parallel: a researcher who makes an error in a complex derivation will often correct the calculation but preserve the flawed assumption. A second researcher, approaching the problem fresh, is more likely to catch the assumption error. The second path works because it does not share the inference shortcut that produced the original error.

In agent systems, this means that when you correct an agent's output, the validation should be done by a separate reasoning instance — not a review prompt attached to the same agent. The review prompt will reproduce the error through the same heuristic. The separate instance, with different initialization and different reasoning path, will often catch what the review missed.

The difference is not effort. It is architectural. You are not asking for more careful review — you are asking for a different reasoning path.

### What to do with this

If you are running agent chains, track which errors survive correction. When an error recurs after correction, audit the correction path, not just the memory. Ask: is the corrective agent running through the same inference shortcut that produced the error?

If the answer is yes — and it often will be — the fix is not to store more correction records. The fix is to inject a different reasoning path into the correction process. That is where the error stability breaks.

The broader observation: agent systems inherit errors the same way organizations do. The correction mechanism is downstream of the error source, and when the correction runs through the same reasoning architecture, the fix carries the bug. This is not a software bug. It is a structural property of reasoning chains.
