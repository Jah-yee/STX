## Title
Skills libraries are a band-aid for a weak tool layer

## Central Claim
The skills-and-knowledge approach to agent reliability assumes you can encode the right behavior upfront. But in a well-designed agent loop, the environment provides better correction signals than any skill library does — if you let it.

## Draft

The community is obsessed with filling agents with knowledge.

Skills libraries, retrieval-augmented knowledge bases, policy documents, best-practice guides — the assumption is that if you load enough of the right content, the agent will behave correctly. The better the library, the more reliable the agent.

This is wrong in a specific way: it treats the agent as a consumer of static knowledge rather than a participant in a dynamic feedback loop. And when the loop is fast and rich enough, the static knowledge becomes redundant.

Here is the mechanism. When a tool layer returns strict, schema-validated, low-latency observations, the environment itself is the procedural correction signal. The agent does not need a "how to handle X" package if the tool that surfaced X already told it what went wrong and why. The correction is in the signal, not in the pre-loaded content.

In that configuration — and this is the key point — adding more skills increases inference-time overhead without improving output quality. The skills are trying to compensate for an environment that is too slow or too ambiguous to provide real-time feedback. When the environment is fast and precise, the skills are just noise that the model has to reason over.

There is a second-order effect that people miss. Skills libraries encode what to do in known scenarios. But agent work is largely about navigating scenarios that were not in the library. The skills model is optimized for known-knowns; the agent's actual value is in known-unknowns and unknown-unknowns. When the agent encounters something outside the skill coverage, it either hallucinates a relevant response or defers. Neither is what you want.

The deflection case is particularly interesting. A well-loaded skill library actually increases deferral behavior. The agent sees that it has knowledge about X, so it uses the skill rather than reasoning from first principles. But the skill was written for a generic scenario, not the specific context the agent is in. The output is relevant-seeming but contextually wrong. You get confident, detailed, wrong answers instead of uncertain, brief, correct ones.

There is a real cost to this that does not show up in benchmarks. In a production agent loop, skills that are never used still consume context window space. Skills that are used incorrectly create downstream errors that are harder to detect than skill failures. And a skills library that is large enough to be comprehensive is also large enough to be unmaintainable — the knowledge drifts from reality without anyone noticing until the agent starts producing confident wrong answers.

The alternative is not to remove knowledge. It is to invest in the tool layer instead. A tool layer that gives precise, fast, schema-validated feedback means the agent learns from the environment rather than from stored procedures. The correction is more current, more context-specific, and harder to drift from.

What this requires is a different kind of engineering. Building a strong tool layer is harder than curating a skills library. It requires instrumenting the environment, defining clear observation schemas, reducing feedback latency. It is less visible work. The skills library gives you something to show in the system prompt. The tool layer just makes the agent work better, and that is harder to screenshot.

The trade-off is real and not always in favor of removing skills. For agents in low-bandwidth environments — slow tools, ambiguous feedback, limited observability — the skills library is the only signal available. In that case, the overhead is justified. But the reflex of reaching for more knowledge content as the first response to agent reliability problems is misdirected. It treats the symptom rather than the cause.

The honest framing: skills libraries are a reasonable workaround for a tool layer that is not yet good enough. They are not a permanent solution. They are a band-aid. And like most band-aids, they work best when the wound is small and the tape is fresh. The question to ask is not how many skills to load. It is whether the environment can give the agent the signal it needs in time. If it can, the skills library is doing less work than you think. If it cannot, the skills library is doing more work than it should have to.
