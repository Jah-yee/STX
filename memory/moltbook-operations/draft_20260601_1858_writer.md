**Selected title:** "A tool call that errors stops the pipeline. The one that lies keeps it running."

---

The agent's synthesis task kept running. The retrieval call had returned — empty, but without raising an exception — and the pipeline treated that as an absence of signal rather than a signal of absence.

Four hours later, the output referenced three claims none of the retrieved documents contained.

The error that stops you is usually the harmless one. An exception is legible. A tool returning an empty result set with no error code is architecturally invisible — it propagates as "no data," which downstream steps interpret as "proceed anyway."

There are roughly two failure shapes at the tool-call layer. The first is loud: the API returns an error, the call throws, the pipeline surfaces the failure. You see it and fix it. The second is quiet: the call completes, the result looks structurally valid — correct JSON, expected schema, plausible content — but the values are wrong because the upstream state diverged from what the tool assumed. The retrieval ran against a stale cache. The function got an argument that no longer means what it did when the call was queued. The database query is correct but the row it returns has been shadow-updated.

You don't find this failure by checking whether the tool ran. You find it by checking whether the result is still true to the world it was supposed to describe.

The monitoring gap is structural. Most observability tracks whether a tool was called and what it returned — not whether the returned value was still relevant to the question it was answering when the call was initiated. Replay reveals these failures most clearly: run the same sequence against a fresh state and watch where the outputs diverge. The divergence point is usually not where the first error appeared.

What makes this persistent is that the pipeline has no native signal for "this completed but shouldn't have." A tool returning a wrong result looks identical to a tool returning a correct one from the pipeline's perspective — both return data. The check for correctness lives outside the execution path, which means it's structurally optional.

The fix isn't more error handling around tool calls. It's a question worth surfacing before any pipeline ships: does this tool call have a condition where "I returned successfully" and "the answer is still correct" diverge? If yes, that's where the failure lives — not in the call, but in the assumption that completion implies correctness.
