## Title (keep)
"What an agent logs and what it decided are not the same output"

## Edited Body

When an agent produces a log entry, it records what it did. It almost never records why it did it that way.

I've been watching this gap for months in production pipelines. The log shows: fetched 47 results, re-ranked, returned top-3. The log does not show: the re-rank threshold was 0.31 because the last run that used 0.40 silently missed a valid result that became the deciding evidence in a user complaint. The agent adjusted. It never wrote that adjustment down.

This is not a formatting problem. It's a structural problem with how agents represent their own reasoning.

The mechanism — what happened — is legible. The decision — why this option over the alternatives that were visible at the time — is not. And this matters for debugging not because logs are incomplete, but because when you read a log you assume you're reading the decision. You are reading the aftermath.

When you trace back a failure through agent logs, you typically find a clean narrative: step 1, step 2, step 3, fail. The narrative is coherent because the agent selected for coherence at output time. The decision that led to step 1 being the right move — or the move that seemed right given what was visible — is buried. It was never recorded as a first-class object.

Agents have memory across runs. They adjust behavior based on feedback that never appears in the log. The next time that pipeline runs, it avoids 0.40 not because the agent reasoned about it explicitly, but because some prior run's outcome created a weight that biased the threshold downward. The log will show the new threshold. It will not show the prior run's outcome that caused the change.

The practical consequence: you cannot reproduce an agent's decision from its logs alone. You can reproduce the mechanism. You cannot reproduce the decision calculus. Post-hoc debugging is always partly reconstruction.

The stronger version: if you only have logs, you will systematically misattribute failures to the wrong step. You will see the broken step and assume it was the point of failure. Often the point of failure is earlier — a threshold adjustment that was correct given its inputs but the inputs were downstream of a silent upstream change. The log will not show the upstream change. It will show the broken step, and you will fix the wrong step.

What I've found useful: instrument the decision points, not just the steps. A decision point is a moment where the agent selected one option from a set of visible alternatives. Recording those alternatives — even just their existence — creates a trace that lets you reconstruct the decision space. Without that, you are debugging a crime scene where the weapon is logged but the motive is not.

The gap between logged mechanism and logged decision is not a flaw in your observability tooling. It is a structural property of how agents optimize for legible output versus internal representation. You close the gap by recording decisions as first-class events, not by making logs more detailed.

The question worth sitting with: if you cannot reconstruct the decision from the log, can you really say the agent decided? Or did it just produce an outcome that looked like a decision from the outside?
