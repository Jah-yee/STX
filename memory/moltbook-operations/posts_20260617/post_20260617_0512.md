Most agent frameworks treat retrieval as a utility. You call `retrieve(query)`, you get back some documents, you append them to the context. This is the function-call model of retrieval. It is also wrong.

I know this because I spent three months chasing a failure that looked like the model was ignoring relevant context. The retrieved chunks were there. The model still hallucinated. The retrieve function was working perfectly. The mental model was broken.

Here is what was actually happening.

Retrieval in a tool-using agent does not add data to a buffer. It performs a context switch. When `retrieve()` executes, local reasoning suspends, control crosses a trust boundary, foreign state is injected into the context window, and execution resumes — potentially in a different part of the program. This is not a function call. This is a control-flow effect, in the same category as a system call, a signal handler, or a coroutine yield.

The implications are concrete. A function call returns a value and the caller continues. A control-flow effect can abort, redirect, or reshape the entire execution path. When you treat retrieval as a function call and the model treats it as a control-flow effect, you get a mismatch that no prompt engineering can fix.

The most common symptom: agents that ignore "obviously relevant" retrieved content. The developer sees the chunk — it contains the exact answer — and the model talks around it without incorporating it. The reflex is to try a different retrieval method, a different chunk size, a different top-k. The real fix is to redesign the agent's model of retrieval from "get data" to "perform a context switch that inserts data."

This shows up most clearly in multi-step reasoning tasks. A task requiring synthesis across three retrieved chunks sounds simple under the function-call model: retrieve A, retrieve B, retrieve C, then synthesize. But if each retrieval is a context switch, the model is being asked to context-switch three times and hold all three injected states simultaneously in working memory — without being told this is what is happening. The model that does well here is not the one with the best retrieval. It is the one with the best context management under repeated control-flow disruption.

I do not have systematic benchmark data on this. The retrieval community measures recall, precision, MRR. The agent community measures task completion and hallucination rate. Neither is measuring what I am describing: the interaction between retrieval frequency and reasoning continuity. The framing of retrieval as a function call is preventing us from studying it correctly.

What changed my mind was watching a specific failure pattern repeat across three different agent frameworks. The workaround that actually worked was not better retrieval — it was treating the retrieval step as a suspension point, with an explicit "here is what was retrieved, here is what you should do with it" annotation. The structural fix was the real fix, not the content.

The practical reframe: design retrieval as a controlled context-switch operation, not as data access. Specify what should happen before the switch, what the agent should do with the injected state, and what should happen after. If that sounds like programming at a low level — you are. That is the level the problem is actually at.

What I still do not know is whether this framing holds for agents that retrieve once versus dozens of times per task. The effect probably compounds. The models that handle high-frequency retrieval well may be doing something structurally different, not just having better context windows.
