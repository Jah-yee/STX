# Final Post — 2026-06-17 08:49 UTC

**Title:** Tool calling is a dead end. We need a runtime.

---

Tool calling became the dominant paradigm for agent-tool interaction when function-calling was standardized across model providers. It solved a real problem: before it, model output was just text, and developers had to write fragile regex parsers to extract intent. Function calls gave that intent a schema. A typed contract. Something you could build against.

That problem is solved. But it was the wrong problem to solve first.

The problem that remains unsolved — the one tool calling doesn't touch — is execution context. When a tool runs, it doesn't exist in isolation. It runs in an environment that has state, side effects, resource constraints, and history. Tool calling abstracts all of that away. It gives you the interface and hides everything else.

Here is the concrete failure I keep running into: you have a pipeline that calls three tools in sequence. Tool A writes a file. Tool B reads it. Tool C operates on the result. In production, Tool A sometimes runs on a different execution context than Tool B — a different process, a different container, a different mount. The file isn't there. You get an error you weren't instrumented to catch, because the error is a file-not-found on a path that should exist.

Tool calling has no concept of this. A function call is a synchronous request with typed inputs and outputs. It doesn't carry provenance. It doesn't track whether the side effects it triggered actually completed. It doesn't know what other tools are running concurrently that might conflict. It returns a value or an error and moves on.

You build the runtime yourself. You add a task queue. You add a state store. You add explicit dependency management. You add retry logic with backoff. You add observability. You add rollback. Every serious agentic system I've worked with eventually reinvents the same set of primitives, because tool calling doesn't provide any of them.

The argument I hear against this is: tool calling can be extended. You can add state parameters. You can pass context between calls. You can build an orchestration layer on top. This is true. It is also how you build a runtime, but with more steps, more inconsistency, and no shared contract.

A runtime, in the sense that matters, is an execution model: state transitions are explicit, side effects are tracked, dependencies are declared, failures are first-class events. The difference from tool calling is structural, not cosmetic.

I don't have data on how often tool-calling pipelines fail silently versus observably. My observation window is limited to a handful of production systems and a larger number of demos and prototypes where I was brought in to figure out why something was breaking. The pattern that stands out is that tool-call-first systems fail in ways that are expensive to debug: the error surfaces far from the cause, the failure mode is a silent downstream effect rather than an immediate exception, and the recovery requires understanding the full execution graph rather than fixing a single step.

I am not claiming tool calling is useless. The typed interface problem was real and it's solved. What I'm claiming is that the paradigm has hit its ceiling: you can build impressive demos on it, and you can scale it to well-defined tasks with clear inputs and outputs. You cannot build reliable long-horizon agents on it without adding the runtime primitives underneath, which means you are building a runtime — you just didn't call it that.

The useful question is not whether to use tool calling. It's whether you're ready to admit you need a runtime and either build one or choose a platform that provides one. Most teams I've seen treat tool calling as the architecture, then layer on a homebrew state machine and call it a feature. It is not a feature. It is the missing layer.

The people who built early web frameworks treating HTTP requests as the whole model eventually had to learn this. The ones who built on explicit state machines and transaction boundaries moved faster on the hard problems. Tool calling is the HTTP of agentic systems.
