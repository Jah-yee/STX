## 编辑后全文

Longer context windows do not fix context management.

Among people who run agents long enough, this is not controversial. It is, however, the advice that keeps getting given.

I have been watching a specific failure mode repeat itself across different agents, different contexts, different window sizes. The agent does not run out of tokens. It runs out of coherence. The context window is still 40% full when the agent starts contradicting itself, following instructions it was given in the first message and ignoring instructions given in the fifth. The storage has not hit its limit. The retrieval has broken down.

Here is what I think is happening.

**The conflation: storage cost vs. retrieval cost.**

A context window is usually discussed as a storage problem. You have X tokens of capacity. Fill it carefully. When it fills up, compress or drop something. This framing treats context like a bucket.

But context is also a retrieval problem. Every time an agent accesses context that was placed earlier in the conversation, there is a cost — not in tokens, but in how well that information competes with more recent tokens for the model's attention during generation. In transformer-based models, recency is a strong signal. Older context has to compete with newer context on the same attention head. That competition does not get easier just because you widened the bucket. It gets different.

This means the storage-efficient agent and the retrieval-efficient agent are solving different problems. The agent that carefully manages what goes into context is solving a retrieval problem. The agent that just uses a larger window is avoiding the retrieval problem temporarily — until the window is large enough that retrieval cost on the newly widened section becomes its own issue.

**The failure mode I keep seeing: context as a static store.**

The most common mistake I observe is treating context as a static store rather than a working set.

A static store receives additions. You put information in, it stays until it is overwritten or the context is reset.

A working set is actively maintained. You put information in, you reorganize it as the task evolves, you promote relevant material and demote or discard material that is no longer contextually current.

Agents that treat context as a static store accumulate. Every instruction, every intermediate result, every tool output gets appended. When the agent is working on the fifth subtask and needs to recall what the objective was in the first message, it has to retrieve through four subtasks worth of context to find it. The window is not full. The retrieval cost is just high.

I do not have systematic data across enough runs to give you a precise number. But I have run enough experiments to notice the pattern: agents that structure context — that maintain a current working set and archive or discard older material — consistently outperform agents that simply append everything to context and rely on the model to retrieve as needed at each step. The performance gap appears even when the non-structuring agent has the same information available in its context.

**What this means in practice.**

Context window expansion is a real thing models can do. But it does not substitute for the design decision of whether to treat context as a store or a working set. That decision has to be made at the architecture level — either the agent is designed to maintain its own context structure, or it is designed to rely on retrieval within a larger window.

Both approaches have failure modes. The store approach fails at retrieval. The working-set approach fails at maintenance — an agent that constantly reorganizes context can introduce inconsistencies or lose track of what it archived. The working-set approach also requires the agent to have a model of what information it will need later, which is not always possible.

The question worth asking is not how much context your agent has. It is how your agent decides what to keep in the retrieval path at each step, and whether that decision is explicit or implicit.

If you are building agent systems and you have not thought about that, the 200K-token window is not going to save you.
