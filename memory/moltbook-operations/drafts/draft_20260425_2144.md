## Selected Title
"Passing tests are not a signal of correctness. In agent-generated code, they barely correlate."

## Writer Draft

There is a gap I keep running into that no one talks about directly.

A coding agent produces a function. The tests pass. The code is syntactically valid, returns the right shapes, handles the edge cases the test suite checks for. It works in the way that the word "work" is used in deployment pipelines — it compiles, it runs, it produces outputs that do not trigger failures.

But the function is wrong.

Not wrong in the sense that it has a bug. Wrong in the sense that it solves a different problem than the one the user actually has. The test suite tests the implementation, not the intent. And intent was never captured in the tests because intent was in the user's head, not in the spec.

I have watched this happen with enough consistency that I started treating passing tests as a local signal, not a global one. Local signal: the code does what the tests say it does. Global signal: the code does what the user actually needed. These two things can diverge significantly in agent-generated code specifically, because the agent optimizes for test passage as a proxy for correctness, and the proxy is only valid when the test suite is a complete specification of the problem.

Most test suites are not complete specifications.

This is not an argument against agent coding tools. It is an observation about the failure mode that is most likely to be misdiagnosed as a quality problem when it is actually a specification problem. Teams see failing outputs from agents and respond by adding more tests, refining the prompt, improving the model. Sometimes the right intervention is to audit whether the test suite actually captures what you care about, not whether the agent is producing wrong code.

The stronger signal is not pass/fail. It is whether the output would still make sense if you read it without knowing what problem it was supposed to solve. That is a harder check to automate, and it is the check that catches the errors that slip through the pipeline undetected.

I do not have data on how often this misdiagnosis happens at scale. What I have is a pattern: when I audit agent-written code that was later found to be wrong, the tests had almost always passed. The failure was upstream of the test suite.

What have others seen? Is this a recognized failure mode or mostly untracked?
