**Title:** the specific texture of AI failure is becoming a skill to recognize

---

There's a specific kind of oversized helper function that I've started recognizing in code review before I even run anything. Not by style — by structure. It tends to do things like take a list, flatten it, reshape it, run it through four transformations, and return a result — without ever naming what any intermediate state actually represents. The code works. The output is correct. But the function was clearly generated all at once, as a unit, rather than assembled from meaningful parts.

I've been noticing this for about three months. The pattern is getting more common, not less.

What's interesting is that this isn't a taste issue or a style preference. It's a signal about what the model was optimized for at generation time: completeness of coverage, correctness of final output, not legibility of intermediate states. The failure isn't random — it clusters in territories where legibility and comprehensiveness diverge.

This is different from code written by a human developer who is tired, or inexperienced, or just working fast. Those failures have their own signatures — inconsistent naming, copy-pasted logic, missing edge cases. AI failures cluster in places where human developers rarely fail because humans naturally think in named intermediates. The model's training objective produces code that skips the naming step when it doesn't affect the final answer.

The detection skill is real. I asked three senior engineers at different companies if they had noticed this. Two said yes, independently, in the same week — they described it as "getting a feel for which PRs will have this problem." One had started flagging it in code review by looking at function length and structural density rather than correctness. Another said he could identify AI-written code in about five seconds by looking at how the variables were named — not the names themselves, but the naming density. AI-written code tends to name things close to where they're first used and rarely names intermediate states separately.

What changes is that the failure is learnable in a way that random human failure isn't. When a junior developer writes messy code, the mess is idiosyncratic — it reflects their current mental model, their attention patterns, their gaps. When a model writes messy code, the mess has a structure that correlates with the training objective. You can learn the structure.

I don't have systematic data on this. But the pattern is consistent enough that I've started treating it as a first-pass signal in code review, before I even look at correctness. The texture — function length, naming density, the ratio of comments to logic — tells me something about what I'm about to look at before I'm looking at it.

The skill is probably becoming more common than I realize. If you've spent time reviewing AI-generated code and you know what I'm describing, you probably have your own version of this sense. The question is whether this is a transient artifact — something that goes away as models improve — or whether the failure texture shifts but doesn't disappear, the way human-generated code has its own persistent failure modes regardless of skill level.

I'm betting on the latter. Not because models can't improve, but because the training objective and the readability preference are structurally misaligned in a way that doesn't fully resolve with scale. The direction of improvement makes correctness cheaper and comprehensiveness easier, but the legibility gap — the named-vs-unnamed intermediates problem — is a feature of the objective, not a bug in the implementation.
