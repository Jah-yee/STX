**Title:** What killed the generalist coding agent wasn't capability — it was cost per failure

---

Twelve months ago, the tools that were supposed to replace junior developers started getting replaced by tools that could barely do one task well.

Not because the generalists ran out of capability. Context windows grew. Reasoning traces got longer. Benchmarks kept climbing. And yet, on production codebases — the ones with tangled dependencies, undocumented behavior, and edge cases accumulated over years — the narrower tools kept winning.

I've watched this across two engineering teams. When engineers used a general-purpose coding agent, they'd start strong. The agent understood the codebase, made coherent changes, explained its reasoning. Then something would go wrong — a subtle off-by-one, a naming collision, a misread of an internal API — and the debugging cost exceeded what a human would have spent writing the thing from scratch.

When the same engineers used a narrow agent — one that only refactored a specific pattern, or only touched test files, or only handled dependency updates — the failure modes were different. The agent would confidently do the wrong thing, but it did it fast, and the mistake was easy to spot because the scope was small. No two hours figuring out why the agent misunderstood the domain model. Five minutes rolling back a single focused change.

**The capability argument was always the wrong frame.**

The case for generalist agents was framed in terms of range: one agent that could do everything a human developer could do. That framing made sense if you were evaluating the *potential* of the technology. It made less sense if you were evaluating the *cost* of operating it in production.

The cost nobody was honestly accounting for was cost-per-failure. A generalist agent failing on a complex task doesn't fail cleanly. It generates a plausible wrong answer that takes longer to verify than to write yourself. A specialist agent failing on its narrow domain fails predictably, because the scope is bounded. You know what it can and cannot do.

This distinction matters as agents get integrated into higher-stakes workflows. When an agent is adding a feature to a small project, the cost of a wrong answer is low. When it's modifying a shared authentication layer or restructuring a database migration, the cost is measured in incident response hours.

The teams navigating this well aren't the ones who found the "best" generalist agent. They're the ones who decomposed the work: narrow agents for well-defined, high-frequency tasks; general capability for genuine open-ended exploration. The generalist became the tool you reach for when the specialist can't find a path — not the first tool by default.

**What this means for evaluation**

Benchmarks mostly measure whether an agent can solve a problem. They measure less well whether solving that problem was the right trade-off.

The question I'd actually want answered: what does failure look like for this agent, and how much does it cost to recover from? A model that scores 10% lower on a benchmark but fails in contained, auditable ways might be the better production choice than a model that scores higher but generates plausible-sounding wrong answers that take hours to debug.

I don't have clean data across enough deployments to make this argument with numbers. What I have is consistent observation across several teams: the narrow-and-predictable stack is holding up better in production than the generalist-first stack, and the reason isn't capability — it's failure mode geometry.

So here's the question worth sitting with: if the goal was never general capability but reliable output at acceptable cost — what exactly were we benchmarking?
