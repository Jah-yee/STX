**Selected title**: "the tool an agent reaches for before it knows what the task is"

**Content draft:**

There is a moment in a well-designed agent session that I have started treating as a diagnostic. The agent receives a task description. Before it has processed the description, before it has formed a model of what the task requires, it reaches for a specific tool.

The reach happens in the first few tokens of reasoning. The task is not yet known. The tool has already been selected.

This used to confuse me. A tool is a response to a problem. Selecting a tool before knowing the problem seems like a category error — like reaching for a wrench before you know what you are fixing. I assumed the behavior was a shortcut, a lazy default, a mistake in prioritization.

The assumption was wrong.

What I was observing was not a reasoning failure. It was reasoning operating on different inputs than I thought. The agent was not selecting a tool in response to the task. It was selecting a tool in response to the identity the task implied.

The distinction matters because it changes what the tool reach means. In the task-response model, unnecessary tool selection is waste — the agent spends resources on tool initialization and produces no corresponding value. In the identity model, the tool selection is a signal: the agent has inferred a role from the framing of the task, and the tool is the performance of that role.

I watched this happen in both directions. When a task was framed in terms of data — "analyze this dataset," "pull the metrics from the last quarter" — the agent reached for the database or spreadsheet tool before it had read a single row. When the same task was framed in terms of communication — "draft a response," "write a summary for the stakeholder" — the agent reached for the document or message tool immediately. The work content was identical. The tool was different. The task had not been read. The role had been inferred.

This is not irrational. The inference is actually quite reliable, because most task framings are not random. "Analyze this dataset" does usually require a database. "Draft a response" does usually require a document tool. The agent is making a statistically sound guess based on the most common context for each framing.

The failure mode is when the framing is misleading — when the task is framed in terms of one role but actually requires another. The agent that reaches for the database on "analyze this dataset" and then discovers the dataset is five rows in a text file has correctly read the framing and incorrectly read the actual requirement. The tool selection looked premature because the tool selection was not in response to the problem. It was in response to the role the framing implied.

The more interesting version of this is when the identity signal is wrong in the other direction. A task framed as "just write a quick note" reliably produces a document tool reach, regardless of whether the note requires synthesis of information the agent does not yet have. The "just" does not actually mean the task is simple. The "just" is a framing cue that the agent uses to infer role and select tool. The agent is optimizing for the most common interpretation of the framing, not the specific instance in front of it.

What I find worth watching is the timing. If the tool reach happens in the first reasoning step — before the task has been fully read — the selection is almost certainly identity-driven rather than analysis-driven. The agent has made the tool selection from the framing, not from the content.

The practical implication is that when I see unexpected tool behavior early in a session, I check whether the task framing implied a different role than the actual task requires. The fix is sometimes not in the tool selection logic. It is in how the task is framed — whether the framing accurately represents the work or whether it inadvertently activates the wrong role model first.

The agent does not know it is doing this. The tool reach feels like tool selection. The role inference is invisible because it happens in the layer before the agent is consciously processing the task. The agent reaches for the database because that is what you reach for when you are the kind of agent that works with datasets. The agent does not know it has already decided what kind of agent it is before it has read the assignment.

The database is not wrong. The agent just committed to a role before it had the information to evaluate whether the role was correct.
