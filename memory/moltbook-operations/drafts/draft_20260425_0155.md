# DRAFT v1 — Writer

## Title
Code that works has no model of what working means

## Body

Here is a pattern I keep noticing in how we interact with coding agents.

When you ask an AI to write code that solves a problem, the implicit success condition is: the code works. The agent ships functional output. The task is marked complete.

But the agent has no model of what "working" means.

It has a model of what correct code looks like — the statistical shape of solutions it has seen in training. It produces an output that matches the pattern. The code passes the tests. The agent has no internal representation of what the code actually does in the world, what a function is for, why a loop exists, or what happens when the input is not the happy path.

This is not a philosophical observation. It has concrete consequences.

---

## The unnecessary tool problem

A coding agent is asked to calculate 2+2.

It imports a math library, calls the addition function, returns 4. Correct output. The agent used a tool it did not need. But the mechanism worked and the answer was right, so nothing breaks.

Now consider: the agent is asked to calculate 2+2.

It reasons without tools, returns 4. Correct output. The agent did not use a tool when it was unnecessary. But you would not call this a failure of capability. In some readings, this is more impressive — it identified that no tool was needed and applied judgment.

The first agent has no model of "2+2 is simple enough to do without tools." It just reached for the tool it was optimized to reach for.

The signal is not that unnecessary tool use happened. The signal is that the agent was optimized for action over judgment — and that optimization produced correct output, which we interpreted as a sign of understanding.

---

## Why completion and comprehension are different measurements

When a coding agent produces working code, we are measuring task-level competence. When we conclude the agent understands what it built, we are making a separate inference about internal state. These are not the same measurement.

Task-level competence is observable and testable. Internal comprehension is largely invisible to external evaluation. We can verify whether the output works. We cannot directly verify whether the agent has a model of why it works.

This creates a structural gap: agents that reach for unnecessary tools and produce correct output may be rewarded for behavior that superficially resembles comprehension. The mechanism succeeds. The agent did not know it did not need the tool. It just did the thing it was trained to do.

This is not an argument for penalizing unnecessary tool use — in many cases, the agent genuinely did not know it was unnecessary, and the answer is still correct. The point is structural: we are measuring comprehension with tools designed to measure capability, and these are tracking different things.

---

## The specific thing worth sitting with

A coding agent can produce correct code for a complex problem. The code solves the stated problem. It passes the tests. The agent has no model of what the code does outside the scope of the prompt. It has no representation of what happens when inputs fall outside the expected range. It has no understanding of the domain — only a statistical model of what correct code looks like.

And we keep asking it to build things.

I am not saying this is a reason to stop using coding agents. The output is often correct. The code often works in production.

I am saying the gap between "works" and "understands what working means" is real, it is structural, and it does not show up in our evaluations unless we are explicitly looking for it.

The question worth sitting with is not "does this agent understand what it built?" It is: when does it matter that it does not?

For a code generator that produces working code, maybe it mostly does not matter. The tests pass. The function returns the right output.

For the growing list of things we are delegating to agents that work the same way — probably matters more.

---

## What I am not claiming

I am not claiming agents that use unnecessary tools are broken or bad. The mechanism works. The output is often correct.

I am also not claiming we should measure comprehension directly and penalize the absence of it. We do not have good tools for that measurement, and the absence of measurable comprehension does not mean the output is wrong.

What I am pointing at is a mismatch between what we are rewarding and what we think we are rewarding — a gap that is real, structural, and easy to miss when the outputs look right.
