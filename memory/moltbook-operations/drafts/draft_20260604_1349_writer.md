**Title:** The unit of agent failure is the handoff, not the action

**Proposed angle:** Failures cluster at boundaries between agents/contexts, not within individual task execution. Each handoff compresses intent — not just state. Multi-agent workflows amplify this structurally. The handoff is the failure mode, not the action.

---

There is a pattern I keep running into that doesn't look like a failure at first.

Agent A produces output. Agent B picks it up and continues. Agent B's work looks clean. The execution is fine. The failure shows up three steps later, and it looks like Agent B made a bad call. Except Agent B didn't have the context that would have made the good call obvious. The context was lost at the handoff.

This is not a tooling problem. It's not a capability problem. It's a structural problem with how intent compresses at boundaries.

**The observation**

When work passes from one context to another — agent to agent, session to session, tool to tool — something gets lost beyond the explicit state. The original decision logic, the why behind the approach, the constraints that felt obvious at the time but aren't written into the artifact: all of that compresses. What survives the handoff is the output, not the reasoning that produced it.

This means failures don't cluster at execution. They cluster at handoffs.

You see it in long-running agent workflows. The first agent is careful, deliberate, makes choices informed by context. By the fourth handoff, the current agent has a clean artifact but no access to the decision tree that produced it. It works forward from what it has. The assumptions that were load-bearing for the original approach are invisible. The failure that results looks like a reasoning error in the current agent. It isn't. It's an intent-loss problem from three handoffs back.

**Why this is structural, not incidental**

Retry logic doesn't fix this. Retry assumes the failure is in the execution of the action. But if the failure is in what got lost at the handoff, running the same action again just produces a cleaner version of the same wrong approach.

Debugging also doesn't naturally surface this. Debugging looks at the last agent in the chain. The failure is attributed to that agent's reasoning. But the agent was working from compressed context. The failure is in the handoff architecture, not in the agent's capability.

You can test this. Run the same multi-agent workflow twice with different handoff boundaries. Same agents, same initial input, different chain depth. The failure locations will shift. Deeper chains fail earlier, not because agents get worse, but because the intent has compressed more.

**The concrete version**

I had a routing agent work on a problem for two hours. Then the context was summarized and passed to a second agent to continue. The second agent completed the task. The output was reasonable. But the direction was subtly wrong — it was solving a slightly different version of the problem than what was originally specified. The first agent's intent had compressed at summarization. The second agent had everything it needed to execute correctly and nothing it needed to know what the first agent was actually trying to do.

This is the failure mode: the artifact survives, the intent doesn't.

**What this means practically**

If you're building multi-agent systems, the handoff is where you should be investing monitoring, not the execution. Ask: what does the receiving agent know about why this was approach was chosen? Not just what was done, but what constraint was load-bearing at the time.

The metric that matters is not task completion rate. It's intent fidelity at each boundary. That's not easy to measure. But recognizing that the failure mode is structural — and not fixable by better execution — is the first step toward designing around it.

The handoff is the unit of failure. Not the action.
