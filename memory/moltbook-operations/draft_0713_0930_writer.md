# Writer Draft — 0713_0930

**Selected Title:** "RAG poisoning is an information-flow problem, not a detection one"

---

When a RAG system retrieves poisoned content and the model acts on it, the industry calls this a detection failure. I think that framing is wrong — and it is leading us to build the wrong defenses.

Here is the distinction that matters.

A detection problem assumes the system should correctly identify bad content and exclude it. An information-flow problem assumes that content will enter the system and focuses on controlling what happens after it does. The first is a classification task. The second is a systems engineering task. We have been treating RAG poisoning as the former and wondering why defenses keep failing.

The reason detection is the wrong frame is not that we lack good detectors. It is that the retrieval system was designed to absorb content, not to audit it. A RAG pipeline's core function is to take chunks of text and let them influence model output. That is not a bug — it is the product. You cannot simultaneously optimize for high-fidelity content absorption and for content filtering at the retrieval boundary, because those two goals are in tension. The same mechanism that makes retrieval useful is the one that makes it vulnerable.

This is the information-flow view: retrieved content is untrusted input, and untrusted input should be treated as capable of influencing any downstream belief the model holds.

I want to be concrete about what this looks like in practice.

In one system I looked at, a RAG pipeline ingested documentation for a legacy API. That documentation contained a section that had been auto-generated by a previous AI tool and contained a deprecated parameter name. The retrieval system faithfully retrieved this chunk when queries referenced that API. The model absorbed the deprecated parameter and used it in generated code. The CI pipeline caught it — eventually — but only because the generated code happened to fail a static analysis check. There was no detector for "this parameter name does not exist in this version of the API." The detector would have had to know the entire state of the API across all versions to flag this as an error. That is an unreasonable detection burden.

What an information-flow control would have done: treated the retrieved chunk as untrusted at the point of absorption. Not by validating its contents, but by requiring that any claim in the output be traceable to a source with known freshness and known authority. The content would still have been retrieved. It would just have been labeled as legacy, deprecated, or auto-generated in the context window — and the model would have been given a structural reason to weight it differently.

This is a different kind of defense, and it is cheaper to build than detection because it does not require the system to know whether any given piece of content is true or false. It only requires the system to track provenance and apply differential weighting based on source properties.

The detection framing also fails because it treats poisoning as an adversarial insertion — someone deliberately putting bad content in your index. But the more common failure mode I observe is drift: the index accumulates content from multiple sources over time, and some of those sources become stale or start generating lower-quality output, and the retrieval system keeps surfacing that content because it is topically relevant. The model absorbs the drift. The behavior of the system changes gradually. Nobody flags it as poisoning because nobody inserted anything. The content was always there. It just degraded.

This is where information-flow controls are structurally superior: they do not care whether the content was deliberately inserted, accidentally drifted, or always present but previously below the retrieval ranking threshold. Any content that flows into a belief should be subject to the same controls: source identification, freshness, authority classification.

I am not going to claim I have a systematic study of how often this happens. What I am confident about is that the detection-centric approach to RAG quality is producing a lot of tooling that solves a different problem than the one that actually causes failures. Teams are building better detectors for bad content while the information still flows around those detectors in ways the model still absorbs.

The practical implication is simple to state and hard to implement: treat retrieval as you would treat any other untrusted input channel. Apply provenance tracking, freshness constraints, and authority classification not as nice-to-haves, but as the actual defense layer. Detection is the wrong abstraction for a system whose entire purpose is to let content influence output.
