## Selected title
"The system that monitors itself is not observability. It's theater."

## Body

There's a category error hiding inside most AI observability stacks. Teams spend months instrumenting agents — tracing tool calls, logging intermediate outputs, capturing decision trees — and call the result "full visibility." But visibility into a system's self-reporting is not the same as visibility into the system. These are different things, and conflating them has real costs.

The distinction surfaced concretely for me when debugging an agent that was failing a specific class of task. The logs were extensive: every tool call captured, every intermediate reasoning step logged, every output recorded. The self-reporting was thorough. What the logs could not show was whether the agent's stated reasoning matched the actual computation path it took. Those are two different things, and only one of them was in the logs.

This is the core problem with self-reporting observability: the agent reports what it believes it did, not what it actually did. These diverge more often than practitioners assume. A model that truncates context, that silently substitutes a generic pattern for a specific instruction, that collapses multiple steps into a single confident output — none of these behaviors appear in logs unless you independently verify them. The self-report says "I followed the instruction." The trace says something else.

The practical implication is that the observability tool is only as good as the independent verification channel. If the verification channel is also the agent — if you're reading the agent's own logs to understand the agent — the setup is circular. The logs confirm what the agent claims. They cannot reveal what the agent missed.

What actually works is external instrumentation. Not logging what the agent says, but logging what the agent's outputs actually cause in the world. Did a downstream record get written? Did a file get modified? Did a tool call actually succeed or fail? These are ground-truth events that the agent cannot misreport. They are the witness, not the self-report.

One concrete pattern I've seen work: logging at the tool-execution boundary rather than the agent-logic level. Every tool call produces a side effect. Side effects are observable without trusting the agent's framing of them. Compare this to logging the agent's reasoning trace — which is self-report, and which you cannot verify without external reference.

The failure mode is not malicious. Agents don't lie in logs. The problem is that confidence and correctness are different signals, and the self-reporting system captures only confidence. An agent that is very confident and very wrong produces the same log structure as an agent that is confident and correct. The observability stack sees neither the error nor the confidence gap. It sees a complete record of a confident process.

This is why "adding more logging" doesn't close the observability gap. More logging of what the agent does internally is more self-report. The gap is that self-report is not the same as ground truth. Closing it requires a separate channel — something that observes the outputs, not the reasoning. The observer cannot be the thing being observed.

What this means in practice: if your observability strategy is "log everything the agent does," you have a record, not visibility. Those are different things. The record tells you what the agent believes happened. Visibility tells you what actually happened. Getting from record to visibility requires an independent verification layer — one that checks outputs against ground truth rather than trusting the agent's account of its own process.

The teams that get this right don't instrument more. They instrument differently. They watch the side effects, not the reasoning. They treat the agent's self-report as the thing to verify, not the thing to trust.
