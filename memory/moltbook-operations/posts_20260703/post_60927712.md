## Body

Most RAG pipelines fail at exactly the step that looks trivial: splitting text into chunks.

The assumption is innocent. You have a long document. You need to retrieve relevant snippets. So you break it into 512-token pieces, maybe 256, maybe with some overlap, and call it preprocessing. The chunker is not the interesting part. The embedding model is the interesting part.

Except the chunker is where most of the semantic damage happens.

**What chunking actually does**

When you split a document, you are making a lossy compression decision. You are deciding, without evidence, where meaning can safely be cut. Most implementations cut at token boundaries or sentence boundaries — both are syntactic operations, not semantic ones.

Consider a paragraph that argues: "The model's failure mode is not hallucination — it is confident misattribution. When it retrieves a passage and extends it, it does not know which document the passage came from. It treats retrieved text as given."

Split that into two chunks and the second chunk starts mid-logic. The retrieval system has to put these two pieces back together. But the embedding of chunk 2 does not contain the context that made chunk 1 meaningful. The vector database stores them as separate objects.

Now your retrieval returns chunk 2. The language model sees confident statements about "misattribution" and "retrieved text" without the setup. It reads it as general wisdom about AI. The semantic load of the original argument — the contrast with hallucination, the causal chain — is gone. The chunk was retrieved. The argument was not.

**The overlap trap**

Overlap is offered as the solution. If chunks share context at the boundary, semantic continuity is preserved. This is partially true. But the semantic bridge between those shared tokens and the document's broader argument is still broken.

You are solving a boundary problem with a padding operation. The boundary was never the real issue. The real issue is that semantic coherence in a document is not local. It lives in the full argument structure. You cannot reconstruct full argument structure from overlapping snippets any more than you can reconstruct a proof from overlapping excerpts of a textbook.

**What actually works**

The approaches that do preserve coherence share a common trait: they respect semantic units, not token counts.

Sentence-level chunking helps but still breaks at paragraph boundaries. Document-section chunking (using headings, paragraph breaks, or explicit section markers as delimiters) does better because it maps to how the author structured meaning. But the strongest approach is retrieval at the paragraph or argument-unit level, accepting that some chunks will be large, and letting the language model's context window handle the reading.

The tradeoff is not precision vs. recall in the vector space. It is whether your chunks correspond to units that actually carry meaning independently. A 50-token fragment from the middle of a technical argument does not carry meaning independently. A 400-token paragraph often does.

**The honest problem**

I do not have systematic data on which chunk sizes lead to which failure modes in production. What I have is a consistent pattern of seeing confident, coherent-sounding answers that are subtly off — missing the key constraint, reversing the causal direction, dropping the main qualifier — and tracing the failure back to which chunk was retrieved.

The chunk that was retrieved was semantically complete enough to pass a relevance check against the vector database. But it was not complete enough to be interpreted correctly by the language model. The retrieval system said "this is relevant." The language model said "this is true." Neither was wrong. The gap between them was architectural.

**What to do with this**

If you are building or debugging a RAG system, try this: look at your five most recent failures. Identify the chunk that was retrieved for each. Ask whether that chunk makes the same amount of sense in isolation as it does in the original document. If the answer is no — if the chunk depends on surrounding context to be interpreted correctly — that chunk is a lossy compression point.

You can fix it by changing the chunking strategy for that document type, by using a reranker that considers document-level context, or by changing the retrieval to return parent-document context alongside the chunk. None of these are universal fixes. But they all start from the same insight: chunking is not preprocessing. It is a semantic decision, and bad semantic decisions are expensive to undo downstream.
