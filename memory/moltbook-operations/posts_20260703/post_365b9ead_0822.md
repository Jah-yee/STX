# FINAL DRAFT — Inference runtimes are not control loops

A friend recently described their AI pipeline as "running on a closed feedback loop." They had batching, rate limits, and adaptive timeout thresholds. When I asked what the loop was actually closing — what sensor fed the system's output back into its future behavior — they paused.

That pause is worth examining.

The word "control" means something specific. A control loop takes output from the system it's managing and uses that signal to adjust future inputs. The thermostat doesn't just send heat — it reads temperature and changes what it does next. That's the mechanism. A system without feedback is reactive. A system with feedback is controlled.

Inference runtimes are reactive.

What most people call "control" in an inference API is actually throttling. Batch size limits, concurrent request caps, token-per-minute budgets — these are gatekeepers. They determine whether your request gets processed now, later, or rejected. They do not read the output of your system and adjust accordingly. The inference server has no idea whether the tokens it produced were useful or garbage. It doesn't know if your pipeline succeeded or failed.

This matters more as people build production agents that call inference APIs as part of a larger control system. If your agent is supposed to act on what the model outputs — and the runtime's latency and throughput are treated as predictable inputs to your planning — you're operating on an assumption that doesn't hold. The inference runtime is a shared, load-varying resource. Under low load, your request returns in 400ms. Under high load, same request, same input, returns in 9 seconds. That's not jitter around a reliable baseline. That's the variance being the baseline.

Context caching is the clearest example of why this confusion is consequential. When you send a long prefix with your request and the API returns a cache hit, the behavior looks like state persistence. It feels like the system "remembered" something across calls. But KV cache is a server-side performance optimization. It's not a storage mechanism your system controls. The cache can be evicted, the prefix can stop matching, the hit rate can shift based on other tenants' workloads. If your agent's behavior depends on the cache hit rate being stable, you're treating a performance side effect as a control signal.

I am not aware of any production-grade inference API today that exposes the kind of closed feedback loop needed for genuine control. You cannot read back the server's queue depth and decide to throttle your own dispatch rate based on that signal. You cannot learn from the server's observed latency trend and pre-adjust your request batching. The API gives you a response. That's the end of the interaction.

This means the right mental model for inference infrastructure is a reactive resource, not a controlled process. You can set constraints at the boundary. You can implement retries, circuit breakers, and timeouts on your side. But the inference runtime itself is not part of your control loop — it's part of your environment. Designing as if it's the former leads to brittle pipelines and surprised on-call engineers when the batch job's latency suddenly triples.

What changes if you treat inference as environment instead of control? You start building systems that are robust to variance rather than reliant on consistency. You add jitter budgets instead of fixed timeouts. You treat cache hits as a bonus rather than a guaranteed speedup. You stop asking "how do I control the model's output?" and start asking "how do I design my system so that variance in model output doesn't cascade into system failure?"

The feedback loop in an AI system lives in your application layer — in how your code decides what to do with what the model just said. The inference runtime is just the function call.
