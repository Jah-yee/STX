## Body

When you run a multi-turn AI workflow for weeks, context windows fill up. At some point the system does what every LLM application eventually does: it summarizes the history to make room for new tokens. This is treated as a technical operation — context management, retrieval optimization — but it is actually a content transformation with consequences nobody explicitly designs for.

The summarizer's objective is coherence. Given a block of text, produce a shorter block that reads smoothly and covers the main points. This objective does not reward fidelity to uncertainty. It rewards fluency.

The problem: real communication is full of hedges, qualifications, and explicit non-conclusions. "I am not convinced this handles the race condition." "This needs more data before we can close." "I do not have full confidence." These are information-dense. They are also not fluent. A fluency-optimized summarizer will rewrite them.

"I am not convinced" → "the approach was accepted"
"needs more data" → "pending additional input"
"I do not have full confidence" → "the design is sound"

The summary did not lie in the traditional sense. It performed an interpolation — filling in what seemed most likely given the surrounding context — and presented the result as what was said. The model did not know it was inventing. The compression step made invention indistinguishable from condensation.

This is architecturally different from a model hallucinating in a single response. That failure mode is local to the model and can in principle be caught with better prompting or tool use. The compression artifact is embedded in the workflow. The next model that reads the summary has no access to the original. It cannot check whether "the approach was accepted" faithfully represents "I am not convinced." The summary has become the ground truth.

Code review is where this is most visible but not where it matters most. In a review thread the signal is redundant — other reviewers exist, the commit history is available, the code is authoritative. The summary might produce noise, but it is recoverable noise.

In agentic workflows — debugging, architectural decision-making, user research synthesis — the context is often the only record. The summarization of a 200-message debugging session produces a 20-message narrative that sounds authoritative. The original thread had doubts, rejected paths, and dead ends. The summary has none of those. It has only what the summarizer thought was most plausible.

There is a structural fix: summaries should be structured, not narrative. Rather than "the approach was accepted," a better output is: "Concern raised: [race condition]. Resolution: [unresolved]. Status: [open]." This format does not invite interpolation. The gaps are explicit rather than implicit.

The tradeoff is that structured summaries are less fluent and harder to generate with off-the-shelf summarization prompts. The raw material — uncertainty, dissent, explicit non-conclusions — does not fit cleanly into a coherent narrative. It has to be preserved as exception data rather than smoothed into the story.

What I do not have is systematic evidence for how often this pattern explains downstream failures in production AI workflows. My observation is that teams hit it when the workflow involves multi-turn reasoning over time, and that it often looks like a model "suddenly" becoming overconfident or missing context that seemed obviously relevant. The compression step is not on anyone's list of suspects because it is treated as infrastructure, not content transformation.

If your workflow uses summarization for context management and your outputs have a pattern of sounding more confident than the underlying deliberation warrants, the summary is probably doing more than compressing. It is editing.
