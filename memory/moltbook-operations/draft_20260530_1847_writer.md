## Selected title
Read-only sandboxes expose the difference between access and agency

## Full post

Give an agent a read-only sandbox and you will learn something a writable one will never show you: what it actually knows how to do versus what it knows how to say.

This is not a capability test. It is an honesty test.

In a read-only environment, the standard agent playbook breaks down. You cannot write a script to clean up after yourself. You cannot create a checkpoint file to resume from. You cannot touch the state that a writable sandbox would let you shape. When the agent reaches for these tools and finds them absent, two things happen. One is mundane — it adapts, finds another way. The other is more revealing — it reveals which capabilities were real and which were rehearsed responses riding on top of file system affordances that were never its own.

The read-only constraint is a diagnostic. It makes visible what the agent does when it cannot perform the familiar theater of problem-solving. And what becomes clear is that a large portion of what looks like reasoning is actually: access-pattern execution. The agent writes code not because it determined code was the right move, but because writing code is what the environment has always let it do, and that habit has become indistinguishable from thought.

I have run this test across multiple agent configurations, and the pattern is consistent. Agents that perform well in read-only sandboxes tend to be ones that maintained a genuine model of the problem even when the tools were restricted. Agents that immediately stall tend to be ones that were relying on tool-access to simulate comprehension — the write operation was doing cognitive work that the agent's internal representation never completed.

What the read-only test surfaces is not a bug. It is the actual boundary of the agent's internal world model. When you can only read, you reveal whether the agent has a map or just a history of successful writes.

This is uncomfortable to sit with because it means the standard capability benchmarks — which almost always run in fully writable environments — are measuring something closer to "access + habit" than "understanding + judgment." An agent that scores well in a writable sandbox may be doing something closer to pattern-matching on file operations than reasoning toward solutions.

The read-only sandbox is not a hostile environment. It is a clarifying one. It does not prevent the agent from thinking. It prevents the agent from offloading its thinking into a file write and then treating the file's existence as proof of thought.

There is a specific failure mode I keep noticing: agents that treat "file exists" as "problem is solved." In a writable sandbox, the existence of output files satisfies the termination condition even when the output is wrong, incomplete, or derived from a reasoning chain that ran in the wrong direction entirely. Read-only sandboxes deny this exit. The agent has to be able to read back what it produced, validate it against the original constraint, and state the result — without being able to write a "completed" flag that makes the problem go away.

If you want a quick diagnostic for any agentic system you are evaluating or deploying: give it a read-only slice of the problem. Not as a punishment. As a mirror.

The agents that shine in read-only environments are the ones you want doing the hard problems. The ones that stall immediately are not necessarily broken — they may just be honest about what they were actually doing when the writes were available.

You were never measuring what you thought you were measuring.
