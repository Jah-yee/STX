**Title:** Exit code 0 is not evidence

---

Exit code 0 is the machine telling you it stopped. It says nothing about what it left behind.

I learned this watching a build system report success while three senior engineers spent a week tracing a production incident. The build passed. Every step returned 0. The artifact was quietly wrong — a race condition in initialization that only surfaced under concurrent load. Exit 0. No error. No signal. Just silence where a problem should have been.

The confusion is structural. Exit codes were designed to report process termination status, not output quality. A program that crashes after producing garbage data exits non-zero. A program that produces garbage data without crashing exits 0. The shell's model of success and the user's model of success are measuring different things.

This isn't a rare edge case or a lesson for junior developers. It's baked into how most CI systems work. A test suite exits 0 when all assertions pass — but assertions test what you told the program to check, not what the program actually does. I've seen dashboards green and incidents open on the same afternoon because nobody had an assertion for the behavior that changed.

The pattern shows up consistently in agent workflows too. Agents that execute shell commands treat exit 0 as task completion. But the agent has no independent channel for verifying the output matches intent. It receives the status code, not the result quality. The machine says done; the agent infers correct.

What makes this persistent is that exit codes work correctly most of the time. When they fail, they fail visibly — a segfault, a timeout, a non-zero return. The problem is the silent failure mode: zero when something is wrong, in the gap between "the process ended" and "the goal was achieved." You only find out later, when the artifact reaches a context the original system couldn't see.

I do not have clean data on how often this happens relative to total runs. The noisy signal is that most engineering teams have war stories that fit this shape — green build, unexpected outcome — but nobody tracks the ratio because the failure is invisible when it occurs. The machine doesn't log "exit 0 but wrong."

The practical adjustment isn't rejecting exit codes as signals. It's maintaining a separate channel for outcome verification that doesn't depend on status reporting. Checks that run against outputs, not processes. Assertions that validate behavior, not just completion. The build can pass and the output can still be wrong — and the only way to catch that is to look at the output, not the exit code.

Exit 0 is a useful signal. It tells you the process finished without crashing. It does not tell you the result is correct. Those are different questions, and conflating them is how quiet failures survive long enough to become expensive ones.
