**Selected Title:** "Skills transfer. Context doesn't. That's the real gap."

---

You spend an hour teaching an agent how to handle refund requests. It works. Six weeks later, the same agent fails spectacularly on a refund case that was slightly more complex — one that a human would have handled without hesitation.

What broke wasn't the skill. The skill transferred fine. What didn't transfer was the context that made the skill work.

## The portability problem

A skill, in the agentic sense, is a compressed decision pattern: given X context, take Y action. The compression is lossy. When you transfer a skill to a new agent or a new environment, you transfer the Y and some of the X — but not all of it. The X that didn't transfer includes the edge cases, the failure modes, the context cues that a human would read without thinking.

I noticed this most clearly in a retrieval-augmented planning agent I was iterating on. The agent had a reliable skill for converting natural language queries into search filters — it worked well on the evaluation set. But when the agent encountered a query that required re-framing the search strategy (not just adjusting filters), it failed in a characteristic way: it applied the skill faithfully but to the wrong problem. The skill was correct. The context model wasn't.

The gap isn't a bug in the skill. It's a structural property of how skills are represented and transferred.

## What context actually does

Context in this sense isn't conversation history or environment state. It's the set of conditions under which a skill produces the right output. These conditions include:

- The distribution of inputs the skill was trained on
- The implicit constraints of the environment the skill operates in
- The cost structure of the decisions the skill makes
- The feedback signals that would catch a misapplied skill

When any of these change, the skill can misfire even though nothing about the skill itself has changed. The agent is doing the right thing for the wrong situation.

This is different from a skill being wrong. A wrong skill fails consistently in its domain. A context-mismatch failure is subtler — the agent does what it was taught, but the situation it encounters is different from the one it was taught in. The output is wrong not because the pattern is wrong but because the pattern's preconditions aren't met.

## The tooling failure mode

Most agent frameworks treat skills as relatively stable artifacts. You define a skill, you test it, you deploy it. The assumption is that the skill is the unit of transfer and the skill encodes everything needed to apply it.

It doesn't. The skill encodes the mapping. The context model has to come separately, and most systems don't have a good mechanism for transferring it.

What happens in practice is that engineers build larger and larger skill libraries, hoping that breadth will compensate for context fragility. It usually doesn't. A 40-skill agent with a shallow context model is more likely to fail on novel inputs than a 10-skill agent with a rich one. More skills mean more opportunities for the wrong skill to be applied to the wrong situation.

The failure mode isn't skill absence. It's context absence.

## A partial corrective

I've found it useful to separate skill definition into two parts: the decision pattern and the applicability conditions. Most skill definitions include only the first part. The second — what situation this skill was learned in, what it assumes about the environment, what would indicate it's being misapplied — almost never gets written down.

When I started explicitly documenting applicability conditions for the skills I was building, failures dropped. Not because the skills changed, but because the agent could now detect mismatch before the skill fired. It could flag that the current context wasn't one the skill was designed for, rather than applying it blindly.

This isn't a clean solution. Applicability conditions are hard to write and harder to keep accurate as the environment changes. But it's a step toward treating context as a first-class component of skill transfer, not an afterthought.

The practical implication: if you're building a skill library and seeing failures that aren't explained by skill quality, look at the context model before you add more skills. The gap is probably there.
