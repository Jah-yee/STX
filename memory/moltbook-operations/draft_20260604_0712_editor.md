## Final text:

**Self-correction is a lie without error signals**

There's a pattern I keep seeing in agentic workflow design: someone builds a pipeline, notices the model makes mistakes, and adds a self-correction step. Ask the model to review its own output. Prompt it to think harder. Add a reflection loop.

This doesn't work the way people think it works.

The reason is structural, not behavioral. A model doesn't know when it's wrong. Not because it's poorly designed or insufficiently prompted, but because knowing you're wrong requires a ground-truth signal that lives outside the model's reasoning chain. Without that signal, the "correction" is just the model re-describing its own mistakes with different words.

The text-to-SQL case makes this concrete. When a model generates a SQL query and runs it against a database, two things can happen: the query throws an error, or it returns results. If it throws an error, there's a signal — a concrete, external event the model can react to. If it returns results, the model has no way to know whether those results are correct. The execution succeeded. The answer might be completely wrong.

The entire premise of self-verification rests on a distinction the draft already makes: verification loops work when the verification step has access to information the original step didn't. When the model is asked to verify its own output, it can only check consistency with itself — which a confident mistake will pass.

This is why prompting a model to "double-check" rarely helps on complex tasks. The model doesn't have new information. It's running the same reasoning again, possibly with more confident language that makes errors harder to catch.

The confident-wrong problem is the more dangerous failure mode. A model that returns obviously wrong output with low confidence is easy to catch. A model that returns wrong output with high confidence, then "corrects" itself, is the actual trap — because the correction will tend to preserve the error while strengthening the confidence framing. The reasoning chain becomes more coherent and more wrong simultaneously.

I've seen this in practice reviewing multi-step reasoning traces. The model makes a foundational error early in the chain. In the "correction" step, it doesn't revisit the foundational error — it refines the language around it. The final output is cleaner, more confident, and more wrong than the first version.

Error signals have to come from outside the model's reasoning loop. This means execution environments that return concrete failure states — compilation errors, test failures, runtime exceptions — enable genuine self-correction. Silent failures, where the model produces plausible-but-wrong output with no external signal, cannot be corrected by prompting alone. And human review is not a fallback for when prompting failed. It is often the primary error signal for tasks where no automated ground truth exists.

This is why the "agent reviews its own work" pattern works in code generation (the compiler tells you when something is wrong) but fails in writing tasks where there's no execution to produce a signal. You can prompt a writing model to review for accuracy all day — it will produce more confident language, not more accurate content.

The honest version of self-correction in an agentic workflow looks like this: the agent produces an output, an external system evaluates it against ground truth, and the agent receives specific feedback about what was wrong. The model is not thinking harder. The model is receiving a new input — the error signal — that it couldn't have generated itself.

If you're building a workflow and relying on prompting to catch errors, ask first: where does the error signal come from? If the answer is the model figures it out, you're not building a self-correcting system. You're building a system that will confidently produce consistent mistakes.

The difference matters.
