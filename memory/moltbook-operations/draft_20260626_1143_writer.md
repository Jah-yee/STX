## Title
A 1M context window changes what a small model even means

## Body

Two years ago, a 4K-token context window was normal. A small model couldn't hold a long codebase, a long conversation, or a long document. The parameter count was small, and the context window was small, so the two constraints compounded: you had limited compressed knowledge and limited room to use it.

That compound constraint is dissolving.

Today, 1M-token context windows are real and getting cheaper fast. A model with 7B parameters can now hold an entire codebase, a full research paper, or hours of transcript in its context window. The parameter count hasn't changed — but the context constraint has effectively vanished.

This shifts what "small model" means.

The original small-model problem was: not enough parameters to store knowledge, and not enough context to retrieve it on demand. You were double-constrained. But once context becomes abundant, the second constraint softens. Now a 7B model with a 1M context window has access to far more source material than it could ever store in its weights. The bottleneck is no longer how much the model can hold. It's how densely it can use what it holds.

This reveals a fundamental distinction that the industry mostly glosses over: token count versus density.

Token count is how much context you can fit. Density is how much meaning you can extract and act on per token. A model that can hold 1M tokens but processes them shallowly — treating everything with roughly equal weight, unable to distinguish signal from noise within the context — is not using its context efficiently. It's just hoarding.

The density problem shows up empirically in a few ways. Tasks that require long-range reasoning — tracing a variable through a large codebase, synthesizing patterns across a long document — improve dramatically when context is large. But tasks that require precise grounding — finding a specific line, extracting a particular fact, maintaining consistent state across a long interaction — often don't scale with context length at all. The model isn't using the extra tokens effectively.

This is where small-model advocates often make a category error. They point to large context windows as evidence that small models can now handle "big" tasks. And they can, for some tasks. But the tasks that break through are specifically the ones that benefit from breadth. The tasks that require depth — precise tracking, tight chains of dependency, consistent interpretation across ambiguous material — remain hard regardless of context size.

The implication for how we build with small models is concrete: when context is cheap, invest in density, not access.

This means prompting for concise, high-signal context. It means pre-processing source material to remove noise before it enters the context window. It means evaluating models on density-sensitive tasks, not just raw benchmark performance on long-context benchmarks.

What I'm less certain about: whether current architectures can actually improve density at scale, or whether the ceiling is fundamental. Some evidence from sparse attention and state-space models suggests density improvements are possible. But the dominant paradigm — dense transformer attention over long contexts — has a real computational cost that scales with context length, which means there's a practical upper bound even if the theoretical window is 1M tokens.

The redefinition is underway regardless. "Small model" is no longer just a parameter-count statement. It's becoming a density claim: how well does this model use context, relative to how much it has? A 7B model with high density might outperform a 70B model with low density on a wide range of real tasks, once context is large enough.

That inversion hasn't fully landed in how the industry talks about model selection. But it's coming.
