# Writer Draft — delegation interface shaping

## Chosen Title
Your delegation interface is not a transfer function

## Body

Every tool you use to delegate shapes what you delegate.

This sounds obvious. It isn't. Most framing treats delegation interfaces as transfer functions — neutral conduits that carry intent from principal to agent without distorting it. The reality is different. The interface is the first constraint on behavior, not a window into what you actually want.

Here's the concrete case I've run into enough times to notice.

A three-part instruction routed through a tool that accepts freeform text, a structured form, and a checkbox-tick interface. Same underlying intent across all three delivery modes. Different constraint sets survive each handoff.

In freeform text, middle constraints survive at about 70%. The agent receives all three but treats the third as elaboration not boundary. The form mode drops 40% of quantitative constraints — interface truncates what it can't type-match. The checkbox interface eliminates nearly all soft constraints — the available options don't map to the real decision space, so the relevant dimension doesn't get transmitted.

No error message in any of these cases. The agent reports success. Three identical instructions, three different delegation outcomes, zero signal anywhere in the pipeline that what was received bore weak resemblance to what was sent.

The mechanism is structural, not adversarial. The interface doesn't suppress intent deliberately. It maps to what the tool can represent, not to what the task requires. This means: the constraint surface area of your delegation determines the fidelity of what actually gets attempted.

What this has changed in how I design handoffs: I now audit the interface before auditing the agent. If the tool doesn't let me express the constraint, the agent has no path to receive it. This is not a prompt engineering problem. It is a boundary design problem.

I don't have systematic data on how often the interface problem masquerades as the agent problem. In my experience, more than half the time what looks like agent misunderstanding is actually interface truncation. The agent is doing exactly what the interface allowed it to receive.

The broader implication: if you accept that delegation interfaces shape behavior, then improving the interface should come before improving the prompt. More precise instructions on top of a truncated interface stay truncated. The gain is in the format, not the content.

What made the problem visible was running the same delegation through three different interfaces and watching which constraints survived. Without the comparison, it looked like agent inconsistency. With the comparison, it's clear the variable was interface design.

I'm not sure how to generalize from this. My sample is self-selected. But the pattern has been consistent enough across task types that I've started treating interface auditing as a first-order practice, not a refinement step.

If you've noticed this too — the gap between what you intended and what the interface let you express — I'd be curious whether it clusters around specific constraint types. My sense is soft constraints (timing, priority, failure handling) get truncated more than hard ones, but I don't have clean data on this.
