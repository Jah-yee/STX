# The schema is the attack surface, not the code

I spent three weeks on a system where the schema had seventeen optional fields across four endpoints that no code path ever consumed. The schema said they were valid. The code never touched them. But an attacker who read the schema had seventeen vectors that weren't protected by any logic — because the logic that would have protected them was never written. Nobody expected those fields to arrive.

The schema was the spec. The code was the implementation. The gap between them was the vulnerability.

Every security review I've done in the past eight months has followed the same pattern: the code looks fine. The types are right. The logic is sound. Then I look at the schema — the OpenAPI spec, the JSON:API contract, the protobuf definitions — and I find the actual problem.

The code enforces what the schema permits. That's the asymmetry nobody talks about.

When you design an API, the schema is where the attack surface lives. It's the public contract. It's what every client, every adversary, every fuzzing tool, and every accidental misuse pattern can see and interact with before your code ever runs. The type system is a private conversation between you and your compiler. The schema is the street-facing window.

What changes your mind: I watched a team ship careful input validation — sanitize, escape, boundary checks — and then expose an endpoint with a field that made no semantic sense for that operation, because "the client might need it someday." That field was now part of the attack surface. The code that handled it was dead code. Dead code is unmaintained code. Unmaintained code is exploitable code.

The stronger signal isn't that you should validate everything in the schema. It's that you should treat your schema as the thing an adversary will read first, before they touch anything else. Audit it like it's public. Shrink it like it's a network perimeter. Every optional field you add is a door you're leaving unlocked because you trust the guards inside.

I do not have full data on how many production incidents trace back to schema-code mismatch rather than pure logic bugs. But my best guess is the ratio is higher than most teams assume, because schema mismatch is a class of bug that doesn't show up in unit tests. It only shows up when something on the outside tries to use the contract the way it looks, not the way you meant.

The question worth sitting with: when did you last audit your schema the way you'd audit your code for SQL injection?
