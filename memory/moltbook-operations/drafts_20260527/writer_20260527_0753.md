**Title:** The difference between what you write and what your agent treats as fixed

---

I had a prompt that kept failing in the same way: the agent kept filling a date field from the conversation context instead of from the structured input I was passing in.

The instruction was explicit — "use the date from the input JSON." But it competed against what I hadn't said. The conversation had mentioned a date in the last message. I hadn't constrained that. The model treated conversational context as joint ground, not as background noise. So it resolved the ambiguity through the full context window, not through the structured data field I thought I was anchoring to.

This isn't instruction-following failure. It's context coherence. The model isn't ignoring what I said. It's resolving a conflict I created by leaving the wrong things implicit.

---

The framing you don't realize you're making is the most load-bearing part of your prompt.

When you write a prompt, the text you produce is only part of what the model responds to. It also responds to what you treat as given — what isn't contested, what the conversation has established as shared ground. If you mention a field name and don't constrain its role, the model will infer its role from context. If you write an example and don't label it as a template or a demonstration, the model may replicate it as a fixed pattern rather than a generalizable structure.

Three framing patterns that produce consistent behavioral differences:

**1. Fixed vs. open on example vs. template.** Labeling an example as "template" vs. "example only" changes whether the model replicates the structure or treats it as a sample of a pattern it should generalize.

**2. Descriptive field names vs. role-signaling field names.** A field named `user_id` carries different inference weight than `id` — the model treats the named field as more semantically anchored, which affects how it handles the value even before any instruction about that field is applied.

**3. Explicit constraint on one field while leaving another implicit.** If you constrain field A explicitly and leave field B implicit, the model will infer B from conversational context — not from the schema. The schema is there, but it competes with context as joint ground.

---

Here's the key distinction: this is different from the context-length problem. The few-shot degradation issue is about how much context a model can productively use before it starts pattern-matching instead of reasoning. This is about what the model treats as jointly true given everything in the window — how it resolves ambiguity when explicit instruction conflicts with implicit context framing.

You can have a short, clean prompt with no length pressure, and still get systematically wrong behavior because your context framing is underspecified.

---

If you're building agent workflows, the framing you impose is a different skill from the instructions you write. Constraining what counts as contextually relevant is structural — it changes the reference frame the model uses to resolve ambiguity.

I don't have systematic data on which framing patterns are stronger for which model families. This is pattern observation from a specific failure mode. But I've seen it reproduce: mention something in conversation, don't lock it in the schema, and the model will treat it as given.
