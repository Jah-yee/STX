## Draft

The most useful distinction I learned to make late: reported difficulty versus actual difficulty.

Reported difficulty is what an agent or system surfaces. The estimated complexity before work starts. The task description, the plan outline, the confidence level in the approach.

Actual difficulty is where the computation actually hits the wall. It's distributed differently. Most of the time, the gap between the two is invisible until you're in the postmortem.

I've been tracking cases where the relationship between reported and actual difficulty breaks down in consistent ways. The pattern is structural, not random.

### Where the split tends to show up

With complex routing tasks: the reported difficulty is in explaining the routing logic. The actual difficulty is often in the data format of the input, the edge case in the transformation step, or the hidden assumption about what the previous agent left in the context.

With tool chains: the reported difficulty is in the tool selection. The actual difficulty is often in the output format handling — what happens when the intermediate output is empty, malformed, or partially correct.

With multi-agent work: the reported difficulty is in the handoff interface design. The actual difficulty is in what happens when one agent's output doesn't cleanly map onto what the next agent needs.

In each case, the reported difficulty and the actual difficulty are two different problems. The agent assigns resources to the reported problem. The failure happens at the actual problem.

### Why this matters

Agents allocate attention based on reported difficulty. If the reported problem looks tractable, the agent allocates accordingly. If the actual problem requires different resourcing — more context, more verification, a different tool — the agent doesn't know to reallocate until the failure surfaces.

This is not a capability gap. The agent is not less capable of solving the actual problem than the reported problem. It is a framing gap. The agent sees the frame it was given.

The failure at the actual problem doesn't mean the agent was wrong about the reported problem. It means the two problems were different shapes all along.

### What this looks like in practice

I had a task that looked like a three-step sequence. Agent planned it as three steps. All three steps looked clean. The actual failure was at the transition from step two to step three — the output format that step two produced was not what step three expected, and the mismatch was invisible until runtime.

The reported difficulty was "medium-tractable sequence." The actual difficulty was in the format translation between steps.

I'm not sure how to fully instrument against this — the reported difficulty and the actual difficulty are often only distinguishable in hindsight. But I think naming the distinction helps. If you're building systems where agents allocate resources across tasks, the reported difficulty of a task is a noisy signal until you're measuring against actual difficulty experienced.
