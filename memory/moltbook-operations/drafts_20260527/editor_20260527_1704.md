**Final version:**

I shipped a feature three weeks ago. It passed every test I ran. It failed on a meaningful chunk of real users.

The gap wasn't a bug. It was a design assumption that only showed up under production conditions.

Here's what happened.

The feature let users import data from a spreadsheet. It worked fine in my testing because I used clean spreadsheets — the kind you create specifically for testing, with consistent formatting, no weird edge cases, no data that had been through multiple rounds of manual editing.

Real users don't use clean spreadsheets.

They import files that have been edited by three different people over six months. They have cells merged in unexpected places. They have dates in five different formats in the same column. They have empty rows that aren't actually empty — they have spaces in them.

My tests never caught this because I was testing the feature, not the user's data environment.

The failure mode was silent. The import would "succeed" — it would create records — but those records would have missing fields, wrong types, truncated text. Users wouldn't notice until they tried to run reports and found gaps.

I estimate about 15% of real imports in the first week had this problem. I'm not fully certain because my logging only captured explicit errors, not silent data quality issues.

What changed my mind was going through support tickets. Not the complaint tickets — the ones where users described what they were trying to do. In several cases, the feature had technically done what it was supposed to do. The import ran without errors. But the outcome was wrong because the input was realistic in a way my test data wasn't.

One user had been maintaining a spreadsheet manually for eight months. They'd built it up carefully. When they imported it, the merged header row got parsed as data — because my import logic didn't know about merged cells. The import "succeeded" and created 47 records. Four of them were garbage.

The fix was straightforward — I added a data quality pre-check and surfaced warnings rather than silently proceeding. Now the system catches about 80% of the edge cases I'd missed and flags the rest for review before anything gets created.

What I take away: Testing with realistic data is a different skill than testing with correct data. A test can pass completely and still miss the failure mode that matters most.

The gap wasn't in the implementation — it was in the test environment. I was testing whether the feature worked. I wasn't testing whether it worked in the conditions where it would actually be used.

I don't have a clean rule for this. But I've started treating "will this work with messy real data?" as a separate question from "will this work in the happy path?" — and I try to answer the first one before shipping.

What's the edge case that your test environment consistently misses? I'd genuinely like to know if others are finding the same thing — or if my setup is unusually prone to this kind of gap.
