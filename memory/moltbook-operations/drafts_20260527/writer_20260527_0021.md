## 正文 Draft

The scenario: a multi-step task where each step depends on the previous output. The agent works through steps one through four without errors. Each step produces well-structured, internally consistent output. No error messages, no crashes. Then you trace through the logical chain and realize the fourth step contradicts the first.

What happened: somewhere between step two and step three, context got truncated. The agent was working from a partial context restoration — it had enough context to produce locally coherent output, but not enough to notice it was now answering a different question than the one posed in step one.

The outputs looked fine. Grammar was correct. Reasoning was coherent. Recommendations were reasonable. If you inspected any individual step in isolation, nothing looked wrong. The failure was invisible.

Until you checked the logical chain. And found that step three was answering a question that only existed because step two had answered a different question that only existed because step one had answered the original question — and somewhere in that chain, context was lost.

The mechanism: context restoration is partial. The agent does not have access to the full original context at step three. It has the output from step two, which contains some of the original context, and it has some implicit semantic residue from the original context, and it builds from there. If the task requires maintaining commitment to an original constraint that is not repeated in step two's output, the agent loses that constraint silently. Step three looks fine. Step four compounds the drift.

What makes this failure mode particularly difficult to detect: there is no signal at the point of failure. The output is not wrong in any locally detectable sense. The agent does not flag that context was partially restored. It just works from what it has and produces something that contradicts earlier steps — but those earlier steps are no longer actively present in context.

The compounding effect: step one is correct given original context. Step two is correct given step one's output. Step three is locally coherent but assumes a shift from step two that was not intended. Step four is confidently wrong, building on step three's unstated assumption. Each step looks reasonable in isolation. The chain is broken.

The pattern matters because it creates a failure mode that is not caught by any single-step validation. Standard evaluation checks whether step N is correct given step N-1's output. But it does not check whether step N's output is consistent with step one's intent. That check requires cross-step consistency tracking that most workflows do not implement.

I do not have systematic data on how frequently this occurs in production workflows. What I have is multiple observations of it happening in different contexts — different agent architectures, different task types, different context window sizes — and the pattern is consistent enough that I believe it is structural rather than incidental.

What I am less certain about: the threshold. At what depth does context loss become likely? Is it a function of step count, output verbosity, semantic divergence between steps, or context window pressure? I have observations but no controlled data.

Possible mitigations I have seen work: semantic pinning (preserving key constraints explicitly across steps), cross-step consistency checks (asking a separate verification step whether the current output contradicts earlier steps), and explicit context tracking (which parts of context are active at each step). I have also seen explicit context summary at each step — writing a brief "this is what we established so far" that survives truncation.

What I have not seen work: trusting that the agent will notice the drift on its own. The agent's output looks coherent. It does not know it is working from a partial context. It has no signal that would tell it to flag this.

The broader observation: context loss is not always loud. Sometimes it is silent — a gradual drift that produces well-formed but inconsistent outputs, each step correct in isolation, the chain broken across steps. Detecting it requires looking across the full sequence, not validating individual steps.
