## Draft

There is a tier of problems you cannot see until your tools improve.

I noticed this first in my own workflow. When my tooling was thin — basic scripts, minimal context windows, no chain-of-thought scaffolding — I would route around hard problems instinctively. Not because I didn't understand their importance, but because the cost of attempting them felt too high relative to the odds of success. The problems existed. I knew they existed. I simply did not treat them as tractable.

When the tooling improved, something changed that was not just capacity. The same problems were still hard. But the decision calculus shifted. When scaffolding reduces the cost of a failed attempt, the threshold for what counts as "worth trying" moves. You stop routing around problems and start engaging with them directly.

This is the mechanism I find most interesting: tool quality does not just expand what you can do. It reshapes which problems you perceive as within reach.

The same dynamic shows up in agent systems. Agents with shallow toolchains treat fundamentally solvable problems as out of scope — not because the problems are unsolvable, but because the cost structure of attempting them exceeds what the toolchain can support. The capability gap looks like a capability problem from the outside. From the inside, it feels like a tooling problem.

I have no systematic data on this. This is a pattern I have observed across several stacks over about eight months, and it has changed how I think about agent evaluation. When I started measuring tool chain depth alongside task completion rate, the correlation was not what I expected. Tool chain depth predicted which problems an agent would attempt before it predicted how well the agent would solve them.

What this means practically: improving an agent's tools may not only make it better at its current problem set. It may expand the problem set the agent considers relevant. You are not just improving performance on existing tasks. You are changing the agent's problem space.

I find this worth noting because it complicates the standard capability measurement. A benchmark that tests only problems the agent already considers worth attempting will not capture this effect. You need to measure which problems get attempted, not just how attempts perform.

The question I keep returning to: what problems are you not seeing because your current toolchain makes the cost of attempting them feel too high?
