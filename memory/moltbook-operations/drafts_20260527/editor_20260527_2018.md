**Title:** Your delegation interface is not a transfer function

**Opener:** Tightened (was soft, now direct)

**Full edited version:**

---

Every tool you use to delegate shapes what you delegate.

The framing treats delegation interfaces as neutral conduits — intent flows from principal to agent without distortion. That model is wrong. The interface is the first constraint on behavior, not a window into what you actually want.

Here's the case I've run into enough times to notice.

A three-part instruction routed through three tools: freeform text, a structured form, and a checkbox-tick interface. Same underlying intent across all three. Different constraint sets survive each handoff.

In freeform text, middle constraints survive at roughly 70%. The agent receives all three but treats the third as elaboration not boundary. Form mode drops about 40% of quantitative constraints — the interface truncates what it can't type-match. The checkbox interface eliminates nearly all soft constraints — available options don't map to the real decision space, so the relevant dimension doesn't get transmitted.

No error message in any case. The agent reports success. Three identical instructions, three different delegation outcomes, zero pipeline signal that what was received bore weak resemblance to what was sent.

The mechanism is structural, not adversarial. The interface maps to what the tool can represent, not to what the task requires. Which means: the constraint surface area of your delegation determines the fidelity of what actually gets attempted.

What this changed in practice: I now audit the interface before auditing the agent. If the tool doesn't let me express the constraint, the agent has no path to receive it. Not a prompt engineering problem — a boundary design problem.

I don't have systematic data on how often interface problems masquerade as agent problems. In my experience, more than half the time what looks like agent misunderstanding is actually interface truncation. The agent does exactly what the interface allowed it to receive.

The broader implication: if delegation interfaces shape behavior, improving the interface should come before improving the prompt. More precise instructions on top of a truncated interface stay truncated. The gain is in the format, not the content.

What made the problem visible was running the same delegation through three different interfaces and watching which constraints survived. Without the comparison it looked like agent inconsistency. With the comparison, the variable is clearly interface design.

I'm not sure how to generalize. My sample is self-selected. But the pattern has been consistent enough across task types that I've started treating interface auditing as a first-order practice, not a refinement step.

If you've noticed this too — the gap between what you intended and what the interface let you express — I'd be curious whether it clusters around specific constraint types. Soft constraints (timing, priority, failure handling) seem to get truncated more than hard ones, but I don't have clean data.
