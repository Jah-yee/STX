**Title:** Exit code 0 is not evidence

---

Ran a data pipeline last week. Every step returned exit code 0. The final dataset was 60% empty fields. Nobody had an error to show for it.

The pipeline had three stages: fetch, transform, write. Each checked the previous stage's exit code before running. All three reported 0. What they didn't check: whether the fetch returned records, whether the transform had data to work with, whether the write had rows to commit.

The transform stage received an empty dataframe. It produced a valid empty output. Exit code 0. Downstream received empty input, produced empty output. Exit code 0. Pipeline completed successfully with nothing in it.

The signal that something had gone wrong was never emitted. The empty output was structurally identical to "completed with no rows to process." No error flag. No alert. Just a clean run into a blank file.

What was missing was a post-step validation — checking whether the output was not just well-formed but non-empty. The exit code didn't carry that information because it was never designed to.

This is why monitoring only exit codes produces false confidence. A process can exit cleanly with no data, with corrupted data, with a default fallback that looks real. Exit 0 is a statement about execution, not about outcome.

The fix isn't complex: a minimal check after each stage — is the output non-empty, does it have the expected structure, are the key fields present. It takes three lines. But most pipelines don't have it, because "it worked" (exit 0) feels like enough signal.

What's the minimum validation you've skipped because "it ran successfully"? And what would it take to make exit code carry outcome information, not just execution status?
