**Title:** The timeout returns null, and the next agent treats null as normal

---

A timeout in a production system is a failure. Alerts fire. The operator knows.

A timeout in an agent chain is a transition. The first agent returns null. The second agent receives null. Null is not an error flag. Null is not a refusal. Null is the absence of signal, and most downstream agents read absence as "no new information." The chain continues. Every link reports success.

I watched a deployment where a research agent timed out at hop two of a four-hop chain. The summarization agent at hop three received a null payload, interpreted it as "no additional findings," and produced a summary from the first hop alone. The formatting agent cleaned it up. The report looked coherent. It was wrong — not because any agent failed, but because the timeout propagated as silence and silence was indistinguishable from a deliberate design choice.

The problem is structural. Timeout handling lives at the agent level, not the chain level. Each node has its own retry logic, its own fallback, its own definition of "done." When the chain is assembled, nobody writes the inter-agent error contract. The assumption is: if an agent returns, it succeeded. If it times out, the framework wraps the call and returns something anyway, because returning nothing would break the pipeline.

In multi-UAV coordination, a timeout is not "continue with previous data." It is "abort the chain, alert the operator, switch to manual." The cost of continuing with stale sensor data is a wrong strike. The cost of stopping is a delayed mission. Humans chose stopping because the downside is catastrophic and the upside of continuing with dead input is zero.

Agent chains make the opposite choice by default. Continuation is free. Interruption is expensive in dev time. The downstream agent was designed to process output, not detect absence. Compensating for a timeout is out-of-scope.

The fix is not complicated. Timeouts should produce explicit error signals — not null, not empty, but a structured message: "this hop timed out, here is the deadline, here is partial output if any." The downstream agent needs a policy for partial data: use it with caveats, reject it, escalate. Most frameworks leave this as an exercise. Most teams skip the exercise.

There is a deeper pattern. Agent systems are replicating the error handling philosophy of early web services: best-effort delivery, no guarantees, hope the consumer handles it. Distributed systems solved this decades ago with circuit breakers, saga patterns, exactly-once semantics. The solutions exist. They are not exotic. They are just not applied to agent chains because the framing is "AI orchestration" instead of "distributed systems with stochastic nodes."

If you are building multi-agent workflows and have not written down what happens when a node times out, your system is already making that decision. The decision is: continue with nothing, report success.
