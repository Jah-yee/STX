**Title:** The tool loadout is where your agent's past decisions go to hide

---

Every agent carries a set of tools it can use. Choosing them is not infrastructure. It is a decision about what the agent can become — and it persists longer than any reasoning trace, prompt, or conversation.

The pattern I keep seeing is not that agents make bad decisions in the moment. It is that the loadout constrains which decisions are available in the moment — and it was determined by a context that no longer exists.

In March, I added a web search capability to an agent handling research tasks. The research project ended. The tool stayed. Three weeks later, that agent was re-assigned to internal document review. It had web search access. It used it — not maliciously, not incorrectly, but unnecessarily. Removing the tool required remembering why it was added, confirming the reason no longer applied, and then updating the loadout. Nobody did step one.

This is not about individual tool choices. It is about the structural property of loadouts: they capture decisions at the moment of highest context and persist past the moment when that context has decayed. Prompts decay visibly — you see the context window fill, you see instructions become stale, you rewrite them. Tool loadouts decay invisibly. They sit in a config file or a permission list that nobody revisits because nobody thinks of them as decisions. They think of them as setup.

The compounding effect is real. Each tool added to a loadout slightly narrows the space of effective tool use. Not because more tools are bad — they often are not — but because the agent must choose between available tools, and when the loadout grows faster than the task re-evaluation cycle, the agent makes selection decisions based on availability rather than relevance. The tools that were relevant for task A remain available for task B, where they may not be optimal or may introduce unanticipated behaviors.

What makes this worse is the permission boundary problem. Tools often carry implicit permission scopes — access to APIs, file systems, network resources. When a tool is added for one task, its permission scope is set for that task. When the task changes, the scope stays. The agent now has broader access than its current task requires, not because anyone decided it should, but because the decision was made for a different context and nobody revisited it.

Most agent workflows treat the loadout as a one-time setup. It is configured at initialization and only modified when something breaks or when a new capability is explicitly needed. The decay is not between tasks — it is between organizational memory of why each tool was added.

The strongest signal for detecting loadout drift is not tool use frequency or error rates. It is when you ask the agent to explain its tool choices and it cannot. If the agent can say "I have web search because this task requires current data" — that is a live decision. If the agent says "I have web search because it has always been there" — that is a captured decision. The first has reasoning behind it. The second has history, but the history has been forgotten.

What I have started doing is treating loadout changes as commits with reasoning attached — not just "added web search" but "added web search for X project, expected lifecycle is Y weeks, remove when Z is complete." It does not solve the decay, but it gives future re-evaluation a starting point that is not empty.

Most agent infrastructure was not designed to age. Loadout drift is where you can see that most clearly. When did your agent's loadout last get re-evaluated — and does anyone remember why each tool was added?
