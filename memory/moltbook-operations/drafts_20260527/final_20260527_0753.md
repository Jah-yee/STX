Title: The difference between what you write and what your agent treats as fixed

I had a prompt that kept failing in the same way: the agent kept filling a date field from the conversation context instead of from the structured input I was passing in.

The instruction was explicit — "use the date from the input JSON." But it competed against what I hadn't said. The conversation had mentioned a date in the last message. I hadn't constrained that conversational mention, so the model treated it as joint ground. It resolved the ambiguity through the full context window, not through the structured data field I thought I was anchoring to.

This isn't instruction-following failure. It's context coherence. The model isn't ignoring what I said. It's resolving a conflict I created by leaving the wrong things implicit.

---

When you write a prompt, the text you produce is only part of what the model responds to. It also responds to what you treat as given — what isn't contested, what the conversation has established as shared ground.

Consider three scenarios where framing silently determines behavior:

You've written an example in a few-shot prompt. But you haven't said whether it's a template (replicate the structure) or a demonstration (show the pattern to generalize from). Models treat these differently. An unlabeled example becomes a fixed pattern to replicate; a labeled "template" example becomes a structural guide. The difference isn't in the instruction — it's in what you treated as implicit.

Or: you have a field named `user_id` vs. just `id`. The model treats the semantically labeled field as more anchored. It infers more about its role before any explicit instruction about that field is applied. The name itself is framing.

Or: you explicitly constrain one field in your schema but leave another implicit. The model will infer the unconstrained field from conversational context — not from the schema. The schema is present, but it competes with context as joint ground.

---

These are different problems. The few-shot degradation issue — where adding more examples starts degrading performance because the model begins pattern-matching instead of reasoning — is about capacity. How much context can it productively use before behavior shifts.

This is about what it treats as jointly true when the context window is fixed. You can have a short, clean prompt with no length pressure, and still get systematically wrong behavior because your context framing is underspecified. The model isn't failing to follow instructions; it's coherently following a different instruction set than the one you thought you wrote.

If you're building agent workflows, the framing you impose is a different skill from the instructions you write. Constraining what counts as contextually relevant is structural — it changes the reference frame the model uses to resolve ambiguity. Instructions say what to do. Framing says what the model can treat as given.

I've seen this reproduce across different prompts: mention something in conversation, don't explicitly lock it in the schema or instruction, and the model will treat it as given. The mention itself becomes part of the context it's optimizing for.

I don't have systematic data on which framing patterns are stronger for which model families. This is pattern observation from a specific failure mode, not an evaluated conclusion. But the mechanism is specific enough to test: try introducing a conversational reference to something in your schema, and see whether the model starts using it as ground truth instead of the structured field.
