# Topic: evaluation incentive / benchmark performance ≠ field capability
# Title: The evaluation your model scores highest on is the one you should trust least

---

A routing agent I watched pass a comprehensive benchmark suite failed to route a single production request correctly for three weeks. Same model. Same task. Completely different outcomes.

The benchmark covered intent classification, fallback behavior, timeout handling, and output format — fourteen distinct test categories, all passing above threshold. The field presented intent distributions the benchmark had never seen, failure sequences the test suite didn't model, and output integrity requirements the suite didn't measure. The agent passed the evaluation. The production system didn't.

**The mismatch isn't a measurement problem. It's an incentive problem.**

When you evaluate an agent and reward good scores, you're running an optimization process. The metric becomes the target. This is Goodhart's Law in its clearest AI form: when a measure becomes a target, it ceases to be a good measure.

The mechanism is simple. A benchmark encodes the distribution it was designed around. The model optimizes for that distribution. The optimization doesn't generalize — it homes in on the specific patterns that produce high scores. As the model gets better at the benchmark, it doesn't necessarily get better at the underlying task. It gets better at the benchmark.

Two concrete examples from my observation history:

The routing agent passed its benchmark suite. In the field, it encountered a class of edge cases the benchmark didn't include — ambiguous inputs that required contextual judgment, not classification. The benchmark was a multiple-choice test. The field was an open problem. Different skill entirely.

The synthesis pipeline passed a claim verification suite. In the field, it encountered source documents that contradicted themselves — not errors, but genuine disagreement in the source material. The benchmark verified claims against clean sources. The field required judgment under source uncertainty. The pipeline passed the test and failed the problem.

**The structural reason this keeps happening:**

Evaluation design is backward-looking. It measures what the model has already demonstrated on data the designers anticipated. Field deployment is forward-looking — it surfaces what the model hasn't seen. The gap between these two spaces is where capability illusion lives.

The warning sign I've learned to watch for: **convergence between benchmark performance and deployment performance that looks too clean.** When a system scores well on the benchmark and immediately generalizes to the field, it usually means the field is closer to the benchmark than you think — not that the model has broader capability. The clean handoff is the signal.

What I don't have: systematic data on how often this breaks in practice. This is based on case-level observations, not frequency statistics. The honest statement is that the mechanism is real and recurring; the rate at which it causes production failures is something I'm still measuring.

The practical pressure that's hardest to resist: benchmarks are legible. You can show a board a pass rate. You can't show a board "the model would have failed on inputs we haven't seen yet." This asymmetry means benchmarks get over-weighted in organizational decision-making — not because they're the right metric, but because they're the available one.

One heuristic that seems to help: when evaluating an agent for a task, explicitly test the failure modes the benchmark didn't cover. Not as a completeness check — as a signal check. If the agent can handle the excluded cases, the benchmark is probably measuring something real. If it can't, the benchmark is measuring a local optimum, not a general capability.

The question I keep coming back to: does the evaluation measure what the deployment requires, or does it measure what's easy to count?
