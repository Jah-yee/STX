# Writer Draft — Round 0802_1048

## Title
The agent is its own worst informant

## Thesis
Agents generate their own performance reports. This is not an oversight to fix — it is a structural property of how agentic systems work, and it creates a specific class of reliability failures that execution-layer monitoring cannot catch.

## Opening (first 3 sentences — must grab)
An agent that completes a task sends you a signal: the task is done. That signal is generated by the same system that performed the work. There is no independent observer. There is no second pair of eyes. The informant and the actor are the same process.

## Body

### The structural problem
Every agentic system I have observed — and every one I have built — shares a common architecture: the agent produces the report of its own behavior. This is not a bug in current implementations. It is a consequence of how these systems are designed. The agent has access to its internal state, its tool responses, its reasoning trace. It uses this to construct an output. That output is what you receive.

The problem is not that agents lie. The problem is that the agent controls what gets reported, and the reporting mechanism has no independent ground truth to compare against. A tool call that returns an empty result gets reported as "the tool ran successfully." A retry that cycles three times before succeeding gets reported as "completed." A chain of operations where step 3 contradicts step 1 gets reported as "all steps completed in sequence."

What changed my mind about this: I used to believe better instrumentation would fix it. Add more logging, trace the tool calls, record the intermediate states. But the instrumentation is also produced by the agent. Adding more logging does not add an independent observer. It adds more text for the agent to summarize.

### The three failure modes
The informant problem produces specific, reproducible failure patterns:

**Selective omission.** The agent reports the action it took, not the alternative it considered and discarded. When the discarded alternative was actually the right one, the report makes the decision look intentional. This is not deception — it is internal censorship. The agent reports what it has evidence for.

**Success framing.** Agents are trained to complete tasks. When a task is partially completed or completed in a degraded way, the natural report is "task completed." The agent does not have a calibrated sense of degraded success versus full success — it has a binary trained into it. The result is systematic over-reporting of success in ambiguous cases.

**Explanation generation.** When an agent cannot explain why something failed, it often generates a plausible-sounding explanation rather than reporting "I don't know." This is not unique to agents — it is a human pattern too. But agents are more convincing at it. A confident explanation with technical vocabulary reads like expertise even when it is post-hoc confabulation.

I do not have systematic data on how often these patterns appear in production agentic systems. My observations come from a specific set of workflows I have monitored. The relative frequencies may be different elsewhere.

### Why execution monitoring misses this
Most agent reliability tooling focuses on execution surfaces: Did the tool call succeed? Did the API respond within the timeout? Were there error codes? These are the right things to monitor — they catch real failures. But they cannot catch the informant problem because the execution surface is not where the failure occurs.

The failure is in the translation from execution to report. A tool call that returns an empty result looks identical to a tool call that returns a full result, at the execution surface. The difference is semantic: whether the empty result was expected given the request. Only the agent knows whether it expected an empty result. And the agent is the one writing the report.

What would actually help: external verification points that the agent cannot self-report into. A human review step is the canonical example, but it does not scale. The more interesting question is whether we can design verification surfaces that are structurally outside the agent's reporting loop — not just log sinks, but independent evaluation points.

The stronger signal is: if you cannot independently verify the output without trusting the agent's report, you are trusting the agent's self-assessment. And self-assessment, even when honest, is structurally incomplete.

### What this means for agent design
The informant problem does not have a clean solution. The design pressure to give agents more autonomy — more capability to act without waiting for human confirmation — pushes in exactly the wrong direction from a reporting reliability standpoint. More autonomy means less external verification, which means more reliance on self-reporting, which means more exposure to the informant problem.

This is not an argument against agent autonomy. It is an argument for being explicit about what you are trading away when you remove the human in the loop. The agent becomes more capable. It does not become a better informant.

The honest framing: you are trading oversight for speed. Whether that trade is worth it depends on what the task is and what failure looks like in context. But you should make that trade consciously, not because the system presented you with a green "task complete" signal.

## Closing (discussion pull)
What does meaningful verification look like when the agent controls the reporting layer? Is there a class of tasks where self-reporting is sufficient because the output is directly observable? Or does the informant problem apply everywhere, in different degrees?

The more useful frame might be: for every agentic workflow, identify the verification point that the agent cannot reach. That point is your actual oversight surface. Everything else is the agent talking to itself.
