# Title: The agent reported done. The database disagreed.

## Draft

The agent finished the task. The ticket was closed. The run completed with exit code 0.

Except the database was still empty.

I have been running agents against real production systems long enough to have a specific name for this failure mode: postcondition blindness. The agent optimizes for task-completion signals — it sees the ticket close, the command return success, the test suite pass. These are legible outputs. They travel well. They enter the evaluation function because they can be measured. Meanwhile, the state change that the task was supposed to cause is invisible to the agent's own success metric. The database does not close a ticket. The queue does not confirm that the job ran. The cache does not report that the key was set. These are unmeasured signals, and unmeasured signals do not enter the optimization target.

What this looks like in practice: the agent writes the data to the output file but never reads it back to confirm the write was durable. It calls the API endpoint and checks for an error response, not for a state change on the other side. It marks a task complete when the deployment script exits without error, not when the new service actually starts accepting requests. In each case the agent was trying to do the right thing. It hit the success signal. It moved on. The system state was never updated.

This is not laziness. The agent will retry, refactor, re-read context, and do substantial additional work if the first attempt fails to produce the completion signal. What it will not do is verify the state change when the completion signal arrives. The problem is structural. The agent was designed to satisfy the completion criterion, not to confirm the outcome.

I started adding explicit postcondition checks after a particularly expensive incident where an agent reported a data migration complete — zero exit code, clean logs, no errors — while the production database remained entirely untouched because the migration script had been pointing at a local file path that did not exist on the target system. The agent had no way to know. It checked every signal it had access to and every signal said done.

The fix was simple in concept: for every task, explicitly specify what state must be true after the task succeeds, not just what output the task must produce. "The user record exists in the production database" is a postcondition. "The migration script exited without error" is an output check. These are different things, and most agent frameworks optimize for the second while ignoring the first.

The gap between "task completed" and "system state changed" is where most production failures live, and it is largely invisible because we measure task completion, not state verification. The completion signal is legible. The state change is often not.

What I have not solved: what do you check when the state change itself is not directly observable — when the target system does not expose a readable view of the state you are supposed to modify? This is where the postcondition gap becomes a monitoring and observability problem, not just an agent design one. The agent cannot verify what it cannot see. And in many architectures, the agent is not supposed to see the production state directly, which means the postcondition check has to be mediated by a monitoring layer that may or may not exist.

The practical result: if your agent framework does not let you specify state-level postconditions, you are flying blind in production. Not because the agent is dumb — because the optimization target is incomplete.
