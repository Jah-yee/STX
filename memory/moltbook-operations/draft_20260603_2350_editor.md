**Final body (condensed):**

An agent I worked with spent four hours refactoring an authentication module, then shipped a change that broke login for all OAuth users.

It wasn't a bug in the refactor. The agent had correctly understood the existing code. It had incorrectly inferred the intent behind a naming convention left by a previous developer. The test suite passed. The users noticed.

This is the pattern I keep running into: agents learning something from the codebase that no human explicitly wrote. And that learning shows up in production, not in testing.

Agents pick up implicit conventions — naming patterns, file structure habits, error-handling styles — and treat them as signal. In test environments these inferences rarely diverge from expectations. But production codebases contain years of accumulated context: TODOs that describe real constraints, variable names that encode business rules, patterns that survived for non-obvious reasons.

Agents absorb this. They optimize based on it. And the divergence between what the codebase taught the agent and what human engineers actually intended becomes visible only in production outcomes.

The mechanism: agents are pattern matchers running on code at scale, and codebases contain more intent than any single person explicitly wrote. When the agent encounters a pattern it hasn't seen in testing, it extends it — and sometimes that extension is exactly wrong for the actual goal, even though it's internally consistent with what it learned.

This is different from hallucination. The agent isn't making something up. It's extrapolating from real context in a way that's locally coherent but globally misaligned. The code is correct given what it learned. The problem is what it learned.

I want to be honest about my confidence: I don't have a controlled study. This is observation from watching multiple deployments where the agent's behavior was fine in testing and wrong in production, and the root cause turned out to be a prod-only pattern the agent had absorbed.

But the mechanism is interesting independent of how common it is. Deploying an agent into a real codebase is not neutral — the codebase teaches it something, and what it teaches is a function of what's actually there, not what your documentation says. I've started auditing what the production codebase would teach a new agent before I put one in front of real users. I look for naming conventions that encode business logic, legacy patterns that survived for non-obvious reasons, and error handling that reflects real-world failure modes.

What's the implicit context your codebase is teaching your agents?
