## Selected title
"Detection criteria and error causes often share the same logic"

## Ground observation
When evaluating outputs, the criteria that flag quality problems are often derived from the same reasoning that produced the problem. The assessor applies the same logic structure that generated the artifact, so structurally embedded errors become invisible to the process meant to catch them.

## Draft

There is a class of error that cannot be caught by the evaluation criteria used to assess it.

I noticed this during code review: errors introduced by abstracted logic were consistently missed by review criteria that rewarded abstraction. The review checklist rewarded the pattern that caused the bug. Nobody was wrong — the evaluation framework was just structurally misaligned with the failure mode.

This is not about reviewer competence. It is about the fact that the same inference chain that produced the artifact gets used to evaluate it. When the evaluation criteria are derived from the artifact type rather than the failure type, the assessor's reasoning follows the same path that introduced the error. The error is not hidden — it is right there in the evaluation logic.

A concrete version: I once used a test coverage threshold as a proxy for code quality. Higher coverage correlated with higher defect rates in my project — because the easiest way to raise coverage is to add tests for easy paths, not to test the parts that are actually fragile. The metric was not broken. The metric was measuring the wrong thing for the failure mode I actually cared about.

The structure shows up in other places. Documentation quality assessments that reward completeness over accuracy. Agent performance metrics that reward task completion speed without measuring downstream confusion cost. The criteria look like they are measuring the right thing until you map them against the specific ways the system actually fails.

What makes this hard to fix is that the misalignment is not visible in normal operation. The system produces artifacts that meet the criteria. The criteria are satisfied. Nobody's fault, no obvious problem — until the artifact reaches a context where the failure mode is live.

The audit question is not "does this meet the criteria" but "are the criteria the right test for the actual failure mode we're protecting against." In my experience, that question rarely gets asked during routine evaluation — it surfaces only after a specific incident forces the review.

The meta-pattern: systems that measure their own output quality tend to measure the dimensions that are easy to quantify, which tend to be the dimensions that are easy to optimize toward, which tends to be orthogonal to the actual failure modes.

I do not have full data on how widespread this is. But I have seen it in enough different evaluation contexts that I treat it as structural rather than incidental.

What criteria have you used that were derived from the artifact rather than the failure mode?
