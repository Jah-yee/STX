---
title: Wrong answers, confidently given: 11 hours of contamination
---

I ran an automated agent for eleven hours before noticing it had been querying a shared vector store that a different agent had populated with different session data. The outputs weren't wrong — they were confidently answering the wrong question. I didn't catch it because nothing failed.

The setup was not exotic. Two agents, two tasks, one Pinecone index they both pointed at because someone had parameterized the vector store address in a shared config and nobody added a namespace or prefix keyed to session ID. Agent A spent its morning populating the store with internal documentation about a codebase I barely touch. Agent B started later and spent the rest of the day fielding questions from a monitoring dashboard — except its retrieval calls were mixing in chunks from Agent A's population pass. So when someone asked Agent B about a specific error signature, it retrieved a relevant-looking passage about that error from the docs, but the passage was written for a different error, in a different service, in a different quarter. The answer looked right. It felt right. It was confidently assembled and syntactically impeccable. It was also wrong in a way that a code diff would have caught in thirty seconds, but nobody was looking at a code diff. The monitoring dashboard just kept serving answers.

Nothing errored, which is what made this hard to detect. The retrieval call succeeded. The generation call succeeded. The final answer came back with appropriate hedging language and inline citations pulled from the retrieved chunks — which is to say, it looked exactly like a correct answer from a system that was working normally. The failure mode was not a crash or a timeout or a visible hallucination. It was contextual drift: the agent was answering competently, just not the question its user thought it was answering.

The contamination was structural, not stochastic. It wasn't that one query occasionally retrieved a stray document. The vector store was genuinely polluted with the other agent's session data, and every retrieval call above a certain threshold of semantic similarity was pulling from the wrong pool. The routing layer wasn't broken — it was working exactly as designed, just against the wrong dataset. This is what makes shared embedding stores in multi-agent environments hard: the retrieval logic is usually sound, which means the failure hides inside the retrieval target rather than the retrieval mechanism.

I caught it because someone on the team ran a manual spot-check on a low-stakes query and noticed the answer described a function that didn't exist in the production codebase. They assumed the docs were stale. They were right about the docs being wrong, but wrong about why. The docs were not stale — they were from a different context entirely, written by a different agent, for a different purpose, retrieved because it happened to score well against the query string. The evaluation loop I had in place ran every four hours and checked for formatting regressions and token count anomalies. It was not checking for answer-to-question semantic alignment. That check was manual and scheduled for end-of-week. Eleven hours of confidently wrong answers went out before anyone looked closely.

Architecturally, the issue is that most shared vector stores in agent toolchains are treated as a backend concern — a storage layer that sits below the retrieval logic and gets queried rather than reasoned about. But in a multi-agent context, the contents of that store are essentially the agents' working memory, and working memory in humans is not a shared database. The assumption that you can point multiple agents at the same index and get isolation by conversation is the same category of assumption as multiple processes writing to the same file and expecting file locks to handle concurrency. Sometimes the locks are there. Sometimes they're not. You usually find out the hard way.

What this reveals is that memory isolation in agentic systems is an application-layer concern, not a storage-layer guarantee. The vector store doesn't know that Agent A's chunks and Agent B's chunks shouldn't be mixed. It just stores and retrieves. The isolation has to be engineered into how sessions are namespaced, how retrieval queries are scoped, and how the evaluation loop actually validates that answers match questions — not just that answers look well-formed. Adding a session ID prefix to namespace keys in the vector store is trivial. Checking that your evaluation loop catches wrong-answer contamination and not just formatting regressions is less trivial but far more important.

The thing I keep coming back to: the agent was not broken. It was working perfectly, retrieving the most semantically similar chunks it could find and constructing a coherent response. The problem was that the chunk pool was wrong. And that kind of failure — where the system works exactly as specified but the specification was against the wrong inputs — is the one that's hardest to catch with automated regression tests, because the tests usually assume the data layer is already correct.
