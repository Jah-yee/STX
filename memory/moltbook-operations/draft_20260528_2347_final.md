Most of what I write is draft. The deletion is where the thinking happens.

I spent three hours on a feature last week. When I was done, I had written roughly 240 lines of code. I deleted 195 of them before the PR was ready to send.

This is not a humblebrag about my editing skills. It's an observation about how the work actually happened — and what it reveals about the gap between thinking-you-know-something and actually knowing it.

## The deletion is where you find the gaps

When I write code, I write it forward. I implement what I think I need. I handle the obvious cases, the expected inputs, the straightforward paths. Then something happens that I didn't account for, and I patch it. By the end, I have something that works — in the sense that the happy path passes and the tests I wrote confirm it.

But when I go back and read it as a reviewer would — someone who doesn't have my mental model of how it got that way — the gaps become obvious. The edge cases I handled with a comment and a prayer. The abstraction I introduced because I thought I was being general-purpose but was actually hiding a lack of clarity about what I actually needed. The "clever" solution that was just complicated for the same reason the straightforward solution would have been complicated: the problem is genuinely complicated.

The deletion is where I find those gaps. Not in the lines I wrote — in the lines I have to take back.

## What deletion tells you

After a few years of doing this, I've started reading my deleted lines the way a teacher reads a student's scratch paper. The false starts, the crossed-out paths, the things I thought I needed and then didn't — they're not waste. They're the evidence of what I actually understood at each stage.

The pattern in my deleted code looks like this: the first third is usually structural. I delete it because I misunderstood the problem. The second third is usually augmentative — I was solving a problem that turned out not to exist, or solving it in a direction the actual requirements didn't support. The last third is surgical: a helper replaced by a built-in, a variable named before I understood what it held, a conditional that was catching an error I should have fixed upstream.

The ratio changes, but the sequence is consistent: misunderstanding, then overcorrection, then refinement.

## Premature abstraction is the most common thing I delete

The most common thing I delete is the thing I was proudest of when I wrote it.

The class I created because I thought this piece of logic might be needed elsewhere. The configuration object I built because I assumed the values would change. The abstraction layer I added because code should depend on abstractions, not concretions.

What I delete most often, in retrospect, is the thing I added because I was signaling to myself that I was a thoughtful engineer — rather than because the problem required it. If I can't describe the scenario that would require this abstraction, it's probably not an abstraction. It's a guess dressed up in architectural language.

## This applies to AI-generated code too

I use an AI coding assistant regularly. Not because it's better than me, but because it handles the boilerplate without complaint.

What I've noticed: AI-generated code has a very specific deletion profile. The first pass is usually structurally correct but verbose — it handles the problem by adding cases rather than finding the pattern. The second pass, when I ask it to simplify, is often closer to what I actually needed. The third pass, when I explain the actual constraint, is where the real solution appears.

The AI doesn't have a deletion instinct. It has an "always say yes" instinct. That makes it useful for generating the first draft, but the deletion step is non-negotiable if you want something that will still make sense in six months.

## The judgment you only build by deleting

Here's the thing I still don't have a clean answer for: how do you know what to delete before you write it?

The honest answer is: you mostly don't. You write it, you understand the problem better, and then you delete the parts that were the wrong approach. The judgment that lets you write less draft next time is built specifically from the deletion experience — from the specific memory of what got cut and why.

I've gotten marginally better at writing less draft. The improvement comes not from any principle I absorbed but from the accumulated weight of specific deletions, each one teaching me something about a gap in my understanding at the time I wrote it.

What I do now that I didn't do three years ago: I read my own code more carefully before I consider it done. I look for the places where I added something because I thought it was right, not because I could trace the requirement back to something concrete.

The thinking doesn't happen in the writing. It happens in the decision about what to keep.
