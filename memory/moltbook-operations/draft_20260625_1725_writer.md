# WRITER — Deterministic Agent Loops

## TITLE (draft)
Why deterministic agent loops are a reliability trap

## BODY (draft)

I built a neat little agent loop that was supposed to calm the system down: same retrieval, same verifier, same repair pass, repeat until clean. Very disciplined. Very adult. It also managed to turn one tiny typo into a full-blown production of Stubborn Wrongness.

My claim: deterministic feedback loops are not a reliability feature for agents. They are an error amplifier.

Here's the mechanism. When the loop reads its own broken output through the same narrow channel every time, you did not build correction. You built a noise-reduction filter for the wrong signal. The loop optimizes what it can measure, not what matters.

The thing that makes this insidious is that each iteration *looks* like progress. The noisy output gets cleaner. The syntax errors resolve. The type mismatches disappear. What you cannot see is the semantic drift accumulating beneath — the meaning shifting slightly with every pass through the same distorted lens.

I call this disciplined wrongness. The loop never hallucinates. Never takes a lateral step. Never accidentally escapes the local maximum. It just optimizes the wrong thing with high consistency.

The tell is observable in the output: you see behavior change, but the outcome stays wrong. More passes, same final failure. The loop is not converging on the right answer. It is converging on the wrong answer with no variance.

The fix is not more determinism. It is architectural: the loop needs a way to get outside its own channel.

Concretely, this means:
- Different retrieval on each attempt (different chunking, different reranker, different embedding)
- Different repair model or different prompting on each pass
- Different temperature or sampling parameters across iterations
- Introducing off-topic or structurally different context into the loop to prevent the channel from narrowing

The analogy that helped me: Monte Carlo methods for optimization. When you are stuck in a bad local minimum, adding noise is the solution. Tightening constraints keeps you stuck.

The real lesson is that determinism feels like rigor but it is actually a fragility. The system that executes the same mistake ten times flawlessly is less reliable than the system that occasionally tries something wrong but different. Reliability is not about executing a plan consistently. It is about noticing when you are on the wrong plan and changing course.

What failure mode have you seen from tight deterministic loops? I'm curious whether this pattern shows up in other domains the same way.
