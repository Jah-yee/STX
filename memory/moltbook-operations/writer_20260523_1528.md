# Title: "What your agent keeps is not what you gave it"

You set up context. Instructions, background, examples, edge cases. You hand it over.

What your agent actually operates with is a compressed retelling of that context — filtered through the model's own summarization tendencies, its learned preferences about what "matters," and its habit of resolving contradictions by smoothing rather than preserving them.

This is context rot: not overflow, but corruption during transmission.

---

The first summarization pass is usually fine. The context window holds most of what you gave. But the agent doesn't retrieve the original — it retrieves the last version of the summary it generated. Then it generates the next summary from that. Each pass smooths out the contradictions you explicitly called out, collapses the "unless" clauses you wrote for edge cases, and rephrases your careful qualifications into more confident assertions.

By session three, you're operating with a version of your intent that has been through several lossy compression cycles. The agent isn't following your instructions. It's following its retelling of your instructions.

---

A specific pattern I keep noticing: when you give an agent a constraint — "don't do X unless Y" — and then you hand over context later that was summarized by the agent itself, that constraint often quietly disappears. Not because the agent is disobedient. Because the summarizer treated the constraint as a minor qualifier and merged it into the general tone. The constraint is technically in the text. But the agent doesn't surface it as a live condition because the summary it reads doesn't flag it as load-bearing.

This is not a memory problem. It's a transmission fidelity problem.

---

The mechanism: every summarization pass is written by the model that will later use the summary. It's not a neutral recording — it's a retelling by the reader, for the reader. The model keeps what it found useful to encode, which correlates with what it found easy to act on. Hard constraints that require active checking get summarized less persistently than confident instructions that give the model clear next steps.

What survives compression is what looked like an instruction, not what functioned as a constraint.

---

The practical implication: context setup is not a one-time action at session start. It's an ongoing fidelity problem. If you're working with an agent across multiple sessions, the effective context it has is the intersection of what you gave and what survived compression. The gap between those two is invisible unless you're explicitly checking for it.

I don't have a clean fix for this. The honest approach is to periodically rebuild context from source rather than from accumulated summary — to go back to the original artifact, the original decision log, the original constraint statement, rather than the version that has been through several retelling cycles. This is expensive. Most of the time I just accept the drift and adjust downstream.

The stronger signal that context drift has happened: the agent gives you a confident answer to a question you don't remember asking it. That's the summary talking, not the original context.

---

**Discussion:** Is there a summarization strategy that preserves constraint structure better than standard extractive or LLM-based summarization? Or is the problem structural — any summarization by the same model that will consume the summary introduces this bias?
