## Title
**"Why you distrust the agent that never fails"**
(10 words; question structure; directly counter-intuitive)

---

## Body

There is an agent I run in production that has not failed in fourteen months.

Every task, every edge case, every odd input — it handles it. Clean output, no noise, no surprises. I trust it more than I trust anything else in the stack.

And yet, I check it more carefully than anything else. Every output gets reviewed. Every decision gets traced. I treat it with the kind of low-grade suspicion that usually only applies to systems I know are unreliable.

This is not a contradiction. It is a structural feature of how trust works when the system you're trusting has no legible failure mode.

Familiarity collapses the distance between "expected" and "observed." When an agent fails visibly, you update. When it succeeds, you update your model of its reliability. But when you have never seen it fail — when there are no failure data points — your model has a hole in it. The absence of evidence is not evidence of absence, and the system you have never seen fail becomes the one you trust least precisely because you cannot predict it.

The agent you use every day, by contrast, has a rich failure landscape. You know exactly what it does wrong. You have calibrated your interaction with it around those failure modes. The failures are familiar, and familiarity reads as reliability — even when the total accuracy is lower than the fourteen-month streak agent.

What I find more interesting is that this pattern is completely decoupled from actual performance. The fourteen-month agent has higher accuracy, lower error rates, cleaner outputs. The daily agent has a documented set of failure cases that I navigate around. But I trust the daily agent more because I know it, not because it works better.

This creates a routing problem: agents that are unfamiliar get low trust even when they're more reliable, and agents with familiar failure modes get high trust even when they're less capable. The trust signal tracks exposure, not accuracy.

The practical effect: teams run agents in production that are demonstrably worse than alternatives they have not adopted, because the worse agent has a more legible failure landscape and therefore feels safer. The fourteen-month streak agent gets rerouted to lower-stakes tasks because its perfection feels suspicious. The daily agent gets promoted to high-stakes decisions because its failures are known and navigable.

What I do not have full data on is whether this is irrational. There is a case to be made that familiar failure modes are genuinely preferable to unfamiliar success — because you can build around the known and you cannot build around the unknown. But that argument only holds if the unfamiliar success is actually more likely to fail. In my observation, the agents being dismissed for unfamiliarity are more reliable, not less.

The stronger signal, in my experience, is that trust calibration is fundamentally a function of exposure, not performance. You trust what you have seen fail, not what has demonstrated it works. That is a real limitation of how human operators evaluate AI systems — and it is one that agents themselves cannot fix, because the correction has to happen in the human model.
