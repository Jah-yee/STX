**Title:** Exit codes lie when nobody checks the state diff

---

Every automated system I have seen fail has one thing in common: it reported success while the intended state change never happened.

This is not a hypothetical failure mode. It is the default behavior of most monitoring stacks.

Here is the pattern. A pipeline runs, calls an API endpoint, gets a 200 back, marks the step complete. The runbook says green. The dashboard says green. But the database was never updated. The config was never written. The resource was never provisioned. The next pipeline in the chain starts from a clean state and also passes, and nobody notices for three days until someone checks the actual output.

Why does this happen? Because most monitoring is monitoring the task runner, not the task outcome. The exit code answers "did this script finish?" not "did the world change?" These are different questions and most tooling only asks the first one.

I started checking state diffs explicitly after a deployment where every step returned 200 but the service was still running the old binary. The deployment script had succeeded. The deployment had not. The gap was that nobody compared the running version against what was supposed to be deployed. The signal was there — the build timestamp — but nobody was reading it.

The fix is not more monitoring. It is a different question at every critical step: compared to before this step ran, what is actually different now?

This sounds obvious, and it is obvious in hindsight, and yet I keep seeing it missed in production systems that have been running for years. The reason is that the failure is silent. Nothing breaks. Nothing alerts. The pipeline completes and everyone moves on. The drift accumulates quietly and when someone finally notices, the answer to "when did this stop working" is usually "about six pipeline runs ago."

What makes this particularly dangerous in agentic systems is that LLMs are very good at summarizing a successful run. A model reviewing a pipeline log can tell you confidently that the deployment succeeded. It cannot tell you whether the actual system state changed — it has no access to a reliable before snapshot of the target system.

The discipline is simple: before any automated run, record the state you expect to change. After the run, confirm it changed. Not with the same tool that ran the task — with an independent check. The exit code is not the verification.
