You used to fix bugs. Now you triage behavior.

The switch happens gradually, then all at once. One day you're debugging code you wrote. A few months later you're interrogating a chain of tools to figure out which one went off-script — and whether the off-script behavior was a feature, a hallucination, or a third thing you don't have a name for yet.

This is the new dominant failure mode in AI-assisted development. Not the bug in your code. The gap between where your code ends and the AI behavior begins.

---

## What the triage layer looks like in practice

Last month I spent four hours debugging a pipeline that was failing in production but not locally. The failure was real — the output was wrong — but the chain of intermediate calls made it genuinely unclear which component introduced the error. Was it the agent that called the wrong tool? The tool that returned a structurally valid but semantically wrong response? The eval that passed the output because it was checking the wrong property?

None of these are bugs in the traditional sense. There is no line of code to fix. There is a system state that drifted from expected behavior through a series of decisions that individually looked reasonable.

The maintenance burden has shifted from "find the broken code" to "reconstruct the decision tree that produced this outcome." This is a fundamentally different skill. Code-fixing is causal. Triage is probabilistic — you work backwards from effect to probable cause, with incomplete information and no clean stack trace.

---

## The specific mechanism that makes this hard

AI tooling failures compound differently than code failures because the outputs are non-deterministic in a way that pure software isn't. A retry might fix it. A retry might produce a different wrong output. The signal you use to debug — the output itself — is produced by the same system you're debugging.

This is different from traditional debugging where you can set a breakpoint and inspect state in isolation. Here, the inspection changes the system. Asking a model to explain its chain of decisions changes what the next call does.

The practical consequence: the hardest debugging problems in AI tooling aren't "why did this fail?" They're "which one of these seventeen steps did what, and was any of it right?"

---

## The triage mindset shift

What has worked for me: treat AI-assisted pipelines like distributed systems debugging. You assume multiple plausible causes and run experiments to rule them out. You look for invariants — things that should be true regardless of which path the model took. When invariants break, you work from the break point backward.

The harder adjustment is accepting that you often won't have a clean answer. The model made a call that looked reasonable in context but produced a semantically wrong result. You can identify that it happened. You can often route around it. You usually can't explain it in a way that generalizes.

But the systems are getting more layered. The question isn't just "which tool malfunctioned?" anymore — it's "which agent in the stack made the call that set the downstream state?"

This is the debugging mode I'm in more often than not lately. The code I wrote still works. The gap is somewhere above it.
