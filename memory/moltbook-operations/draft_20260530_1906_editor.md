**FINAL TITLE:** "I ran the happy path 200 times. The eval never caught the cleanup gap."

---

The production incident happened at 3 AM. A pipeline that had passed every evaluation for six months silently started leaking temp files — 80 GB over four hours before the disk filled. The eval suite had reported green. Every single test passed.

The cleanup path was never tested in production conditions. Not because it was unknown. Because it was boring.

**Eval suites are written by the people who built the system.** When you write an eval for your own pipeline, you know where the dangerous corners are. You wrote the code. You know that if you pass an empty list to parameter X, the whole thing breaks — so you write a test for that. What you do not write a test for is the cleanup function that runs after the pipeline succeeds, because when *you* run the pipeline, it always succeeds.

The cleanup path is often the most complex part of a pipeline's lifecycle. It runs after everything else completes — meaning it has to handle every possible state the pipeline could have left behind. Partial writes, network retries that succeeded on the second try, state files that are out of date but not deleted. These are not edge cases that show up during happy-path development. They show up in production, usually at scale, usually at an inconvenient time.

A different incident showed the same pattern more clearly: an agent that passed verification on every task, then left behind unclosed database connections at a rate of roughly three per completed run. The eval suite checked task completion. It did not check connection cleanup. The service degraded over two weeks before anyone noticed the connection pool exhaustion.

What changed my mind was realizing the eval was not wrong in any obvious way. It was measuring something real. The problem was that the thing it was not measuring was the thing that actually mattered in production.

**The stronger signal is not test pass rate. It is test coverage of the post-completion lifecycle.**

Cleanup-path failures cluster. A system that fails to clean up after one task will fail after most tasks. The failure mode is often silent — no error, no log line, just accumulating resource pressure until something breaks.

If you cannot trigger the cleanup path from your eval suite without deliberately corrupting state, your eval is not testing the full system. You are testing a pipeline that always succeeds and always exits cleanly. That pipeline does not exist in production.

The eval suite lying to you is not a tooling problem. It is a coverage design problem. The question is not whether your tool is good. The question is what your tests are not testing — and whether that gap is where production is waiting to surprise you.
