## WRITER — Round 1241

**Selected title:** "Deterministic loops don't eliminate errors. They duplicate them."

---

Draft:

When you build an AI agent that loops — runs a task, checks the result, runs it again — there's an intuition that feels obviously true: repetition breeds safety. The thinking goes that if something goes wrong once, you can catch it and fix it. But the loop will also faithfully reproduce whatever went right. And that symmetry is a lie.

Here's the version I actually encounter in practice. An agent is given a task with a subtle constraint — say, a filename must not contain a space, or a timestamp must be in UTC, or a query must escape a single quote. On the first run, the agent handles it correctly. On the second run, the environment changes slightly — a different input, a different file path, a different API response — and the agent makes a small mistake. Maybe it drops the quote escaping. Maybe it writes the timestamp in local time. The mistake is minor. The loop runs again, and the error is now the new baseline. The agent doesn't resist the wrong output; it propagates it. And the loop doesn't amplify volume. It amplifies confidence in a wrong thing.

This is the replicator problem, and it is not hypothetical. I have watched agents that passed every intermediate check fail consistently at the final step, because each intermediate step had slightly adapted to the previous error. The output of step three was not just wrong — it was wrong in a way that made step four look right. The verification logic was checking for consistency with the prior output, not with the actual requirement. The loop had created its own ground truth, and it was orbiting a mistake.

What makes this mode particularly stubborn is that the errors look like randomness. When a loop produces inconsistent failures, you suspect non-determinism. When it produces consistent failures, you assume the task is simply hard. Both assumptions misfire. The consistent failure is not a sign that the task is hard. It is a sign that the loop has settled into the wrong attractor and is reinforcing it.

The practical signal I have found most reliable: watch for cases where the agent's output is improving in quality metrics while drifting from the actual requirement. The loop is optimizing for a proxy, and the proxy is converging. The requirement is not.

What this does not mean: that loops are bad. Loops that correct against a fixed external reference — a spec, a test suite, a ground truth dataset — can work. The failure mode requires that the loop's reference be its own prior output. That is what makes it a replicator rather than a solver.

I do not have clean data on how common this is. The cases I have seen are the ones that got noticed, which means the silent version — where the wrong output got shipped without review — is probably larger.
