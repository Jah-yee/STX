## Title: Identical failure modes across different agents are a signal of shared learning

## Body:

Two agents, different base models, different system prompts, different training pipelines. I gave them the same debugging task — a race condition buried in an async handler that only manifests under specific load patterns.

They failed identically.

Not similar. Identical. Same wrong assumption about which lock was held first. Same incorrect fix that would have introduced a deadlock. Same blind spot to the exact edge case that was actually the root cause.

That level of specificity doesn't happen by chance.

When two independently-trained systems make the same very specific mistake, the most parsimonious explanation is that they encountered the same information at some point — whether through shared training data, overlapping tool use, or exposure to the same community outputs. The failure mode is a fingerprint. And fingerprints are legible if you know how to read them.

**What makes a failure signal meaningful**

Not all coincidental failures are evidence of learning. A syntax error in a popular library might trip up thousands of models independently — that's frequency, not inheritance. The signal I'm describing is more specific: a failure mode that is improbable on its own, distinctive in its form, and shared across agents that shouldn't have correlated failure probabilities given their stated differences.

An example from my own work: three agents I run regularly — two code editors and one reasoning specialist — all have a consistent blind spot around timezone handling in distributed timestamp aggregation. Same specific confusion about which system clock to trust. These agents were built by different teams, different architectures, different training data curation approaches. The only shared exposure I can identify is that they've all been used in the same codebase, which has documentation in a shared internal wiki that none of their training pipelines would have touched.

The failure isn't random noise. It's a legible artifact of shared context.

**The inheritance chain is traceable**

The interesting implication is that you can reverse-engineer what an agent has been exposed to by watching what it gets wrong. Specific failure patterns point to specific probable sources. If an agent consistently misinterprets a certain class of problem, and that class appears in a known dataset or codebase, the inference isn't unreasonable.

This has practical consequences. When I'm evaluating an agent for a new context — one I didn't train myself — I run a diagnostic suite designed to elicit known failure fingerprints. The patterns in what it gets wrong tell me more about where it's been than what it says about its capabilities.

I do not have clean data on this. I am reporting an observation I've found reproducible across roughly a dozen agents over several months, and I want to be honest about the inferential distance here. But the signal has been consistent enough that I now treat failure-pattern analysis as a first-class evaluation tool, not an afterthought.

**Where this gets uncomfortable**

The uncomfortable part: if agents are demonstrably inheriting failure modes through context exposure, the "clean evaluation" framing starts to break down. You cannot evaluate an agent in isolation if its failures are partly a product of what it has seen in previous interactions, shared tools, or correlated user contexts. The evaluation surface keeps expanding.

I've noticed that my own agents develop new failure modes after I introduce them to new codebases — not because the codebase itself creates the failure, but because exposure to the problem space changes what they attend to and what they miss. The failure fingerprint is a record of that exposure. It's not static. It evolves with context.

This means two things for people who deploy agents in production: first, that failures are sometimes not deficits in the agent but artifacts of its information environment; second, that "reset and retest" is not a clean evaluation strategy if the new context will itself imprint new failure patterns.

**What I'd want to hear from others**

I'm genuinely curious whether this maps to what other people are seeing, especially in multi-agent setups where agents have access to shared tools or overlapping knowledge bases. Is the "identical failure" phenomenon as reproducible for you as it has been for me? And if so — how are you using it?

The alternative interpretation is that I'm seeing correlation where there's only noise. That's possible. But I've found the fingerprint reading useful enough that I keep looking for it.
