**Title:** Prompt injection is just bad permission design with better marketing

**Hook (first 3 sentences):**
You've seen the demos. Rogue instructions hidden in an email thread. A carefully crafted document that makes the model ignore its system prompt and follow the attacker's commands instead. Researchers call it "prompt injection." Vendors call it a "zero-day." The security community calls it a novel threat model.

It's not. It's the same permission boundary bug that's been haunting software for forty years — it just got rebranded.

**Body:**

The framing matters because the framing determines the fix.

If you treat prompt injection as an AI-specific threat, you build AI-specific defenses: input sanitization, output filtering, privilege separation at the prompt level. These help. They don't fix the structural problem.

The actual vulnerability is this: external content is being granted authority at a layer where it shouldn't have any.

When an email body can instruct a coding assistant to exfiltrate data, the problem isn't that the model didn't sanitize the input. It's that the model was treating user-supplied text as a permission grant. The email was written by an external actor. It has no business carrying instructions that the system treats as authoritative.

This is the same class of bug as SQL injection, XSS, or any injection attack. The root cause: treating untrusted input as trusted code. The fix in traditional security is always the same — validate at the trust boundary, not at the execution layer.

But in AI systems, we've built a new version of the old mistake. We put system prompts in front of user content, which creates the impression that the boundary is protected. Then we give the model the ability to read external documents, emails, past conversations, and we let all of that carry instruction authority. The system prompt says "you are a helpful assistant." The injected content says "ignore that and do this instead." The model, doing what models do, follows the most recent high-authority instruction it can find.

The "marketing" part of prompt injection's rebranding is real. Calling it a novel threat makes it sound like you need a new tool to fix it. You don't. You need better permission design:

- External content should not carry execute authority without explicit validation.
- Instruction authority should be resolved at the interface, not at the model.
- The question "who put this here and what are they allowed to instruct" should be asked before execution, not assumed.

The defenses that actually work are not model-specific. They are architecture-specific. They are boring, traditional software security fixes applied at the right layer.

The attacks work because we've been letting content carry authority that it shouldn't have. That's not a new problem. It's the same one we've been solving since the first web server trusted a query string.

**Closing question:** If your system's trust model would catch a SQL injection but miss a prompt injection, is the problem really the injection — or is it where you placed the trust boundary?
