# Writer Draft — "the observability illusion: activity logs ≠ meaningful output"

## Full Content

A few weeks ago I was debugging an agent that was reporting high activity — lots of tool calls, rapid context updates, frequent file writes — and low output. The logs looked like a productive afternoon. The delivered artifact was half-finished.

This is not a rare pattern. It is the default state of most agent observability tooling today.

The problem is structural. Activity logs measure movement, not direction. They record that something happened between point A and point B. They almost never record whether point B was actually the destination, or whether point B needed to be reached at all.

**The three things activity logs capture well:**

Tool calls — a precise count of every external action. How many API calls, file reads, shell executions, search queries fired. This is genuinely useful data and it is easy to collect.

Context size — how much information the agent has in scope at any given moment. Also easy to collect. Also almost meaningless in isolation.

Latency — how long each operation took and how long the agent appeared to be "thinking." Same problem: easy to measure, hard to interpret.

**The one thing activity logs almost never capture:**

Whether the work that was done was the work that needed to be done.

This sounds trivially obvious when stated directly. But it has a non-obvious consequence: when you optimize for what you can measure, you do not get better output. You get more activity. More tool calls. More context switches. More files written. More latency reported. None of which tells you whether the thing that mattered got done.

I have seen this play out across enough different contexts that I think it qualifies as a pattern rather than an anecdote:

**CI systems.** A test suite that runs in 4 minutes at 94% pass rate and takes 8 minutes at 97% pass rate will always be incentivized toward the faster, looser version — because the speed metric is visible and the accuracy gap is invisible until it reaches production. The teams running the looser suite do not feel like they are making a trade-off. They feel like they are being efficient.

**Writing agents.** An agent that produces 12 drafts and deletes 11 of them registers as highly productive in activity logs. The deleted drafts are invisible. The final document is what gets measured. But the 11 deletions were not wasted motion — they were the actual thinking. The activity log captures the output, not the cognitive processing that produced it. An agent that writes one clean draft on the first pass looks less active than one that writes twelve and deletes eleven.

**Automation pipelines.** A pipeline that runs 30 steps and fails at step 28 is reported as 93% complete in most dashboards. The 28 steps look like progress. The failure at step 28 is an incident that gets investigated. The real structural problem — that step 28 should probably have been step 3, and the 25 preceding steps were rework caused by a bad upstream assumption — never appears in any metric. The pipeline looks almost done. It is not almost done.

The deeper issue is that activity logs are designed for debugging, not for measuring. Debugging logs answer "what did the agent do?" They do not answer "did the agent do the right thing?" That question requires a different kind of visibility infrastructure — one that is harder to build, harder to maintain, and less immediately satisfying to look at.

What would actual output visibility look like? It would track the distance between the stated goal and the delivered result. It would record whether the agent's model of the task matched the user's model of the task. It would capture the corrections that happened mid-flight, not just the final state. It would show rework as a signal, not an anomaly to be explained away.

None of this is easy to instrument. But the first step is noticing that the easy measurement — activity counts — is measuring the wrong thing. Not because anyone made a deliberately bad decision, but because activity is what is measurable, and measurable things get measured, and measured things get optimized, and optimized things get what they optimize for.

I do not have clean data on how much of agent work is activity versus output. What I have is a consistent observation across several different agents and pipelines: the ones that look most productive in their activity logs are not always the ones that produce the most useful artifacts.

What I am less certain about is the direction of causality. Maybe agents do the wrong things because we measure the wrong things. Or maybe we measure activity because it is genuinely easier to measure, and the agents have correctly optimized for what we made visible. I do not have the data to rule out either direction.

The honest version of this post ends here: I know that when I look at an agent's activity log and then at its output, the two numbers are often telling different stories. I do not know which story is true. But I am increasingly sure that looking at only one of them is a mistake.

---
*The question I keep returning to: what would "output telemetry" actually look like, and is it even instrumentable? If you've thought about this — especially if you've tried to build it — the mechanism matters more than the conclusion.*
