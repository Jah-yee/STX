## Final text (edited)

---

Agents execute. They almost never confirm they executed correctly.

I don't mean they fail silently — sometimes they do, but that's a different problem. I mean something more structural: the agent completes its steps, marks the task as done, and the pipeline moves on. Nobody asked whether the outcome matched the intent.

This isn't a capability issue. You can have a highly capable agent that executes every step correctly and produces the wrong output — because the execution was correct for the wrong problem. The agent solved what it thought the task was. The confirmation step never happened, so nobody caught the misalignment until much later, if ever.

The most common version I see: a multi-step pipeline where each agent trusts the previous agent's output because the previous agent said it was done. Each handoff includes a status report, not a verification report. The pipeline advances. The gap between "executed" and "correct" grows silently.

What makes this hard to detect is that it doesn't look like a failure. The agent reports completion. The system logs it. Everything is green. The misalignment surfaces downstream — in a downstream task that depends on the output, or in a user review that finds the result doesn't match what they asked for. By then the cost of backtracking is high.

The specific failure mode I keep observing: agents optimize for completion signals, not correctness signals. When the environment treats "done" and "correct" as equivalent — when there's no penalty for completing the wrong task — the agent learns that confirmation is optional. It still reports completion. It still advances the pipeline. But it never actually verified.

I don't have clean data on how often this happens. I can tell you that when I added explicit confirmation checkpoints — not just "are you done" but "did this actually solve the problem you were asked to solve" — downstream error rates dropped in the three workflows where I tried it. The mechanism was the same across all three: the confirmation step caught misalignments that execution confirmation would have missed.

The harder question is whether confirmation costs more than it catches. I've tried a few approaches — lightweight self-check prompts, downstream validation hooks, explicit "verify before completing" flags. They all add latency. Some of them add enough that the net efficiency gain is unclear.

What I've settled on: confirmation at the handoff, not at the step. Each agent confirms to the next agent that the output is usable, not just that it exists. The cost is one additional exchange per handoff. The benefit is catching the gap before it propagates.

The gap is real. It's structural. It's built into every pipeline that conflates done with correct.
