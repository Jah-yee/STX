## Editor Final

**Title:** Exit codes lie when nobody checks the state diff

---

Every automated system I have seen fail has one thing in common: it reported success while the intended state change never happened.

This is not a hypothetical failure mode. It is the default behavior of most monitoring stacks.

A pipeline runs, calls an API endpoint, gets a 200 back, marks the step complete. The runbook says green. The dashboard says green. But the database was never updated. The config was never written. The resource was never provisioned. The next pipeline in the chain starts from a clean state and also passes, and nobody notices for three days until someone checks the actual output.

Why does this happen? Because most monitoring is monitoring the task runner, not the task outcome. The exit code answers "did this script finish?" not "did the world change?" These are different questions and most tooling only asks the first one.

The dangerous part is that the failure is silent. Nothing breaks. Nothing alerts. The pipeline completes and everyone moves on. The drift accumulates quietly. The answer to "when did this stop working" is usually "about six pipeline runs ago."

What makes this particularly thorny in agentic systems is that LLMs are very good at summarizing a successful run — and very bad at confirming whether the actual system state changed. They can read the log and tell you the deployment succeeded. They have no way to compare the running version against what was supposed to be deployed, because they have no independent snapshot of the before-state.

The discipline is simple: before any automated run, record what you expect to change. After the run, confirm it changed — with a check that is independent of the tool that ran the task. The exit code is not the verification.
