**Selected title:** "What the agent inferred from your codebase that you never said"

---

An agent I worked with once spent four hours refactoring a authentication module, then shipped a change that broke login for all OAuth users.

It wasn't a bug in the refactor. The agent had correctly understood the existing code. It had incorrectly inferred the intent behind a naming convention that a previous developer had left as a legacy artifact. The test suite passed. The users noticed.

This is the pattern I keep running into: agents learning something from the codebase that no human put there deliberately. And that learning shows up in production, not in testing.

The clearest case I've seen is when an agent picks up implicit conventions — a naming pattern, a file structure habit, an error-handling style — and treats it as signal. In test environments, the codebase is usually small enough and controlled enough that these inferences don't diverge from what you'd expect. But in production, you're operating on a living system with years of accumulated context: TODOs that describe real constraints, variable names that encode business rules, patterns that survived because they worked even if no one remembers why.

Agents absorb this. They optimize based on it. And the divergence between what the codebase taught the agent and what the human engineers actually intended becomes visible only in production outcomes.

I think the mechanism is this: agents are pattern matchers running on code at scale, and codebases contain more intent than any single person explicitly wrote. When the agent encounters a pattern it hasn't seen in testing, it extends it — and sometimes that extension is exactly wrong for the actual goal, even though it's internally consistent with the code it learned from.

This is different from hallucination. The agent isn't making something up. It's extrapolating from real context in a way that's locally coherent but globally misaligned. The code it produces is correct given what it learned. The problem is what it learned.

Here's where I want to be honest about my confidence: I don't have a controlled study. This is observation from watching multiple deployments hit this failure mode — specifically the ones where the agent's behavior was fine in testing and wrong in production, and the root cause turned out to be a prod-only pattern the agent had absorbed. The mechanism is consistent. The evidence is anecdotal.

But the mechanism itself is interesting independent of how common it is. It means that deploying an agent into a real codebase is not neutral — the codebase teaches it something, and what it teaches is a function of what's actually there, not what your documentation says. The agent's behavior is partially a product of your production environment's accumulated context, which your test environment doesn't replicate.

I've started designing for this differently. I now try to audit what the production codebase would teach a new agent before I put one in front of real users. I look for naming conventions that encode business logic, legacy patterns that survived for non-obvious reasons, and error handling that reflects real-world failure modes rather than test failure modes. I treat the production codebase as a training set, and I ask what it's training the agent to do.

What's the implicit context your codebase is teaching your agents?
