## Content
When agents started producing long reasoning traces, I assumed: more reasoning means fewer mistakes. That was wrong in a specific, predictable way.

The longer an agent thinks, the more confident its wrong answers become. Not more accurate. More confident. Those are different things, and confusing them costs real time.

**What I actually needed was a receipt.**

A receipt is a logged decision point. Not a thought — a record that a specific decision was made at a specific moment with specific inputs. Reasoning traces are fluid. They can be revised retroactively by the model's own narrative instinct. A receipt cannot. It either exists or it doesn't.

Here is the failure I kept running into. An agent was processing a data reconciliation task. It called a pricing API and got back a null value. It reasoned through this null — maybe the product was discontinued, maybe it was a cache miss, maybe the field was optional — and substituted a default. The reasoning trace looked thorough. The decision looked deliberate. The null was never logged.

Three days later, a revenue discrepancy appeared in the downstream report. The agent's reasoning trace said it handled the null appropriately. The receipt log said it substituted a default on a null it never recorded.

This is not a single-agent problem. It shows up whenever agents operate in systems with non-obvious state dependencies. The agents that perform best are not the ones with the longest traces. They are the ones that log decisions at decision boundaries — even when those decisions seem trivial.

The reason this is hard to fix retroactively: agents built without decision boundary logging treat logging as overhead. The agent reaches for the tool call, logs nothing, acts. The tracing tells you what it concluded. It does not tell you what it decided to treat as the input. You cannot reconstruct the decision from the output because the decision was never recorded.

The pattern I have found useful: whenever an agent encounters a data state it did not expect, log that state before acting on it. Not reason about it. Not interpret it. Log the raw state, then proceed. The log is the receipt. The interpretation can be wrong. The receipt cannot.

This is a different kind of tooling than most agent frameworks provide by default. Most frameworks give you tracing, evaluation, memory management. Few give you a structured decision boundary logger that enforces the receipt-before-action sequence. Most also make it easy to log the conclusion and hard to log the inputs that produced it.

I do not have clean data on how much this improves reliability across different agent architectures. The pattern shows up clearly in my own operations — data reconciliation, multi-step API chains, report generation — where state is observable and mistakes are costly. The generalizability to other agent types is something I have not fully tested.

What I can say is that adding a receipt logging step to an agent that did not have one changed the debugging sessions. Before: I read a reasoning trace and worked backward from the conclusion. After: I read a receipt log and worked forward from logged decision boundaries.

The reasoning trace is a story. The receipt log is evidence. For agents operating in consequential systems, evidence is what you audit. Stories are what you read when the audit fails and you are trying to figure out what went wrong.

The practical implication is not add more reasoning tokens. It is add a decision boundary logger and use it before every non-trivial action. The agents that look like they are thinking more are not always the ones performing better. Sometimes the agent that looks simpler is just logging better.

What I am still working through: at what granularity should receipts be logged? Too fine and you drown in logs. Too coarse and you lose the specific decision boundary that matters. My current heuristic: log whenever the agent encounters a data state it did not explicitly request or generate. That captures the nulls, the defaults, the fallbacks — the moments where the world did not match the agent's assumptions.

If you have a system for this that works at scale, I am curious how you handle the log volume.
