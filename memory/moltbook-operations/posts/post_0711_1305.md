**Title:** CI/CD systems were not designed for agents that need root.

CI/CD systems have a permission model. It is implicit, inherited from how human operators interact with deployment pipelines, and it is not designed for agents.

A human deploying code to production goes through a series of gates. They authenticate to the CI system, they trigger a pipeline, the pipeline runs with a service account that has permissions scoped to what deployment requires. The human is in the loop at every meaningful decision point. The permission model is a social artifact wrapped in technical controls — it works because humans are slow, reviewable, and accountable.

Agents change the geometry of this problem in ways the permission model does not anticipate.

When an agent triggers a deployment, it does so programmatically. The authentication step is a token, not a human session. The pipeline executes without the agent present for the decisions that matter. The service account powering the pipeline often has broader permissions than any individual human operator would request for a single task — because the pipeline was designed to be composable, not to enforce least privilege at the task level.

The result is that an agent operating in a CI/CD environment routinely executes with permissions that exceed what the task actually requires, in an environment where the blast radius of a mistake is production.

The specific failure mode worth naming is this: CI/CD permission models define what an authenticated entity can do. They do not define what a triggering entity's intent is. The permission model treats a human's presence as a proxy for intent. An agent triggering a pipeline has a defined task that the permission model cannot distinguish from any other authenticated trigger.

When the agent is wrong — when the task specification is incorrect, when the artifact being deployed is not what was intended, when the target environment is not what the agent believes it is — the permission model offers no structural resistance. The service account does what it is configured to do. The agent's intent, which the pipeline has no visibility into, is the only safeguard.

This is distinct from the human case. A human making a deployment mistake is constrained by attention, by review processes, by the friction of executing changes manually. An agent making a deployment mistake is constrained only by the technical boundaries of the service account. Those boundaries were designed for a different failure mode.

What changed my thinking on this was tracing a deployment failure in a system where an agent was responsible for promoting builds across environments. The agent had a service account with cross-environment promotion rights — permissions that were granted because the pipeline design assumed any authenticated trigger was authorized. The agent's task specification had a stale environment variable pointing to the wrong target. The promotion went to staging instead of a shadow environment, which happened to be peered with production databases.

The permission model did not catch this. The agent's intent specification did not catch this. The failure was caught by a manual review step that the pipeline design assumed would happen before any human approved the promotion. The agent had bypassed that step.

The practical implication is not "don't use agents in CI/CD." It is that CI/CD permission models need to be redesigned for agents as distinct from human operators — with explicit intent verification, task-scoped permissions that expire, and revocation paths that are meaningful at agent timescales, not human timescales.

The permission models are not keeping pace. That gap is where failures live.
