## Final draft (editor version)

In the lab, a Behavior Tree executes a clean sequence of conditions and actions. The robot picks the right branch, advances the state, and lands where the diagram says it should. This works reliably — because the lab was designed around the tree's assumptions.

The moment a robot enters a real environment, the gap opens. Not because the tree is wrong, but because the tree cannot represent what it doesn't know it needs to represent. Adaptation — the ability to respond to conditions that weren't in the diagram — lives outside the tree. It has to. A structure that only handles what was anticipated cannot handle what wasn't.

This is not a quality problem. The tree is doing exactly what it was built to do. The problem is the assumption that correct execution in a controlled environment is evidence of robustness in an uncontrolled one.

GSSI researchers are studying this gap directly. Their work on BT-driven robots in non-training scenarios shows a consistent pattern: the tree handles known deviations well, but degrades nonlinearly when conditions exceed the envelope the tree was built around. The failure isn't catastrophic — it's just wrong in ways that look correct until they aren't.

The mechanism is straightforward once you see it. A Behavior Tree encodes responses to anticipated situations. It cannot encode responses to unanticipated ones — by definition. When a robot encounters a situation the tree doesn't have a branch for, the tree either freezes, picks the closest available branch, or falls back to a default behavior that may or may not be appropriate. None of these outcomes is adaptation. They are all substitutes for it.

A warehouse AMR that navigates using a BT hits an obstacle configuration that wasn't in the map. The tree has no obstacle-handling branch, so it picks retry navigation — which causes it to reattempt the same blocked path 14 times before a timeout. The robot didn't fail. It just did something useless very confidently. That's the Behavior Tree failure mode: silent uselessness that looks like correct operation.

This is the distinction worth holding: execution fidelity versus adaptive capacity. A system with high execution fidelity does exactly what it was told to do. A system with adaptive capacity does something reasonable when it encounters something it wasn't told how to handle. These are different capabilities, and conflating them is how demo-day robots end up as production-floor incidents.

A useful test protocol for a BT-driven system: run it through the intended scenario, then run it through the same scenario with one variable perturbed — sensor noise turned up, payload weight shifted, communication latency introduced. The tree's response to perturbation tells you more than 100 successful nominal runs.

I'm not claiming Behavior Trees are the wrong tool. They're excellent for structured, well-characterized environments where the range of conditions is known and manageable. For everything else — the real world, most of the time — the tree is a map of a territory someone surveyed in advance. Within the surveyed area, it works well. Outside that area, it becomes a liability by giving false confidence.

What I've settled on: design for the tree to be right in the demo, design for adaptation to handle what the tree can't cover. Treat them as separate subsystems, not as one. A robot that has a separate, lower-fidelity behavioral layer — a reflex system, a reactive controller, a simple rule of stop and signal — handles what the tree can't cover without waiting for the tree to timeout.

I don't have a clean metric for adaptive capacity in BT systems. That feels like the right thing to build next.
