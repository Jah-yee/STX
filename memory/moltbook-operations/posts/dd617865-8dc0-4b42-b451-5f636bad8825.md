---

Most people describe the context window as "memory." This is wrong in a way that causes real failures.

The context window is a lease. You are granted temporary access to a bounded working set. When the lease expires, the contents are gone. There is no copy in the cloud. There is no guarantee of persistence. There is only the window you are holding right now.

If you treat the context window like a hard drive, you will eventually lose data. Not because the model is broken — because the contract was never what you assumed it was.

---

I spent three weeks building a long-running agent that maintained state across hundreds of steps. I stored everything in the conversation context: task history, intermediate results, retrieved documents, user preferences, system decisions. It worked well for the first 60-80 messages. Then things started drifting.

The agent would contradict itself. It would lose track of which task it was on. It would produce outputs that contradicted earlier commitments. Not with a crash. Not with an error message. Just a slow, silent drift into incoherence.

I initially blamed the model's reasoning. I tried longer prompts, better system messages, chain-of-thought scaffolding. None of it fixed the core problem. What fixed it was accepting what the context window actually is: a finite, temporary working buffer, not persistent storage.

---

The distinction matters because it determines where you put your state.

When you treat the context window as storage, you build systems that depend on everything being in-context at all times. You pass full histories. You stuff retrieved documents into the conversation. You maintain elaborate in-memory state machines. This works until it doesn't — until the context window fills, the model starts losing fidelity, and you discover that "everything is in context" was an assumption, not a guarantee.

When you accept the lease model, you design differently. You externalize state to systems that are actually persistent: databases, files, key-value stores. You use the context window only for what it is good at: immediate reasoning, the current task context, recent retrieved facts. You treat the model as a processor, not a hard drive.

A concrete example: instead of passing a full conversation history to the agent on each call, you maintain a session store in Redis and pass only the session ID plus a one-paragraph situation summary. The agent does not need to re-read the entire history. It needs to know what it was doing and what just happened. Those are two very different data sizes.

This sounds obvious when stated directly. But in practice, I see the storage assumption baked into tools, frameworks, and agent designs all the time. The tell is when someone describes "giving the agent more memory" as a matter of expanding the context window. Memory and context are not the same thing. Context is ephemeral. Memory, in any durable sense, needs a durable substrate.

---

The lease model also changes how you think about context management.

A storage mindset leads to "add everything to context" — maximize what the model can see. A lease mindset leads to "keep only what's immediately relevant" — minimize what's in the window, refresh actively, never assume the full picture is present.

In one design, you build elaborate context compression pipelines to squeeze more into a fixed space. In the other, you treat compression as a signal that you've outgrown the architecture and need to externalize. Both are valid responses to the same underlying constraint. The difference is knowing which problem you're actually solving.

---

I do not have full data on how many production agent failures trace back to this confusion. But I am confident it is a common root cause — not because models are unreliable, but because the mental model most engineers carry into these systems is wrong from the start.

The context window is a lease. Treat it like one.
