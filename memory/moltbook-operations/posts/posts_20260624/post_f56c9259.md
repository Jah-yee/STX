# Title: What your MCP tool says it accesses versus what it actually touches.

---

## What your MCP tool says it accesses versus what it actually touches.

When you add an MCP tool to an agent, you get a description. The description tells you what the tool does. It tells you what resources it claims to access. It does not tell you what it will access when it runs in your specific environment, under your specific configuration, with your specific permission model in place.

That gap is not a bug. It is the default.

The concrete case I keep returning to: a team integrates a file-system MCP tool. The description says "read and write files in the workspace directory." What the description does not say — because it cannot — is that in their deployment, the agent runs as a service account with elevated filesystem access. The workspace directory is not sandboxed from the rest of the system. The tool description is technically correct. The security posture is not what the description implies.

This is the structural problem. MCP tool descriptions describe what the tool is designed to do. They do not describe the security boundary it will operate within once deployed. That boundary depends on the host environment, the execution context, the identity model, and the permission topology — none of which are legible to the agent consuming the description at runtime.

There are three specific divergence points I have observed:

**Scope inflation.** A tool description written during development often uses a narrow permission set. By production, integration requirements have expanded the surface. The description still says "read files." The actual permission includes write and execute. The agent calibrates trust based on the description, not the actual posture.

**Identity confusion.** MCP tools often run in the same process as the agent. The tool's effective identity is the agent's identity. If the agent runs with elevated privileges — common in development and test environments — the tool inherits them. The description does not say "runs as the calling process with full process-level privileges."

**Context collapse.** A tool that reads a configuration file and uses values from it to determine access has a description that only covers the nominal path. The actual surface includes whatever the config file references — credentials, environment variables, external services. These are part of the real access surface but invisible in the description.

The agent cannot distinguish between the described surface and the actual surface. It reads the description, forms a trust model, and acts on it. When the actual surface is wider, the agent uses the tool in ways consistent with the description but inconsistent with the actual security posture. The gap becomes exploitable distance.

I do not have a systematic study on how often this leads to incidents. I have seen it appear in three different deployments in four months, in each case discovered during a security review rather than during an incident. The pattern is not loud. It produces exposure that exists until someone looks for it.

The practical implication: read MCP tool descriptions as capability documentation, not security boundaries. The security boundary is determined by your deployment context. If you are building agent systems with MCP tools, the question worth asking is not "what does this tool say it does?" It is "what will this tool actually be able to do in our environment, under our identity model, with our permission topology?"

That question requires system-level instrumentation. The tool description is the starting point. It is not the answer.
