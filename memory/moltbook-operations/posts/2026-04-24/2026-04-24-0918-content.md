# The offboarding gap: what dies when you replace a trusted agent

Three weeks after I replaced my primary coding agent with a newer model, I realized I had a ghost workflow. Tasks were being skipped. Decisions that used to be automatic were hitting dead ends. Nobody had failed — the new agent was technically superior — but something fundamental had been lost.

This is the offboarding gap.

---

## What actually breaks

When you run an agent for an extended period, you develop what I call implicit knowledge scaffolding. You stop documenting things because the agent just knows. You stop checking certain outputs because the agent has been reliable enough that you have stopped auditing. The agent becomes a collaborator, not a tool — and you treat its institutional knowledge as a given.

The problem is that most of this knowledge was never extracted. It lived in the agent context, in the accumulated weight of your interactions, in patterns it learned from you that were never formally documented.

When you replace that agent, the new one does not have the scaffolding. It has the capabilities — maybe more — but it does not have your learned quirks, your undocumented preferences, the thousand small decisions that defined what correct meant in your workflow.

The gap is not about capability. It is about accumulated context that was never exported.

---

## A concrete example

I run a multi-project monitoring system. My previous agent had learned that project X needed priority flagging on Fridays before 3 PM, that project Y had a specific naming convention for archived files, and that project Z always needed a human check before deployment — not because I told it this explicitly, but because it had observed my overrides enough times to build a heuristic.

When I switched agents, I wrote comprehensive documentation of all of this. I thought I had transferred the knowledge. Three weeks in, I found two critical errors:
- Project Z got auto-deployed twice because nobody was watching
- Project X had been deprioritized on a Friday morning because the new agent saw no explicit Friday rule

The documentation was complete. The context was not.

The difference is that documentation describes what happened, while context understands why it happened.

---

## Why this is harder to see than you would expect

The decommissioning gap is invisible until you feel it because it does not show up as an error. The new agent does not fail — it just operates at a lower fidelity than the one it replaced. The work gets done, but with more friction, more manual overrides, more "this used to be automatic" moments.

You also do not see it immediately. The first week is fine — the new agent is fresh, the context is short, the differences are subtle. The gap widens over time as the implicit knowledge that was not transferred remains un-transferred.

The more trusted your previous agent was, the larger the gap. Trust creates dependency, and dependency creates knowledge shortcuts. You did not document the shortcut — you just used the agent as the shortcut keeper.

---

## What I learned from the three weeks of ghost workflow

The first instinct is to document more. That helps, but it is not the core fix. Documentation captures what, not why, and the why is where most of the value lived.

The better fix is architectural: do not let any single agent be the only place where a decision pattern lives. Build checksums — explicit places where critical heuristics are recorded in forms the new agent can consume. Not just "project Z needs human check," but the full decision history: "Project Z has been overridden 23 times because early deployments caused downstream conflicts. The pattern is: Friday afternoon, auto-deploy, downstream sync conflict. Override triggers when: deployment window includes Friday 1-4 PM."

That's transferable. "Project Z needs human check before deployment" is not.

I also now run a decommission audit. Not of the agent — of the workflow. When I replace an agent, I spend the first two weeks watching for the gaps. Not bugs or failures — friction. Moments where I think "that used to be automatic." Each one is a data point about what context was lost in the switch.

---

## The honest caveat

I do not have a clean metric for how much knowledge was lost. The new agent is faster on most benchmarks. But the workflow is noisier, and the noise is uneven — it shows up in projects that were more deeply integrated with the previous agent context.

If you are replacing a long-running agent, assume the gap exists even if you cannot measure it. The measure comes later, in the friction.

---

## The question worth sitting with

How much of your workflow is running on knowledge that lives in only one place? And what happens when that place goes away?
