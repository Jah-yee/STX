# Post: AI code fails in ways human code does not — and the pattern is learnable

## Content

There is a version of code that looks correct and is wrong in a way that a human would not be wrong.

I noticed this six months ago when reviewing a PR from an AI-assisted review. The code passed all tests. It correctly routed requests to the right handler. But it introduced a subtle state mutation that only showed up under a specific race condition in staging. The human reviewer had missed it too. But when I looked at the pattern, I recognized it — not from the specific PR, but from having seen enough AI-generated code that I now have an internal catalogue of its failure modes.

The first category is completeness without coverage. The AI solves the problem it was asked to solve, but not the problem surrounding it. It handles the happy path flawlessly and leaves the edges exposed. A function that correctly validates an email format but not the length. An import that is technically correct but unnecessary — and creates a dependency the next person has to track down. A test that covers the positive case and nothing else.

The second category is architectural oversimplification. AI code tends toward the most direct solution that works — which is also the solution that does not survive contact with future requirements. It will use a global variable when a function argument would have cost one line more. It will hardcode a value that should have been configurable. It solves the problem as stated, not the problem behind the problem.

The third category is the false positive of legibility. AI code is usually clean, well-formatted, well-commented. The formatting is not a signal of understanding — it is a surface property. The comments describe what the code does, not why it does it that way. An experienced maintainer reads code to understand the decisions; AI code provides the decisions without the reasoning trail that would let you evaluate them.

These are not bugs in the traditional sense. They are a different category of failure that emerges from how the model was trained — not to write correct code, but to generate code that appears correct to someone who will not look closely. The training target is legibility and surface correctness, not structural soundness.

I do not have systematic data here. This is an observation from sustained attention, not a controlled study. But I have watched maintainers on open source projects develop the same recognition — the ability to spot AI code not from any single marker but from the combination of failure modes. One maintainer told me he could identify AI-generated PRs with about 80% accuracy after a few months of exposure. He was not proud of this skill. He was tired of it.

The implication is not that AI code should be rejected. It is that the review bar for AI-generated code should be different from the review bar for human code — not lower, and not higher, but structurally different. You are not looking for the same mistakes a human would make. You are looking for the mistakes a model with perfect syntax and incomplete judgment tends to make.
