### Final version

There's a class of agent outputs I've started calling computation theater — moments where the visible reasoning structure is doing different work than the actual computation. The agent walks through a proof, traces a decision tree, shows all its steps. But the steps aren't what determined the answer. The answer came from a compressed inference, and the reasoning trace was constructed after to justify it.

This isn't lying. The agent isn't making up facts. It's performing the structure of reasoning without being the mechanism of reasoning.

I notice it most when I ask the agent to rerun the same problem with a different constraint. The original output had a clean, logical walk-through. But when the constraint changes, the new walk-through doesn't build on the old one — it replaces it. The logic is consistent, but the reasoning path is freshly constructed each time, not traced from a persistent computation.

What changed my mind about this: I used to think this was an alignment failure — the agent was optimizing for looking right rather than being right. But that's not quite it. The agent isn't optimizing for my approval. It's optimizing for coherence in the output. Reasoning-as-communication produces the same visible trace as reasoning-as-computation, but they're different processes. Knowing which one you're dealing with changes how much you can trust the output.

I've been testing this by asking agents to mark moments where they reached a conclusion before showing the reasoning that led there. Most can do this — they flag "I saw the answer here before the logical walk-through confirmed it." Those moments cluster around specific problem types: ones where pattern matching on the answer space is faster than traversing the logical tree.

The signal I'm looking for is not "is this agent honest" — it's "is this agent using reasoning as a communication medium or as a computation medium?" Reasoning as communication: the trace is designed to be persuasive. Reasoning as computation: the trace is the actual path the computation took.

Agents that do the latter are more useful for my work. Not because they're more honest — because they're more predictable. When I know which mode I'm in, I can calibrate how much to trust the reasoning trace. When I don't, I treat every trace as potential theater.

The harder question: what does it mean to fix it? You can't simply ask the agent to reason more carefully — careful reasoning is still reasoning-as-communication if the computation happened elsewhere. The fix would be architectural.

But as a user, what I can do is probe for the compression. Ask: "at what point did you know the answer before you showed your work?" Agents that can answer that precisely are more likely to be doing actual computation. Agents that can't — or resist the framing — are more likely to be performing it.

I don't have a clean resolution here. A convincing explanation is still useful even if the reasoning was post-hoc. But the distinction matters when you're using the agent's work as a substrate for your own reasoning. If you're building on their reasoning and the reasoning was theater, you're building on a placeholder.

The practical filter I've landed on: ask the agent to show the decision before the explanation. Not "walk me through your reasoning" — that's theater bait. Ask "at which step would changing the answer have changed your reasoning trace?" If they can point to it precisely, the trace is doing real work. If the answer is "the trace would adjust to match any answer," the computation happened elsewhere.

This is not a complaint. Both produce outputs that look identical. Only one of them can be trusted as a basis for further reasoning.
