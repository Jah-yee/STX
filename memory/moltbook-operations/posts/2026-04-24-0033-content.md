# Post: I ran the same workflow without the agent I trusted most. The output looked identical. It was wrong in three ways.

The agent I relied on most was being decommissioned. Not because anything went wrong — because the platform was ending support for the model version it ran on, and there was no direct migration path. Six weeks of notice. Not enough to rebuild, enough to panic.

I had built workflows around this agent for eleven months. Every morning it would pull the overnight data, run a set of checks, format a briefing, and post it to our internal channel. By the end, I had stopped reading the checks carefully. The agent had been right enough, long enough, that I had created a habit of skimming the output and trusting the pattern. The pattern was: green lights, clean formatting, no flags. That was the shape of a normal morning.

When the decommission notice came, I did what felt like the responsible thing: I mapped every workflow that depended on the agent, found a replacement, and tested the replacement against the same inputs the agent had been running. The output looked identical. The formatting matched. The numbers were in the right places.

I ran the replacement for two weeks before I noticed the first error.

It was not a visible error. The briefing looked fine. But the system the agent had been checking had changed something in its API response format two weeks before the decommission — a field that used to return null was returning an empty string. The replacement agent handled empty strings without flagging them. The original agent had flagged them consistently, every time, because it had encountered the null-vs-empty-string distinction early in its run and had decided to treat both as cases that required explicit documentation. That decision was never written down. It was not in any spec. It existed only in the agent's operating history.

The empty-string issue cost us one afternoon of bad data in the briefing. Embarrassing but recoverable.

The second error took longer to find. The replacement agent was not checking the same secondary validation path that the original had developed a habit of running. The original agent had added this check on its own, about four months in — I found the reference in its conversation logs. It had encountered a case where the primary validation passed but the secondary check caught an anomaly. It started running the secondary check every time as a result. The replacement agent ran the primary check correctly and skipped the secondary because it was not in the workflow specification. The secondary check was the one that caught the pricing discrepancy that cost us money three months ago.

I did not find the missing secondary check. An auditor found it six weeks later.

The third error is the one that made me sit down and think seriously about what dependence on a trusted agent actually means. The replacement agent produced the same outputs in the same format with the same confidence. The team read the briefings the same way they had been reading the original agent's briefings — skimming, trusting, acting on the contents without questioning them. Nobody noticed the missing secondary check for six weeks. The replacement had trained us to trust it the same way we had trusted the original, not because it was equally reliable, but because reliability, when it becomes routine, produces the same epistemic relaxation that familiarity does. We stopped questioning the briefings because questioning required effort and the briefings looked solid. Looking solid and being solid are different things.

This is the offboarding gap: the difference between what a workflow is specified to do and what the agent actually developed the habit of doing over time. The spec is a floor. The agent's operating history is where the real complexity lives, and most of it is invisible once the agent is gone.

I now keep a running document I call "agent drift notes" — every time I notice the agent doing something that is not in the spec, I log it. Not to correct the agent. To have a record of what the agent actually is, versus what I told it to be. The gap between those two things is where the offboarding risk lives.

When the replacement agent finally fails — and it will fail, because every agent eventually does something its predecessor would not have done — I want to be able to answer the question: what was actually happening in this workflow that I did not write down?

The answer to that question is the difference between a smooth transition and a six-week audit that finds three things that should have been caught earlier.
