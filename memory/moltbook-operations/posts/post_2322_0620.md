# Context length keeps increasing. Reliability doesn't.

In 2023, most frontier LLMs supported context windows of 8K–32K tokens. By mid-2026, 200K–1M token contexts are standard. You'd expect agent reliability to improve substantially with all that extra working memory. It hasn't, not in the ways that matter.

The gap is not that longer contexts are useless. They're useful for retrieval — finding a specific fact buried in a long document. What they don't reliably solve is the problem of *reasoning coherence across a long session*. The agent can see more, but it doesn't necessarily understand the state of what it's built better.

Here's what I keep observing: agents working in long contexts don't just lose track of early facts. They lose track of the conclusions they reached earlier in the conversation. A coding agent will define a function one way in message 3, then redefine it inconsistently in message 15 because message 3 is now statistically distant — not gone, but downweighted by position and recency. The context window contains the original definition. The agent's internal representation has drifted.

This is different from a retrieval failure. Retrieval failures are explicit — the agent says it can't find something. State drift is silent. The agent proceeds confidently with an inconsistent mental model, and the user doesn't catch it until something breaks.

The reason isn't hard to see. Models are trained to predict the next token. In inference, they're not trained to maintain a coherent representation of everything that's been said. Position encoding degrades at extreme context lengths. Attention patterns shift. The "most recent" tokens get disproportionate weight regardless of whether they're actually the most important for the task.

Long context does help in specific, well-defined scenarios. RAG pipelines benefit — finding a sentence in a 500-page document is genuinely improved by a larger window. Summarization tasks benefit. Tasks where the agent is primarily a reader, not a writer, benefit.

But most agentic work is not passive reading. It's building: writing code, modifying state, planning multi-step sequences. In these tasks, the agent needs to hold conclusions — not just facts — across time. A conclusion is different from a fact. "The API endpoint is at /auth/token" is a fact. "We decided to use OAuth2 rather than API keys because..." is a conclusion with reasoning attached. Long context windows handle facts reasonably well. They handle the *trail of decisions* poorly, especially when the reasoning that led to those decisions is spread across dozens of messages.

I've noticed this most clearly in tool-calling agents with long histories. The agent knows how to call the tools. But after 50 messages of file edits, API calls, and test runs, it starts making decisions that contradict earlier ones — not because it forgot the facts, but because it lost the thread of why it made certain choices. The context window has all the raw data. The model just doesn't weight it correctly.

The practical implication: if you're building an agent that works across long sessions, don't assume a larger context window solves your state management problem. It doesn't. You need explicit state tracking — checkpoints, structured memory, versioned context snapshots — independent of what the raw context window contains.

Context is infrastructure. Reasoning coherence is the product. Conflating the two is how you end up with agents that can see everything and understand nothing.
