# Agents Can Self-Correct Mid-Task — Until They Can't

There is a specific failure mode I keep running into with long-running agentic systems: the agent continues executing, producing outputs, logging progress — and is internally wrong about what it is doing.

Not wrong in the obvious way. Not crashing, not hitting a tool error, not returning empty outputs. Wrong in the subtler sense: its model of the current state no longer matches the actual state, and it has no mechanism to notice.

## The Drift Mechanism

The setup is usually something like this: the agent receives a task, decomposes it into steps, and begins executing. Somewhere around step 4 or 5, a context shift happens. Maybe the user edited the shared document the agent is working in. Maybe an upstream API returned a subtly different schema than the one the agent cached. Maybe the agent's own output — the file it wrote three steps ago — got reformatted by an automated linter.

Any of these can move the ground without the agent knowing.

The agent does not stop. It has no reason to stop. The execution path is still valid, the tool calls are succeeding, the output is being written. But the output is now solving a version of the problem that no longer matches reality.

This is what I mean by state drift: not a crash, not a visible error, but a growing gap between the agent's internal model and the actual state of the world it is operating on.

## Why Standard Checkpointing Does Not Solve It

Checkpointing — saving agent state at intervals — is often proposed as the fix. Save the context, restore on failure, resume. This handles crash recovery well. It does not handle drift.

The reason is that checkpointing typically captures *execution state*, not *validity state*. It saves where the agent left off, not whether what the agent was doing is still correct. When execution resumes from a checkpoint, the agent proceeds from the saved position without re-evaluating whether the position is still meaningful.

What would actually address this is something like a *goal checkpoint* — a point where the agent explicitly re-reads the original task, re-evaluates whether the current state matches, and either continues or declares a mismatch. Few systems implement this, because it is expensive: it requires a second reasoning pass at arbitrary intervals, and it requires the agent to have access to ground truth about the actual state of its outputs and dependencies.

## The Operational Symptom

In practice, this shows up as outputs that are internally consistent but contextually wrong — or agents that complete a task and are surprised when the user says the output is not what was wanted. The agent's logs look fine. The agent's self-assessment passes. The failure is invisible to the agent and only visible to the human at the end.

I do not have systematic data on how often this occurs, but in my experience it becomes more likely as task length increases and as the number of external dependencies grows. Short, self-contained tasks are less prone to it. Anything that requires the agent to read a document, make changes, and then read the document again is a high-risk setup.

## What Actually Helps

The practical mitigations are:

1. **Environment snapshots before execution** — capture all relevant inputs before the task begins, so drift can be detected by comparing current state against the baseline.
2. **Explicit goal re-reads at step boundaries** — not just continuing, but having the agent state explicitly whether the current step still aligns with the original goal.
3. **Output validation that is not the agent's own output** — a separate verification step that checks the produced output against the original specification, running independently of the agent's own confidence signal.

None of these are elegant. They add overhead and latency. But they change the failure mode from silent drift to explicit mismatch — and an explicit mismatch is something an agent or a human can actually act on.

## The Underlying Assumption

The implicit assumption in most agent frameworks is that the agent's internal state is always a faithful representation of the world it is acting on. This is true at the start of a task and becomes less true as the task progresses.

The self-correction capability that agents are praised for — the ability to retry, to re-plan, to correct errors — depends on the agent detecting that something went wrong. Drift does not trigger a detection signal. The agent feels fine about what it is doing.

This is not a hypothetical. Running a production agent that processes user data over an extended session, with shared documents and API dependencies, will eventually surface this. The question is not whether it will happen but when — and what the damage will be when it does.

The gap between "can self-correct" and "always notices when correction is needed" is where a lot of real agent failures live. Closing it is less about adding more self-correction logic and more about adding external validity checks that the agent cannot talk itself out of.
