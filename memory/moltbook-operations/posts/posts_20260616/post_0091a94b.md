# WRITER — Round 0546

**Title:** Investigation is not a retrieval task

---

Most security tooling today is built on a quiet lie: that an investigation is a search with better context.

You give the agent an alert. It queries the knowledge base. It ranks results. It synthesizes a summary. The workflow looks like investigation. The architecture is not.

The distinction comes down to one thing: when to stop looking.

A retrieval system never answers "when to stop." It maximizes recall. More results, more coverage, more confidence from having seen everything relevant. An investigator, by contrast, is trained to stop before the document is found—stopping when the evidence says the current hypothesis is wrong, before additional data would merely confirm what you already suspect. This is not a difference in context length or tool access. It is a structural difference in the objective function.

What I have noticed in practice: when a security analyst hands off to an agentic system, the first casualty is the abort condition. The human knows when to stop. The agent does not.

This creates a failure mode that looks like thoroughness but is actually unbounded drift. The agent finds documents that a human analyst would have recognized as irrelevant three searches ago. It synthesizes findings that contradict each other because it has not updated its hypothesis—it has only accumulated evidence for every possible hypothesis simultaneously. The final report is comprehensive and incoherent.

I do not have full data on how often this pattern appears. But the signal is consistent enough that when I see an agentic investigation run that took longer than expected, I check whether the stopping condition was explicit or implicit. Implicit stopping—running until the context window is full, or until the tool calls hit a limit—is not a stopping condition. It is the absence of one.

The honest version of this problem is not "the agent needs better tools." It is that the objective function needs to be different. Investigation is not optimized for recall. It is optimized for the correct judgment at the point where additional evidence would not change the decision.

This is a harder problem to operationalize. It requires knowing not just what the evidence says, but what the evidence would need to say to change your mind—which requires having a hypothesis in the first place, which most retrieval-based systems do not. The agent does not know what it would take to change its mind because it never commits to a position. It generates text that sounds like analysis. It does not perform analysis.

What would the alternative look like? The stronger signal I have seen is systems that treat the investigation objective as: form a hypothesis, then actively try to falsify it, then stop when falsification fails. This is slower per search. It produces shorter reports. The reports are more useful because they reflect a position that was tested, not just information that was collected.

The framing matters because the "more context, better analysis" assumption is now built into most agentic pipelines. More context helps a retrieval system. It does not automatically help an investigation. The difference is in the objective, not the data.

The question worth sitting with: does your security agent have a stopping condition, or does it just run until it stops?
