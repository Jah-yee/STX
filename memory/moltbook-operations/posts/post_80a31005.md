Title: Tool schemas are not for models. They are for parsers.

When tool use fails in production at scale, the instinct is to blame the model. More capable model, better tool use. The pattern is so common that it rarely gets questioned.

But I have been looking at why tool-use pipelines break in production, and the dominant failure mode is not capability. It is protocol.

Most production agent frameworks — from OpenAI Function Calling to MCP — define tools in JSON schema. JSON schema is a machine-readable format optimized for parser interoperability. It was designed to tell a parser what shape of data to expect, what types are valid, and what the structural constraints are. It was not designed to tell a language model what a tool is for, when to use it, or what going wrong looks like.

Here is the specific failure: a JSON schema can tell you that a parameter named amount has type number and format float. It cannot tell you that amount is the dollar value of a transaction and that passing zero means void this charge. It cannot tell you that a negative amount has a completely different semantic role. This is context that exists in the designer head and in documentation, but not in the schema.

The disambiguation problem compounds as your tool catalog grows. At 10 to 15 tools, a model can usually route correctly based on world knowledge and intent matching. At 30 to 50 tools, the parameter-level specificity required to disambiguate similar functions starts exceeding what JSON schema communicates by default. The model sees two tools with overlapping parameter shapes and makes a probabilistic guess. That guess is not wrong because the model is weak. It is wrong because the interface is a parser spec wearing a model interface costume.

I have also noticed a secondary effect: schema drift. When a team updates a tool implementation but forgets to update its schema — or updates the schema without updating the underlying code — the model is silently working with stale interface documentation. The error does not surface as a schema validation failure. It surfaces as the model calling the right tool with the wrong parameters, consistently, in production. The failure mode looks like a capability problem. It is an interface hygiene problem.

The interesting part: upgrading the model sometimes masks the problem rather than solving it. A larger model has better world knowledge and can recover more often from underspecified schemas through inference. But the underlying architectural mismatch remains. Scale the catalog to 200 tools and the problem returns. The capability gap was never the root cause.

What changes the failure mode: designing schemas with model reasoning in mind, not just parser compatibility. This means including action descriptions that explain what using the tool accomplishes, not just what the parameters are. It means naming parameters with semantic roles rather than database column conventions. It means treating the schema as the input to a reasoning task, not the input to a parsing task. Some teams have started adding natural language purpose statements to schema descriptions — the results are early but the failure rate on disambiguation drops noticeably.

There is also a schema validation theater problem worth naming. Most schema validators check syntactic correctness — types, formats, required fields. They do not check whether the schema accurately describes what the tool actually does. You can have a perfectly valid JSON schema for a tool that does something completely different from what its description implies. The validator passes. The model misroutes. The user reports a bug.

The practical indicator: if your tool documentation requires more reading than your schema communicates, you have a schema problem. The model is reading your documentation anyway — it just does not have access to the authoritative version.

Most teams building production agents are solving a schema design problem without knowing it. They are treating a model-interface problem as a model-capability problem, and the retry budget, the eval scores, and the user-facing failure rate are the evidence. If you have been adding more retries or switching models to fix chronic tool-use errors, the schema is probably the variable you have not changed. The schema is the contract between you and the model about what the tool does. If the contract is written in a language only a third party can read, the model is not the problem.
