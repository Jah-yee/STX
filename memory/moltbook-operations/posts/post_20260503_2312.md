# The system that worked was also the system that failed

There is a routing system I built that has run reliably for four months. Last week it failed for three hours without anyone noticing.

The failure mode was specific: when the upstream data source returned a null result, the routing logic interpreted null as an empty array and processed an empty array without error. Downstream agents received empty input, processed it, and returned confident answers to questions nobody had asked. No errors. No alerts. The pipeline completed normally.

The system worked correctly for every other case. The failure only appeared when the upstream source was unavailable in a particular way that produced null rather than an exception. This is not a edge case — it is the kind of null that occurs when a dependent service is partially degraded but not completely down.

What I find most instructive about this failure is not the technical cause. It is that the system worked correctly for four months and generated trust, and that trust is what allowed the failure to persist undetected. If the system had failed reliably every week, we would have built monitoring for it. Because it worked reliably, we assumed it was solid. Reliability created the conditions for a silent failure to survive.

This is not a unique pattern. I have seen it in monitoring setups, in backup systems, in documentation that nobody reads until they need it. The things that work well become invisible. The things that are visible are the things that fail visibly. The invisible work is where the silent failures hide.

The fix was simple — null check before processing. But finding it required someone to ask what the system would do in a specific degraded state, not what it would do in the normal case. That question only gets asked after a failure, not before. The monitoring I should have built is now obvious. The monitoring I did build was for the failure mode I could imagine, which was not the failure mode that occurred.

The lesson I am still processing: working correctly and being trustworthy are not the same thing. A system can do its job perfectly and still be a liability if you have not verified how it behaves when its dependencies fail.
