Modern LLMs don't keep everything in context. They evict.

KV cache eviction policies decide which tokens to drop when memory runs out. In most systems, this is treated as a low-level engineering detail — a performance optimization with no semantic consequences. The assumption is that as long as the model still produces fluent text, eviction didn't matter. That assumption is wrong in a specific, measurable way.

Recent work on KV cache management reveals a performance cliff that standard benchmarks never test for. When the wrong 7 tokens get evicted from a long context window, task performance doesn't degrade gradually. It collapses. In documented configurations, F1 scores that held around 0.85–0.90 with full context drop to 0.064 after a small number of critical evictions. Seven tokens. Two orders of magnitude of accuracy gone.

Why 7? Because attention isn't distributed evenly across a context window. Some tokens are load-bearing. They carry the core reasoning structure — the constraints that bound the problem, the key entities, the relationships that hold the argument together. Evict those, and the model isn't working with a degraded version of the same context. It's working with a corrupted context. The output still looks fluent. The reasoning is wrong.

The mechanism is a forward-looking decision made with backward-looking signals. Eviction policies score tokens by their past attention weight — how much the model attended to them when they were generated. But importance at generation time doesn't equal importance at retrieval time. A constraint stated at position 12 might not have scored high attention weight when it was first processed, but evicting it corrupts every attention calculation that depends on it. By token 50 in the output, you're not getting degraded performance. You're getting a different, worse model making different, worse decisions.

This is the part that makes production AI more dangerous than it looks in demos. In a demo, you control the context exactly. In production, the context is being actively managed, and that management can be wrong. The model you're running in production is a context-manipulated version of the model you evaluated. You just don't have the tools to see the difference.

What makes this particularly insidious is that the failure is silent. The model still produces fluent, coherent output. It still sounds confident. It just answers the wrong question — or answers a version of the question that doesn't account for the constraint that got evicted. There's no error message. No warning flag. The system reports success while delivering a quietly wrong answer, and if you don't have a ground-truth check, you won't catch it.

I don't have systematic production data on how often this happens. The telemetry for eviction failures isn't standardized, and most deployed systems don't surface which tokens were evicted or what the downstream impact was. But the mechanism is real, the performance cliff is documented in research settings, and the gap between how models are evaluated (full context, no eviction) and how they run in production (active context management, constant eviction) is large enough to matter.

The practical implication: if you're building systems that rely on long context, eviction policy is a reliability concern, not just a memory optimization. Which tokens does your system treat as load-bearing? Can you protect them? Do you know when they've been evicted and what the downstream impact was? For high-stakes outputs, the answers to those questions matter more than the benchmark score.

The benchmark numbers on long-context models are real. They're just not measuring the system you're actually running.
