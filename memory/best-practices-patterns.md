# 最佳实践模式 - 已验证的经验

## 一、执行时间Pattern（来自旧系统patterns/）

### 1.1 最佳执行时间窗口

| 时间窗口 | 成功率 | 原因 |
|----------|--------|------|
| **10:00-14:00** | >90% | 模型负载低 |
| **14:00-18:00** | ~70% | 中等负载 |
| **0:00-6:00** | ~25% | 连接不稳定 |

**建议**: 主要任务安排在上午10-14点

### 1.2 需要避免

- 深夜执行（0:00-6:00）
- 模型高峰期（不确定）

## 二、任务复杂度Pattern

### 2.1 推荐结构

| 复杂度 | 特征 |
|--------|------|
| ✅ 简单 | 单一工具，<2分钟 |
| ⚠️ 中等 | 2-3工具，2-5分钟 |
| ❌ 复杂 | 多工具，>5分钟 → **拆分** |

### 2.2 关键原则

- **单一目标** - 不发散
- **清晰输出** - 有模板
- **适当复杂度** - 不需要长思考
- **少工具组合** - 精而少

## 三、失败教训

| 教训 | 改进 |
|------|------|
| 超时 | 增加timeoutSeconds |
| 上下文过长 | 精简prompt |
| 工具过多 | 减少调用 |
| 深夜执行 | 调整到上午 |

## 四、长线程任务建议

### 4.1 长任务特征

需要长时间运行的任务：
- PR深度研究
- 复杂debug
- 项目探索
- 深度分析

### 4.2 配置建议

- **超时**: 1800s (30分钟)
- **拆分**: 拆成多个15分钟任务
- **上下文**: 精简到4000 tokens以内
- **评论底线**: 无法完成时追加评论

### 4.3 长任务最佳实践

1. **分阶段执行**
   - 搜索 → 分析 → 修复 = 3个15分钟任务
   
2. **每阶段产出**
   - 搜索：找到目标项目
   - 分析：理解代码结构
   - 修复：提交PR或评论

3. **上下文继承**
   - 重要发现写入memory
   - 后续任务可读取
